## **Agent 化的攻击需要 Agent 化的防御**

在针对一家公司发动攻击时，攻击者通常走过同样的流程：把公开数据武器化 → 构造伪装身份作为诱饵 → 攻入内部系统。这个流程已经被 AI 加速。

在动手入侵任何东西之前，他们会先搜集关于该组织及其高管、员工的公开信息。

然后把这些情报变成诱饵——比如一个带着伪造登录页的假网站——诱骗受害者交出凭证。从这些诱饵中获得的访问权帮助攻击者突破边界，触达组织最有价值、最敏感的资产。

这一三段式的攻击链是可预测的，但传统的安全工具每次只能守住其中一片：

- 威胁情报工具盯住"公开数据"阶段
- 品牌保护工具监视"伪装身份"阶段
- 端点工具守护"内部系统"阶段

Outtake 的 Recon Agent 调查的是一次伪装身份背后那整张网络。例如，它不是仅仅把一个克隆的登录页下架，而是从这次伪装身份事件中收集并归类证据。

它顺着这些线索追到关联基础设施——比如一个假装自己是"客服"的假冒 Telegram 账号——并在一张图中绘制出这张对手网络。Agent 的最后一步产出一份报告，解释调查过程、刻画威胁行为者的画像、并重建攻击者所做事情的时间线。

为了执行这种复杂工作流，Recon Agent 能够读写并运行代码。它甚至能与恶意的登录页直接交互，看看被盗凭证到底流向哪里。

这些调查可能要求 agent 长时自主运行。Agent 会话的中位时长是 16 分钟，但常常会拉长到一小时以上；目前最长的一次会话跑了两小时的智能体工作才返回结果。

## **Outtake 如何用 Claude 构建一个复杂的长时运行 agent**

Outtake 大致用四个阶段构建了 Recon Agent。每一阶段都是先弄清"一次好的调查是什么样"，然后把这种判断逐步交给 agent。

### **第一步：先成为那个领域的专家**

在动手搭建 agent 的任何部分之前，Outtake 的工程师自己亲手跑过真实的网络调查，并从客户与设计伙伴那里吸收领域专业知识。

目标是定义"好"长什么样。对这类调查而言，这意味着识别"哪些证据是重要的"、"如何组织这些证据"、"什么把可下结论的判断与猜测区分开"。这个标准成为他们在后续每一阶段都会回到的固定参照点。

> "构建长时运行 agent 时最重要的事，是你真的必须搞懂'什么是好？'、'agent 应当做什么？'，"Outtake agent 平台工程负责人 Jack Hayford 说。"因为最终，你要确保 agent 每次都能做到那件事。"

### **第二步：在 Claude Code 中做原型**

起初，Outtake 团队用传统的 agent 框架，去逐步自动化他们正在标准化的那些调查。

但他们很快意识到，Recon Agent 不能只是一个简单的调查员。它需要写代码、跑代码、现场造工具，还要真的能与恶意域名交互。

> "每一次调查都不同，且技术深度极高，"Hayford 说。"agent 需要编码能力，而 Claude Code 是一个强有力的初始 harness，让我们能够验证这些假设，并且越试越多。"

正是在 Claude Code 里做原型的过程中，他们锻造出核心的设计原则：**在编排层面对 agent 做紧约束**（"调查一个域名时，永远要执行 X、Y、Z"），但在需要判断的地方，**让它自由即兴发挥**。

### **第三步：升级到生产级的 harness**

> "我们非常喜欢 Claude Code 引入的那些模式，但我们需要更深入地接触到那些底层原语——而我们并不打算自己造这些，"Hayford 说。

用 Claude [Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) 是把 Recon Agent 推上生产的自然下一步。把 Claude Code 的 skills 与模式带过来，让团队在获得对 Recon Agent 内存、上下文、文件系统更精细控制的同时，没有为了 agent loop 和会话处理而"重复造轮子"，也不会丢掉节奏。

### **第四步：构建由 evals 驱动的紧密迭代循环**

能以低成本、高响应速度迭代的能力，在网络安全行业尤为关键——攻击者只要察觉防御工具存在就会立刻调整打法。团队从一开始就嵌入了 agent evals，并搭起一套能同时跑大量场景的强 eval 套件。这让他们能安全、充满信心地做出"重大改动"——比如模型升级、整套内存系统的重构。

它也让团队得以把自己从 agent 循环中抽出来。例如：当 Recon Agent 完成调查后回报说"如果当初有某样工具我能做得更好"，一个独立的编码 agent 会读取它们，写出新工具，并搭一个测试场景试一下。

只有在最后，才由人来检视结果：有了那个工具之后，agent 的调查是否真的更好了？"我们才是瓶颈——当你搭建这些长而复杂的 agent 时，让反馈循环自动化非常重要。它既快得多，作为开发者也愉快得多，"Hayford 说。

## **构建一个长时运行 agent 的心得**

在 agent 时代的早期，构建者会预先把 agent 行为脚本化为硬编码的、确定性的、一步步的路径，防止它跑偏。如今，复杂的工作流正在被一种 "harness" 取代：一个由内存、工具、skills 与护栏组成的支持性环境。

以下是 Outtake 团队在落地 Recon Agent 时总结的几条心得：

### **工具：一个文件系统 + bash 就够了**

文件系统让记忆能扛过压缩。Agent 通常被给予非常具体、非常细致的工具；但给 agent 一个文件系统，外加读写和运行代码的能力，能帮它在遇到障碍时灵活应变。

> "把这些极其强大、开放式的工具和能力交给 agent 是一个巨大的飞跃。我们观察到大量这样的场景：agent 拥有的某个工具因网络抖动之类的原因失败了，它会自己找到正确的 workaround 并继续，"Hayford 说。"因为我们搭的 harness 足够强，又把这些强大、开放式的工具留给 agent 即兴发挥的空间，它依然能走向成功的结果。"

### **Prompt 只是建议**

Prompt 在需要时提供弹性，但凡能硬编码之处就硬编码以确保稳定性。"当你搭建这些长时运行的、随时间越来越复杂的 agent 时，prompt 就是建议，"Hayford 说。"当 agent 没做到你想做的事时，自然的反应是去往最'软'的地方补——在系统 prompt 里塞一句'当 X 发生时，确保你做 Y'，短期内也许管用，但随着这个 agent 运行得更久，那段 prompt 里的每一个字最终大概率都会被忽略。"

正确的做法是把这种可能性纳入设计：先把"agent 每次都要做的事"识别出来，让它成为 agent 护栏的一部分。"把这些东西从 prompt 里抽出来，放进 harness 里，"他说。"这样 agent 就不必再想它，腾出了更多上下文空间与注意力，可以投向那些它真正能出彩的领域。"

*更多关于引导 Claude 的最佳实践，以及每种方法的"context 成本与权威性"，请读 *[*Steering Claude Code*](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)*。*

### **Evals 是为了速度，不只是可靠性**

把人工"复盘"作为通往自动化 evals 的路线图，从而缩短开发周期。** 传统观点认为 evals 是可靠性的质量门槛。但对长时运行的 agent 来说，更大的回报在于速度。

早期，每次 Recon Agent 跑起来，团队都会手工复盘它的表现。但读一份 30 分钟的 agent transcript 既痛苦又不可扩展。

> "在现代 agent 开发里，对产出做评估是循环中最昂贵的一步，"Jack 说。

Eval 就是那种"复盘"的结构化、可打分、可自动化的版本。一旦把"什么是好"编码成可重复的检查，你就可以让一位 agent 当"评委"——读那份 30 分钟的 transcript 并给这次运行打分。

> "我觉得有些工程师对搭 evals 心存顾虑，因为这听起来像是要建一个'完美的用例'，"Jack 说。"从一开始就搭建 evals 的某种版本，会让你搭出那个 agent 的速度更快——无论它们有多'不正式'或者多不'完美'。"

### **保护你的 agent**

[Prompt injection](https://www.anthropic.com/research/prompt-injection-defenses) 是真实的威胁，所以把你的 agent 放进沙箱、或者给它"穿甲"是必要的。Outtake 选择 Claude，部分原因就是它在 prompt injection 上的抵抗力。

> "安全是 Recon Agent 构建过程中的重点关注项，"Hayford 说。"我们给了它一个文件系统和 bash，又把它送到对抗性环境里，所以我们必须解决的最重要问题，是搭一种'防爆箱'——既能保护你的 agent 不被敏感的内部信息暴露，又不阻碍它工作。"

他们的方案假定 agent 可能会被劫持，因此围绕它的系统就被设计为能"收得住"损害。但安全在不同 agent 之间长相不同，取决于它们的目的，并非所有 agent 都适合"防爆箱"模式。

Outtake 现在正对 agent 触达互联网的那一刻做"信任评分"：在它接触任何东西之前，先在检查点上问："这个页面是伪装身份？是恶意软件？是现在正在试图对 agent 做 prompt injection 吗？"当 agent 在一个日益对抗的互联网上穿行时，这也许正是它们需要的"甲"。

## Outtake 团队的最佳实践

**你知道"什么是好"长什么样吗？**
**先做一次那个 agent。** 亲自跑一遍真实任务，从客户和设计伙伴那里吸收领域知识，建立一个固定标准来对照之后每一次迭代。

**每一处复杂度都是必要的吗？**
**找到最简单的、能跑的版本，再一段段自动化。** 只有当结果证明值得时，才增加复杂度——和传统软件一样的纪律。

**你的 harness 与工作负载匹配吗？**
**在 Claude Code 里快速验证假设**，当需要对内存、上下文与会话有更低层级控制时，再升级到 Agent SDK。不要自己重写 agent loop。

**agent 应当在哪里被约束？**
**在编排层面硬编码护栏，但不要让这些约束下探到低层判断。** 即兴发挥的空间，才是最佳结果的来源。
