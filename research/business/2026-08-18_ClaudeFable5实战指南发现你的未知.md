# Claude Fable 5 实战指南：发现你的"未知"

*原文标题：A field guide to Claude Fable 5: Finding your unknowns*

> 原文链接：https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns

在使用 Claude Code 时，我经常想起"地图"和"实地"之间的差别。

地图——对工作的一种表征——是我的 prompt、skills、上下文，也就是我交给 Claude 的东西。实地是工作真正要发生的地方：代码库、现实世界、它实际的约束。

![]()

地图与实地之间的差别，就是我所说的 *未知（unknowns）*。当 Claude 撞上一个未知，它必须基于"我大概想要什么"的最佳猜测做出决定。工作越多，Claude 可能撞上的未知也就越多。

Claude Fable 是我遇到的第一个模型：产出质量的瓶颈，落在"我能不能为它澄清这些未知"这件事上。

重要的是，事先规划并不总是足够的。你可能在实现深处才发现未知，或者你的未知会指向一个事实——你其实应该用完全不同的方式来解决这个问题。

我发现，与 Fable 协作是一个**在实现前、实现中、实现后**不断发现未知的迭代过程。

## 认识你的未知

什么是你的未知？当我带着一个问题去找 Claude 时，我倾向于把它拆成四种：

- **Known Knowns（已知之已知）**：本质上就是我的 prompt 里写下的内容。我告诉 agent 我想要什么？
- **Known Unknowns（已知之未知）**：我还没想清楚，但我知道我没想清楚？
- **Unknown Knowns（未知之已知）**：太显而易见到我永远不会写下来，但看到时能认出来？
- **Unknown Unknowns（未知之未知）**：我根本没考虑过的？我意识不到自己缺哪些知识？我知不知道某件事能"做多好"？

最顶尖的智能体编码者拥有的未知相对较少。观察 [Boris](https://www.linkedin.com/in/bcherny) 或 [Jarred](https://www.linkedin.com/in/jarred-sumner-a8772425) 这些人写 prompt，可以明显看出他们非常清楚自己想要什么。他们与代码库、与模型行为都深度同频。

![]()

但他们同样会假设未知的存在。在很多层面，"减少并为未知做规划"就是智能体编码的 **skill**。幸运的是，这是一项可以与 Claude 协作、不断提升的技能。

## 帮助 Claude 帮到你

给 Claude 指令是一门需要拿捏的学问。如果你太具体，Claude 会照办，哪怕它本来可以走一条更合适的岔路。如果你太模糊，Claude 又常常基于业界最佳实践做出选择和假设——而这未必契合你的任务。

当你没有把未知纳入考量时，两头都会失败：你不知道路上何时会有障碍，也不知道何时一路坦途，但你仍然希望 Claude 能灵活转向。

Claude 能帮你更快地发现未知。它可以极快地扫描你的代码库和互联网，对大多数话题的知识量也远胜于你。它也能更快地从失败中迭代。

这个过程中最重要的，是把你的"起点"交给 Claude。比如告诉它你在思考链的哪一环；坦白你对问题和代码库的熟悉程度；让它像一个"思考伙伴"那样与你协作。

本文会详细介绍我用来揭示未知的一些模式，包括：

**实现前（Pre-implementation）：**

- 盲点扫描（Blind spot pass）
- 头脑风暴与原型（Brainstorms and prototype）
- 访谈（Interviews）
- 参考资料（References）
- 实施方案（Implementation plan）

**实现中（During implementation）：**

- 实现笔记（Implementation notes）

**实现后（Post implementation）：**

- 推销与说明文档（Pitches and explainers）
- 自测题（Quizzes）

## 实现前

### 盲点扫描

开始一项工作时，你能做的最有价值的事之一就是理解自己的盲点。比如你在代码库的新区域写一个特性，或者让 Claude 帮你做你不熟悉的工作——比如对一个设计做多轮迭代——你很可能就有大量 **unknown unknowns**。

你可能不知道该问什么、不知道好的长什么样、不知道历史上做过哪些工作、或者不知道要避开哪些坑。

在这些情况下，你可以让 Claude 帮你找出 unknown unknowns 并向你解释。我喜欢直接用 "blind spot pass" 和 "unknown unknowns" 这两个原词。把"你是谁、你已经知道什么"这样的上下文告诉 Claude，通常对 Claude 找到合适的协作起点很重要。

**示例 prompt：**

- "我要加一个新的认证提供方，但我对这套代码库的认证模块一无所知。你能做一个盲点扫描，帮我找出相关的 unknown unknowns，并帮我把 prompt 写得更好吗？"
- "我不知道什么是 color grading，但我需要给这段视频做调色。你能教我认识我在 color grading 上的 unknown unknowns，让我能写出更好的 prompt 吗？"

### 头脑风暴与原型

当我在一个充满 **unknown knowns** 的领域工作时——也就是那些"只有看到才知道怎么定义"的标准——我喜欢让 Claude 跟我一起做头脑风暴和打原型。

在原型阶段就把 unknown knowns 识别出来、说出来是非常有价值的，因为在实现阶段发现它们的代价相对高昂。一个特性或规格的小改动会让代码实现出现截然不同的路径，让 agent 撤销之前的改动也会更难。

比如，你可能只是想知道给某个 frame 加上一个按钮看起来什么样，而不必在后端搭一条路由，也不用在前端维护额外状态。

另一个例子是视觉设计。对我而言，这是一个很难讲清楚、但看到就知道想要什么的东西。在这些情况下，我会要求 Claude 给某个产物产出几种不同的设计方向。

我几乎在每一次编码会话开始时都会先做一个探索或头脑风暴阶段。这让我从"先有意图"出发来界定项目范围。Claude 经常能找出我本来会漏掉的、价值很高的方案——有时也会"只见树木不见森林"。头脑风暴能避免我把范围设定得过窄或过宽。

**示例 prompt：**

- "我想要一个数据看板，但我没有视觉品味，也不知道什么是可能的。给我做一个 HTML 页面，给我 4 种截然不同的设计方向，让我对着它们做出反应。"
- "在连任何后端之前，先做一个 HTML 文件，用假数据 mock 一下新的编辑器工具栏。我想先对着布局给出反馈，再动真正的应用。"
- "这里有个粗略的问题：用户在 onboarding 之后就流失了。在代码库里搜一下、头脑风暴出 10 个我们可以介入的地方，从最便宜到最有野心。我会告诉你哪几个有共鸣。"

### 访谈

做完足够的头脑风暴之后，我通常仍然会有未知。

这时我会让 Claude 来"采访"我，针对任何未知或模糊之处提问。让 Claude 采访时，试着把关于你问题的上下文喂给它，引导它的问题。

**示例 prompt：**

- "一次一个问题地采访我，所有有歧义的地方都问一遍。优先问那些我的回答会改变架构的问题。"

### 参考资料

有时候你没法详细描述你想要什么。比如你可能找不到合适的语言，或者它太复杂、表达起来需要很长时间。

这时最好的办法是给一份参考资料。你可以用图表、文档或图片，但**最最最好的参考资料是源代码**。

如果你有一个库用某种方式实现了某件事，或者你很喜欢的一个设计组件，只要把那个文件夹指给 Fable，告诉它要找什么——哪怕它是另一种语言。与截图相比，这能为 Claude 提供关于标记与结构上的更丰富细节。

**示例 prompt：**

- "vendor/rate-limiter 里的这个 Rust crate 实现了我想要的精确退避行为。读它，然后用同样的语义在我们的 TypeScript API 客户端里重新实现一遍。"

### 实施方案

当我觉得可以进入实现时，我倾向于让 Claude 整理一份实施方案给我评审。方案要聚焦在最可能变化的部分——例如数据模型、类型接口、UX 流程——这样能让 Claude 浮出我真正可能需要改动的部分。

**示例 prompt：**

- "用 HTML 写一份实施方案，但把'我最可能想调整的决策'放在最前面：数据模型变更、新的类型接口、任何面向用户的东西。机械性的重构埋在下面，这部分我相信你。"

## 实现中

### 实现笔记

当我满意计划之后，我会开一个新会话，把所有产物都塞进 prompt。这样 Claude 有了一个全新的上下文窗口，但又有你从规划阶段攒下来的全部信息。例如，我可以传一个 spec 文件和一个原型，让 agent 去实现。

但事实是，无论你做多少规划，总有潜伏的 unknown unknowns。Agent 可能在执行中发现，由于它撞到的某个代码里的边缘情况，它需要换一种做法。

我让 Claude Code 维护一份临时的 `implementation-notes.md`（或 `.html`）文件，记录它做的决策，以便我们在下一次尝试中学习。

**示例 prompt：**

- "维护一份 implementation-notes.md。如果你撞到到某个边缘情况、不得不偏离原计划，选择保守的方案，把它记到 'Deviations' 下，然后继续推进。"

## 实现后

### 推销与说明文档

把东西做出来最重要的一环，是获得认同与批准。在最终文档里搭好推销（pitch）和说明（explainer）产物有助于：

- 当评审者带着跟你一样的未知开始读时，加快他们理解的速度
- 当专家想看你是否已经考虑过那些他们本以为你会忽略的未知与常见失败点时，加快他们批准的速度

**示例 prompt：**

- "把原型、规格和实现笔记打包到一份单一文档里，我可以丢到 Slack 里求认同。把 demo GIF 放在最前面。"

### 自测题

经过一场很长的协作，Claude 可能完成的工作远超我所意识到的。光读 diff 只能给我一种"轻"层的理解，因为很多行为要依赖既有代码路径。

让 Claude 给我出题考我——并同时给我足够的上下文——能帮助我真正搞懂发生了什么。我必须完美答对这份测试，才会合并。

**示例 prompt：**

- "我要确保我完全理解这次改动里发生的一切。给我一份 HTML 报告，介绍这次改动——包括背景、直觉、做了什么等等——并在末尾附上一份关于这次改动的自测题，我必须答对。"

## 这一切如何串起来：Fable 的发布

[Fable 的发布视频](https://x.com/ClaudeDevs/status/2064399512664526853) 是端到端用 Claude Code 剪辑出来的。这对我是一个全新的领域，我绝对算不上专家。

所以我从"我已经知道什么"开始。我了解 Claude 能用代码编辑视频、做转写，但不确定它够不够准确。我请 Claude 给我讲讲 Whisper 之类的转写原理，以及我能不能用 ffmpeg 准确地把"嗯"、长停顿之类的东西切掉。

我想要 Claude 做出一个与我讲话节奏同步的 UI，但不确定能不能做到，于是让 Claude 用 Remotion 和一段转写做一个原型视频，看看能不能跑通。

最后，视频看起来有些暗淡。我知道这是调色的结果，但调色到底是什么，我并不真的清楚。我第一轮让 Claude 给我出了几个变体让我挑，但我意识到我对"调色做得好长什么样"完全没有概念。于是我改为让 Claude 教我关于调色的知识，让我发现自己的未知。

## 让地图与实地对齐

模型越强，正确的方法就越能让你达成更多。当一个长时任务结果不对时，往往意味着你需要花更多时间去定义未知，或者写一份能让"你和 Claude 一起穿过去"的实施方案。

每份 explainer、每次 brainstorm、每场访谈、每个原型、一份参考资料——这些都是"在修复变得昂贵之前发现你不知道的事"的廉价手段。

所以，下一次启动项目时，请让 Claude 帮你发现你的未知。

想了解与 Fable 这一代模型相关的"context"一侧，请参阅 [the new rules of context engineering](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)。
