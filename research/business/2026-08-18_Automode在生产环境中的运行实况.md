# Auto mode 在生产环境中的运行实况

*原文标题：Running auto mode in production*

> 原文链接：https://claude.com/blog/auto-mode-in-production

Nuro、Gusto 和 Garner Health 三家团队如何使用 auto mode 在生产规模下兼顾速度与安全。

[Auto mode 现已成为 Claude Code 的默认设置](http://claude.com/blog/auto-mode-default-in-claude-code)。它不再让你逐一批准智能体要执行的每条命令，而是由一个分类器评估每一项动作，拦截看起来可能有害的操作。

Auto mode 的设计化解了智能体编码中常见的取舍：**速度 vs. 安全性**。逐条审批让人参与其中，但当会话延长到几小时、并行翻倍时，这种监督反而成了瓶颈。完全跳过权限检查会更快——但这也是 prompt injection、范围漂移，以及偶尔被误删的生产资源得以蒙混过关的路径。

Auto mode 关闭了大部分这样的差距。在内部评测中，分类器捕获的危险动作比开发者手动点击权限提示时还多，并在第三方红队测试中保持了稳定的性能。由于会话被打断的次数更少，Claude 在两次中断之间的工作时间是以往默认设置下的 9 倍 —— 这是所有 Claude Code 使用量的整体数据。

为了观察 auto mode 在生产环境中的表现，我们采访了 Nuro、Gusto 和 Garner Health 三家团队，了解他们为何把 auto mode 当作日常工具，以及如何在生产环境中兼顾速度与安全。

### Nuro：驱动长时运行的自主智能体

Nuro 是一家开发通用 L4 级自动驾驶技术的"物理 AI"公司，于 2025 年末采用 Claude Code，到次年三月它已成为公司内部最受欢迎的智能体编码工具。

在 auto mode 发布之前，资深软件工程师 Kai Zhou 已经在内部搭起了一个临时替代方案：一个钩子，把每一项待执行的动作发给一个小模型，常规的 90% 自动批准，敏感操作则路由到 Slack 由人工复核。这个原型回应了一个真实的张力：工程师讨厌盯着审批提示看，但从公司安全与法务的角度看，完全跳过权限又过于危险、无法放行。auto mode 发布后，Kai 把这个内部项目搁置了。

如今，Kai 在所有自己写的代码上都用 auto mode。

> "我不想一直坐在那里点 '批准'，"Kai 说。"我用 auto mode 完成 100% 的编码工作。大多数时候，我会并行开三到四个 auto mode 会话，需要时再回去看一眼。"

唯一例外的是涉及其他团队的工作。例如当 Claude Code 代他审阅 Pull Request 时，Kai 会切回交互模式，逐条复核后再发出。

Auto mode 也并非毫无约束地运行。Nuro 大量依赖 [skills](https://agentskills.io/home)，工程师在配置中直接拒绝最危险的命令（例如递归删除）。分类器就在这些护栏之内做判断。

不过，auto mode 更大的解放在于：**能启动那些工程师下班后还会继续跑的工作**。具体而言，Kai 的团队用 auto mode 驱动长时运行的研究智能体，让它们围绕自动驾驶栈的评测指标"爬山"：这些任务自带清晰、可度量的信号，智能体可以独立地反复迭代。

一夜之间，智能体可以研究评测套件标记的假阴性、起草方案、跑实验，并基于结果不断迭代。这种方法可以推广到任何有清晰评测方式的任务——Nuro 另一个团队用它来缩减某个特定二进制的内存占用——因为指标本身就会告诉智能体是在变好还是变差。

> "前几天晚上 10 点我启动了一个智能体，它一直跑到凌晨 5 点——第二天早上给了我三个 PR，"Kai 说。"我觉得这相当惊艳。只有 auto mode 才能支撑这种工作负载。"

### Gusto：更快速、更安全地交付 PR

在领先的中小企业 SaaS 公司 Gusto，引入 auto mode 的初衷是一次主动的安全升级。

公司 AI Dev Tools 团队的 Martin Emde 此前眼睁睁看着权限疲劳拖慢了团队的节奏。auto mode 在不牺牲控制力与安全性的前提下给了他们同样的速度。自从在整个工程团队推广以来，整体的"权限负担"明显下降。

Martin 自去年十二月以来已启动 2,425 个 Claude Code 会话，auto mode 是他的日常工具。原本会在"文件夹访问审批"上卡住的跨仓库工作，现在可以一气呵成；原本需要守在旁边的无人值守任务（比如从 GitHub、Slack、Jira 汇总每日笔记）现在可以独立运行。Martin 团队自己的分析显示，自 2026 年 5 月中旬以来，约 10% 的会话记录里出现了 auto mode 的拦截——这证明分类器在做实事，又没有拖累合法任务。

> "Auto mode 在速度与控制之间给了我们一个更安全的平衡，"Martin 说。"我们得以移除反复出现的提示，在不牺牲安全的前提下提升效率。我们能看到 auto mode 在恰当的时机拦截，这让团队有底气加快节奏。"

Gusto AIT 云工程团队的 Chad Kunsman 从另一个方向得出了同样的结论。他的工作——端点调查、日志审计、连接器管理、跨多个 MCP 服务器的文档摄取——是以 20 分钟一段的短回合进行的，而不是通宵马拉松。他并不追求更长的运行；他想要的是"绕过权限"的那种放手节奏，又不必担心一个糟糕的 prompt 或 prompt injection 借机混入。

> "考虑到它对 prompt injection 的防护，以及它会核验你正在做的事是否真的与你的请求相符，它比'绕过权限'更靠谱，又比权限提示快得多，"Chad 说。

在分类器真的介入的少数几次里，Chad 表示它判断得很准。"它拦下我的时候，给出的解释是合理的。它正在偏离我最初的请求，所以它主动来确认一下。它一点也没有判错。"

对最敏感的工作，Chad 仍然会退出 auto mode。当会话已经"咬住"生产基础设施——Terraform、AWS、对线上 API 的直接 POST 调用——他会切到"接受编辑"模式，逐个手工核验工具调用。"你必须权衡节省的时间、它可能出错的地方、以及出错的代价有多严重，"他说。"说到底，你仍然要对发生的事负责。"

这种判断运作在更广的纵深防御体系之内：Gusto 把 MCP 流量通过一层带工具防护和 prompt 检查的可控代理路由出去，让智能体在 auto mode 介入之前就已经工作在严格受限的权限范围内。

### Garner Health：加速软件开发生命周期（SDLC）

医疗科技公司 Garner Health 在二月向全体 550 名员工、所有职能部门铺开了 Claude Code。Claude Code 接入了所有核心系统——包括 Salesforce、Zendesk、Snowflake——公司鼓励员工每周花大约两小时，把工作中最具重复性的部分自动化掉。

在 auto mode 出现之前，这个规模伴随着大量开销。Garner 平台工程经理 Evan Magnussen 把权限管理形容为"手工整理批准的命令清单、再眼睁睁看着管道命令被拒绝"这种乏味的循环。

如今，Evan 与他绝大多数同事在每个会话里都开 auto mode——从研究代码库，到通过 MCP 管理外部集成。

> "我们为整个工程组织搭建了一套标准化的软件开发生命周期，而它真正能够实现，正是因为有 auto mode，"Evan 说。"员工们把它看作一种如释重负：他们不再需要一连几个小时盯着自己的智能体。"

这套生命周期以一组标准化的 skills 插件形式运行。智能体接手任务后，先探索它能访问到的上下文，把上下文文件提交到代码仓库，再做 Evan 所说的"对抗性研究"（antagonistic research）来压力测试自己的假设，然后进入实现——只有在找不到自己需要的上下文时，它才会停下来找人。Evan 指出，那些偏重研究的阶段在 auto mode 出现之前根本是不可能的。

开箱即用的分类器几乎不需要调参。Evan 做的唯一一处调整和 Kai 在 Nuro 的做法一致：他配置 auto mode **不批准**那些会与他人通信的动作，比如发 Slack 消息或邮件。

> "我个人并不喜欢 Claude 在我跟别人沟通时擅自代表我行动，"他说。负责核心知识产权的团队——他们是对 auto mode 出现之前"跳过权限"最怀疑的——也学会了通过调整分类器的注入 prompt 来让自己的工作在更宽松或更严格的边界之间取得平衡。

对其他正在推广 auto mode 的企业，他的建议是：迎难而上，构建合适的控制机制，在确保安全部署的前提下赋能工程师。"如果我们说'大家都去搭自己的工作流，我们没有任何遥测'，那会非常危险，"Evan 说。"正因我们有遥测、正因我们搭的工作流相对标准，我们才更有底气。"
