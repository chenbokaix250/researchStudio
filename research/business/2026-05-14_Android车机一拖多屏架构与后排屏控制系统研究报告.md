# Android 车机一拖多屏架构与后排屏控制系统研究报告

## 一、背景

随着智能座舱（Cockpit Domain Controller）发展，现代车机已经从：

```
单 SoC + 单屏
```

演进为：

```
单 SoC + 多屏
```

甚至：

```
多 SoC + 多 Display Domain
```

典型屏幕包括：

- 仪表（Cluster）
- 中控 CID
- 副驾娱乐屏
- 后排娱乐屏（RSE）
- HUD
- 流媒体后视镜
- Side Mirror Display

在这种架构下：

**"显示内容控制"**

与

**"屏幕亮灭控制"**

逐渐成为两个完全不同的系统层级。

同时：

后排娱乐系统（Rear Seat Entertainment，RSE）开始出现：

- 遥控器
- 多用户
- 儿童锁
- 驾驶限制
- 权限隔离
- 视频策略
- Occupant Zone

等复杂业务。

因此：

**必须重新划分 Display 系统架构边界。**

---

## 二、核心问题

当前系统存在：

### 1. ACCMode 服务控制屏幕亮灭

例如：

- Display ON/OFF
- 背光
- Sleep/Wakeup

属于：

```
Power Lifecycle
```

---

### 2. 屏幕禁用功能

通过：

```
Overlay 遮挡
```

实现：

- 后排锁定
- 驾驶中禁用
- 家长控制
- OTA期间禁用

属于：

```
Display Business Policy
```

---

当前问题：

**是否应该将"遮挡禁用业务"放入 ACCMode？**

结论：

**不建议。**

因为：

```
Power Domain
≠
Display Business Domain
```

二者属于不同架构层级。

---

## 三、车机显示系统的层级划分

现代 Android Automotive 显示系统应拆分为：

```
+--------------------------------------------------+
|                Application Layer                 |
+--------------------------------------------------+
|           Display Business Policy Layer          |
+--------------------------------------------------+
|            Display Composition Layer             |
+--------------------------------------------------+
|               Display Power Layer                |
+--------------------------------------------------+
|                 Hardware Layer                   |
+--------------------------------------------------+
```

---

## 四、Display 内容控制架构

### 4.1 Android Multi-Display

Android Automotive 基于：

- DisplayManagerService
- WindowManagerService
- SurfaceFlinger

实现：

```
一个 Android
控制多个 Display
```

例如：

```
Display0 -> Cluster
Display1 -> CID
Display2 -> Rear Display
Display3 -> HUD
```

每个 Display：

- 独立 Window 栈
- 独立 Surface 组
- 独立输入焦点
- 独立渲染目标

---

### 4.2 内容渲染链路

Android 显示本质：

```
App
 -> Surface
 -> BufferQueue
 -> SurfaceFlinger
 -> Hardware Composer
 -> Display Pipeline
```

重点：

**每个 Display 独立合成。**

---

### 4.3 Display Routing

通过：

```java
ActivityOptions#setLaunchDisplayId()
```

实现：

```
指定 Activity 显示到哪个屏幕
```

例如：

```java
options.setLaunchDisplayId(2);
```

将 Activity 启动到后排屏。

---

## 五、Display 电源控制架构

### 5.1 电源控制与内容控制的区别

显示"黑屏"并不等于：

```
屏幕真正关闭
```

屏幕状态通常分为：

| 状态           | 内容            |
| ------------ | ------------- |
| 内容黑屏         | UI 黑色         |
| Overlay 遮挡   | 视觉遮挡          |
| 背光关闭         | Backlight OFF |
| Pipeline OFF | DSI/eDP 停止    |
| Panel OFF    | PMIC 断电       |

因此：

**Display Power 是独立系统。**

---

### 5.2 实际车机电源控制链路

现代车机：

```
Android
   |
Vehicle HAL
   |
MCU / Power Manager
   |
Display Power Controller
   |
Panel / Backlight / PMIC
```

Android：

通常只负责：

```
Logical Display State
```

真正：

- GPIO
- PWM
- Regulator
- Panel Enable

通常由：

- MCU
- Kernel Driver
- Vendor HAL

控制。

---

### 5.3 ACCMode 的职责边界

ACCMode 应只负责：

| 功能             | 是否属于 ACCMode |
| -------------- | ------------ |
| Display ON/OFF | YES          |
| 背光控制           | YES          |
| Suspend/Resume | YES          |
| Panel Power    | YES          |
| Overlay 遮挡     | NO           |
| 用户权限           | NO           |
| 后排锁定           | NO           |
| 遥控器            | NO           |

即：

**ACCMode = Display Power Lifecycle**

而不是：

**Display Business Controller**

---

## 六、Overlay 遮挡业务分析

### 6.1 遮挡本质

当前：

```
用一张图遮挡屏幕
```

本质属于：

**Display Access Restriction**

而不是：

**Display Power OFF**

即：

```
Display still ON
System still running
```

只是：

- 用户不可见
- 用户不可操作

---

### 6.2 Overlay 推荐实现

推荐：

**System Overlay Layer**

而不是：

```
全屏 Activity
```

推荐：

- SurfaceControl Overlay
- TYPE_DISPLAY_OVERLAY
- System Layer

优点：

| 优点          | 内容              |
| ----------- | --------------- |
| 切换快         | 无 Activity 切换   |
| 无闪屏         | Surface 级       |
| 不影响 Task 栈  | 不污染 Activity    |
| 支持多 Display | 独立控制            |
| 可统一管理       | Overlay Manager |

---

### 6.3 Input 必须同步控制

仅视觉遮挡：

```
不等于禁止交互
```

因此需要：

**Input Block**

例如：

- InputFilter
- InputDispatcher
- InputWindowHandle Disable

实现：

```
用户无法点击被遮挡内容
```

---

## 七、后排屏系统（Rear Screen System）分析

后排娱乐系统逐渐形成：

**独立 Display Domain**

典型功能：

| 功能            | 是否属于 Power |
| ------------- | ---------- |
| 遥控器           | NO         |
| 多用户           | NO         |
| 家长控制          | NO         |
| 后排锁定          | NO         |
| DRM           | NO         |
| 视频限制          | NO         |
| Occupant Zone | NO         |

因此：

**后排系统必须独立服务化。**

---

## 八、推荐架构：RearScreenService

建议引入：

**RearScreenService**

作为：

**Rear Display Domain Controller**

---

### 8.1 服务职责

```
+------------------------------------------------+
| RearScreenService                              |
|------------------------------------------------|
| Remote Input Manager                           |
| User Permission Manager                        |
| Rear Display Policy                            |
| Overlay/Mask Controller                        |
| Session Manager                                |
| Occupant State                                 |
+------------------------------------------------+
```

---

### 8.2 服务边界

RearScreenService：

只负责：

```
Display Business Policy
```

包括：

- Overlay
- Input Block
- 用户权限
- Occupant
- 遥控器
- Session

不负责：

- 背光
- PMIC
- Panel
- Suspend

---

## 十、推荐状态机设计

建议：

**状态机驱动**

### 10.2 Policy Event

例如：

```
Remote Input
```

## 十一、为什么必须解耦

如果：

```
ACCMode 同时控制：
- Power
- Overlay
- User
- Remote
- App
```

后果：

**ACCMode 服务会逐渐变成"超级上帝服务"**

最终：

- 状态机失控
- Resume 异常
- 黑屏难排查
- 多屏逻辑爆炸
- 无法扩展

这是车机项目中的典型失败架构。

## 十三、推荐最佳实践

### 13.1 ACCMode

仅负责：

```
Display Power Lifecycle
```

包括：

- ON/OFF
- Suspend
- Wakeup
- Backlight

---

### 13.2 RearScreenService

负责：

```
Display Business Policy
```

包括：

- 遮挡
- 锁定
- 权限
- 遥控器
- 输入限制

---

### 13.3 Overlay

采用：

```
SurfaceControl System Overlay
```

---

### 13.4 Input

必须同步：

```
Input Blocking
```

---

### 13.5 状态机

采用：

```
Policy Engine + State Machine
```

而不是：

```
if/else
```

---

## 十四、最终结论

本次研究核心结论：

---

### 1. Display 内容控制 与 电源控制是两个层级

```
Display Content
≠
Display Power
```

---

### 2. Overlay 遮挡属于业务策略

而不是：

```
Power OFF
```

---

### 3. ACCMode 不应承载后排业务逻辑

ACCMode 应只负责：

```
Display Lifecycle
```

---

### 4. 后排系统应独立服务化

推荐：

**RearScreenService**

作为：

**Rear Display Domain Controller**

---

### 5. 推荐采用"Power Domain + Business Domain"解耦架构

即：

```
ACCMode
    -> Power

RearScreenService
    -> Business Policy
```

---

### 6. 未来方向

系统最终会演化为：

**Occupant-aware Multi-Display Architecture**

即：

```
面向乘员
而不是
面向屏幕
```

的智能座舱架构。
