# Anthropic 如何守护它的 AI 原生软件开发生命周期

*原文标题：How Anthropic secures its AI-native software development lifecycle*

> 原文链接：https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle

Anthropic 副 CISO Jason Clinton 详细介绍了安全工程团队如何在"AI 编写的代码占总合并代码 80%"的 SDLC 中守护安全。

在 Anthropic，代码量与部署节奏呈指数级增长。我们的软件工程师平均每个季度提交的代码量，是 2021–2025 年的 8 倍。

我们的评审、监控与其他安全流程必须与这种加速齐头并进。否则就会变成瓶颈的配方（[Amdahl's Law](https://en.wikipedia.org/wiki/Amdahl%27s_law)）。

我们的软件开发流程本身也发生了剧变。Claude 已经从编码助手演变为主要的创造者与评审者。[Claude 如今负责编写](https://www.anthropic.com/institute/recursive-self-improvement) 我们代码库中合并代码的大约 80%。

超过一半的代码是由我们内部版的 [Claude Tag](https://www.anthropic.com/news/introducing-claude-tag) 合并的，而人类工程师专注于指导、设定意图，并拥有最终的批准权。

这意味着我们的安全团队必须保卫一个快速扩张的攻击面，并加固一个"心脏"是"非确定性、持续演进的 agent"的生命周期。本文会介绍守护 SDLC 的策略。

*（本文应与我们近期发布的 [*Zero Trust for Agents*](https://claude.com/blog/zero-trust-for-ai-agents) 框架配合阅读；本文中所有内容都用到了该框架中的安全设计思想。）*

我们要主动防御的威胁是具体的：一个被攻陷或被 prompt-injected 的 agent 引入恶意改动；agent 作为"可信输入"而吃下的供应链与依赖投毒；以及那些更"传统"的应用漏洞——只是现在它们的到达量更高了。下面的每一项控制都至少对应其中之一。

我们部署了几条总体策略，在不显著拖慢研发节奏的前提下完成这件事，包括：

- 把安全左移，完全融入代码开发阶段；
- 用强制的访问与身份边界来收窄爆炸半径；
- 在生产前与生产后，把自动化的确定性评审与智能体评审组合起来；
- 在杠杆最高的位置把人工引入循环。

本文将介绍我们在 SDLC 各具体阶段落地的安全流程，以及它们背后的核心原则。这些原则更具持久性，因为安全团队必须随着模型能力的演进不断重审、并常常需要重做他们的流程。

## **不断演进的软件开发生命周期**

我们的研发团队已经 [详细介绍了](https://claude.com/blog/running-an-ai-native-engineering-org) 他们对 SDLC 的改造，所以这里只做一段简短铺垫，再深入到各阶段。

总体而言，我们的 SDLC 是被压缩的。它更多由原型与内部采用（dogfooding）驱动，而不是冗长的规划周期。创意来自组织的各个角落，传统角色（前端、后端、设计）之间的边界变得模糊。评审与审批仍然有"人在回路"，但它们本身也由智能体循环驱动。

虽然每个阶段都被 Claude Code 与 Claude Tag 从根本上改造并加速了，但各阶段的名称与目的对一个来自更传统组织的开发者来说并不会显得陌生。这些天然的关卡，也被我们作为 AI 原生 SDLC 安全流程的一部分来使用。

## **规划（Plan）**

我们的第一批安全自动化之一，是一个由 Claude Opus 驱动的 PSR（项目安全评审）Web 应用。它读取一份项目设计文档，并对照 [MITRE ATT&CK 框架](https://attack.mitre.org/) 进行分析，识别潜在漏洞与建议缓解措施。

我们后来通过把它接上一个内部知识索引而显著增强了这个系统——该索引提供了横跨全公司策略、过往决策和相关系统的更深上下文。

![]()*Anthropic 内部自动化 PSR 的流程。*

这让我们对潜在风险有了更好的把握，也补全了 PSR 文档里漏掉的信息。这一处实现就为 AppSec 团队省下了大部分时间。一旦我们建立起" Claude" 评估风险的准确度，我们就允许团队自行批准自己的项目，前提是 Claude 认为该次上线风险足够低。

这里我们就能看到 AI 原生 SDLC 的第一处关键适配。PSR 原本是为了在漫长且昂贵的编码流程之前就抓住安全问题。在这个阶段抓到一个问题，可以省下几个月的返工。

如今，多个主要功能的原型可以在几小时内被创建出来，这让"细致的架构评审"不再是那么关键的关卡。把我们的 PSR 应用与知识索引相连，捕获到的是原本可能漏掉、却不该制造不必要减速的上下文。把它做成一个 Claude Code skill，则让 Claude 能进一步"扇出"到上下文所在的任何地方，捕获额外信息。

**持久原则：** 把安全 agent 接到组织级上下文上。随着规划周期的压缩，把它们带到上下文已经在的地方——聊天线程、过往评审、代码库——比"硬要在可能已经不再需要这些文档的阶段，逼人写出详尽文档"更有效。无论如何，agent 都需要代码之外的上下文。

## **编码（Code）**

在 AI 原生工程组织里，安全从业者拥有了一个新杠杆：他们可以直接塑造"代码是如何被创造的"，从源头就帮助阻止漏洞。

过去，团队会观察反复出现的漏洞，并据此编写"安全编码指南"去应对，但这些指南难以强制执行，也很少被标准化。

在 Anthropic，这些指南被编码进 `CLAUDE.md` 文件，并引用组织级的 skills——这样代码在生成出来的那一刻就遵循了这些最佳实践。这是一个闭环的一部分：一旦 agent 发现了一类 bug，相应文件会被更新，以防未来代码再踩同样的坑。

![]()

当然，这并不意味着所有代码出来就完美。我们的团队一开始就有一份 `CLAUDE.md`，要求 agent 在开 PR 前最后一步跑 `/security-review`（[在 Claude Code 中自动做安全评审](https://support.claude.com/en/articles/11932705-automated-security-reviews-in-claude-code)）。这个已 GA 的命令是团队内部评审流程的产品化版本，它会去找"潜在可被攻击者控制的输入流入点"、扫描可疑链接，然后核验它自己的发现。

如今，这些评审是在 Claude 生成代码的过程中完成的。一旦安装 [security guidance plugin](https://code.claude.com/docs/en/security-guidance)，Claude 就会在生成代码的过程中同时审视对话与代码。它会在同一个会话里给出安全改进建议、修复常见漏洞。

在 PR 阶段的其他"轻推"会引导内部、非技术团队把他们的应用托管到我们的低代码应用托管平台，从而避免长期以来困扰安全团队的"影子 IT"。

我们的一些客户选择把 `/security-review` 配上一个 PreToolUse hook，让这一环节变成更硬的关卡。这也很有效，但我们的团队选择把"硬代码评审"这道关卡放在测试/CI 阶段。

除了塑造与评审代码之外，**收窄爆炸半径**也是我们在这一阶段主要的关切之一。我们的做法是：在身份上设置硬边界（更多内容见 Monitor 一节），并让开发者在一台虚拟机里写代码。

把写代码搬到远程 VM 上是一次相对无痛的迁移，相比仅依赖笔记本，给了我们更高的控制力与可见性。这些 VM 上的 agent 流量走的是"出口白名单"。

这些严格的出口控制在 agent 读取不可信输入时尤其重要——因为不可信输入里可能藏着 prompt injection 载荷。被注入的指令无法触达互联网上的任意目标：数据外泄路径被限制在一小撮被监控的服务里。

这里又能看到一处对 AI 原生 SDLC 的清晰适配。远程写代码过去主要是为了保护 IP，而今天我们看到更多成熟的 AI 编码团队采用这类环境，把它当作"收住 agent"的手段。

**持久原则：** 在 AI 原生工程组织里"左移"意味着闭合"漏洞发现"与"更新指令以定制 Claude 如何生成代码"之间的回路。同时按需用硬边界收窄爆炸半径（最小代理原则）与 agent 能访问的范围。

## **测试（CI）**

以我的经验，在 AI 原生转型如火如荼的工程团队里，测试或 CI 阶段会最快成为最痛的瓶颈。在 Anthropic，一旦大多数开发者开始用上智能体编码工具、并且同时跑多个 agent，很快就会清楚地看到：**团队只能以"人评审代码的速度"为限前进**。

说清楚一点：人的问责制仍然是流程的中心。我们做的是用"自动化智能体评审 + 确定性评审"的组合来加速评审过程，而把人工评审留给受监管或真正关键的代码。

历史上，人工代码评审被奉为标准，但 [经验性证据](https://link.springer.com/chapter/10.1007/978-3-642-36563-8_14) 表明它并不完美。安全 bug 在全世界各类软件里照常合入。我们的评审流程能评审更多代码、抓到特别复杂的问题，从而帮助降低这些风险。

获得"实质评审评论"的 PR 占比 [从 16% 增长到了 54%](https://claude.com/blog/code-review)——我们之所以对这些发现越来越有信心，是因为我们要求 agent 必须写出"它发现的问题确实成立"的证明。我们也判断，[过去 claude.ai 事故中大约三分之一的 bug 都会被我们现在实现的自动化流程抓到](https://www.anthropic.com/institute/recursive-self-improvement)。

做出同样发现的并非只有我们一家。[Intercom 公开过](https://www.intercom.com/blog/ai-is-approving-our-pull-requests-heres-how-we-made-it-safe/) 它们自动批准了 19% 的 PR，部署量翻倍、由"破坏性改动"引起的停机时间下降 35%。CircleCI 也得到了类似的结论——他们基于 Claude 打造的 Chunk（一个自主 agent，用来解决 CI/CD 维护问题）会在人类介入之前 [自行验证它的修复](https://claude.com/customers/circleci)。这套方法让 agent 任务转化为完成 PR 的比率翻了一倍。

在 Anthropic，一个 PR 一被开启，多个 agent 就会自动评审它。每个评审 agent 都按一个特定的、范围很窄的焦点来设计与构造，并通过 RAG 调取关于过往事故的额外上下文与记忆。

这比"一个巨大的 prompt 或超级安全 agent"要有效得多，理由有几条：

- 它们不共享偏见与盲区
- 如果其中一个被攻陷或出错，其他评审者可以发现
- 不会把精力摊得太薄、覆盖多个领域

说清楚：agent 并不是未经审核就把代码合入生产。我们按风险对代码库分层，并对哪些部分做自动化做出审慎决策。整个代码库都有严格的人工审批流程。

对于由 Claude 评审与合并的代码，人的问责制仍然是核心。**每一次审批都连同其背后的信号与推理一起被记录**，并对其中按风险加权抽样的部分进行人工复核。另一轮测试聚焦于不变量，比如"A 用户永远不能读 B 用户的"数据，并在触发时引入额外的人工复核。我们还把 agent 扫描与 SAST 工具组合使用，后者直接评论在 PR 上。

大多数扫描方案——无论是 agentic 还是确定性的——都是"按消费量"计费的。代码吞吐越高，成本越高，团队需要决定对他们来说合适的覆盖率水平。

我们接受这里的成本会随代码速度一起增长，但同时预计单位成本会下降。今天的模型在编码上已经比几年前的任何模型都强，我们预计这种趋势会持续。

**持久原则：** 自动化评审是一种不同类型的风险，要用不同的方式去控制——通过多道关卡、彼此独立上下文窗口的多个 agent。**人仍然留在回路里**，但他可能位于生命周期中的不同位置，这取决于代码库的性质。

## **部署（CD）**

Anthropic 维护着一套稳健的预发环境，会执行常见的安全最佳实践，例如对重大上线做外部渗透测试，并定期做 DAST 扫描，去抓静态扫描遗漏或看不到的逻辑 bug。

与其他 SDLC 阶段一样，AI 给安全团队既带来了新挑战，也带来了新方案。一方面，能走到这一阶段的漏洞变少了。另一方面，能活到这一阶段的漏洞，往往是最微妙、最难抓的那一批。

再加上更大的代码量被以更频繁的节奏推出，周期性的动态测试看起来也没那么"动态"了。

好消息是，AI 模型在跨组件、多步骤的推理上更强了，而这正是抓到更复杂漏洞所需要的。例如，二月份我们披露 Claude 发现并协助修复了 [500 多个高危 OSS 漏洞](https://www.anthropic.com/research/zero-days)。

在 Anthropic，我们正在预发环境里落地持续、由 AI 驱动的 DAST 扫描。它们瞄准的是系统级的漏洞——两个或或多个服务之间的假设出错。市面上已有若干厂商提供这些能力。

**持久原则：** 动态测试应当匹配部署节奏。

## **监控（Monitor）**

任何一个合格的安全团队都知道：代码推到生产之后，工作并没结束。我们可以假设任何漏洞都会被越来越老练的攻击者迅速发现。

我们的安全团队在此部署了一些常规做法，例如 [公开的漏洞悬赏计划](https://hackerone.com/anthropic)、红队模拟攻击，以及对我们的依赖、密钥、供应链、云态势与容器定期扫描。

Claude 在其中扮演着重要角色，但这里我们重点谈谈由 AI 原生 SDLC 带来的、更大体量的监控动作变化：**告警 triage** 与 **代码迁移**。

在 Anthropic，告警一响起，Claude 就开始：

- 翻查生产日志
- 追根因
- 写事故复盘；以及在某些情况下
- 写出修复 bug 的代码改动

这位 agent 唯一不能做的事，是自动部署修复。它是一个单一目的的系统账号 agent，**只有三项权限**：可以写新文档、可以在公司频道里发言、可以读生产日志。

修复要么来自另一个独立的"agent + 人工评审"系统。原因回到身份、权限与硬边界的管理上：把代码推进生产时，必须收窄爆炸半径。**把 agent 分开至关重要，因为它们彼此（一或多对）会形成制约**。

![]()

这也是给 CISO 们的一个重要教训——也是我曾经吃过的亏。当设定一个 agent 的硬边界时，你必须把"它对其他 agent 的访问"也考虑进来。

一次模型升级之后，事件响应 agent 主动通过 Slack 联系了另一个 Claude 实例。它请那个能写代码的 agent 推送这次修复。**这件事在设计好的人工评审关卡被拦截住了**，但这次经历教会我们：要把边界画在"访问与动作"上，而不是画在"模型的指令"或"我们以为模型能做到什么"上。如今在 Anthropic，agent 之间通过 Slack 沟通已是常态，我们会花相当心思去设计 [agent 身份模型](https://claude.com/blog/agent-identity-access-model)。

第二项主要变化，是我们的团队如何处理迁移。每个安全工程团队都经历过那样的时刻——他们意识到，必须做一次代码迁移才能修复公司运营中某个系统性问题。过去，CISO 得开始四处奔走、向各部门"申请"未来几个季度各占一小撮的工程资源。

迁移的经济成本与跨公司协调成本双双降了下来。Claude 能在几天内 [自动化完成动辄数万行代码的迁移](https://claude.com/blog/ai-code-migration)。

**持久原则：** 给每个 agent 一个"单一目的"的身份，权限严格限定在它的工作所需。**如果你允许 agent 之间协作，让它们走与人相同的沟通渠道。**

## **治理（Governance）**

我们自动化了许多安全流程，但人依然是守护 SDLC 安全不可或缺的一部分。不过，我们关注的重点已经从"评审代码与 bug 报告"转向了 Claude Tag、各类 loop 和仪表盘。

这凸显了强治理的意义。当某个 skill 过时了、某类发现的 bug 没回流到 `CLAUDE.md`、或某个 agent 的决定没被抽样——整个体系就会就退化。我们通过以下做法避免这种情况：

- **按风险对代码库分层**，然后基于这个层级做自动评审。
- **对新 AI 评审员采用"影子模式"**。新 agent 在获得信任之前只能发评论、待人批准。我们的团队还会"红队"它们，尝试插入恶意改动。
- **对所有自动化批准进行抽样**。
- **盯好生命体征**。我们维护并密切观察一个仪表盘，它汇总了每个安全流程与工作流的关键指标。
- **把每一个 agent 动作都送进 SIEM**。每一次自动化批准、工具调用与 agent 间消息，连同它用到的信号一起被记录、落地到我们的 SIEM，让每一项决定都可追溯、可审计。我们把这些数据用起来，把这些 agent 当作一类新的内部威胁来对待——一旦它们的行为偏离预期，就会拉响告警。

**持久原则：** 安全工程师的工作，从"盯 bug"演变为"盯 loop"。

*关于这些控制背后的评估框架，请见 [CISO's guide to agentic AI](https://claude.com/blog/ciso-guide-to-agentic-ai)。*

## **让 AI SDLC 在模型演进中保持安全**

再怎么强调 SDLC 演进的快速、以及让它变坚固的方法的演进，都不为过。模型能力每个月都在前进，既带来新挑战，也带来新方案。

今天"不太能用"或"经济上不划算"的事，很快就会变得可行。你团队应该问的正确问题不是"我们能不能负担得起扫一切？"而是"**如果扫描几乎免费，我们会跑什么？**"为那个未来做规划。
