# 榨干 Claude Code 会话的每一滴价值

*原文标题：Maximizing the value of your Claude Code sessions*

> 原文链接：https://claude.com/blog/maximizing-the-value-of-your-claude-code-sessions

*如何运行高效率的会话，让每一个 token 都物有所值。*

## TL;DR

- **在不同任务之间跑 `/clear` 。** 这能防止之前不相关的上下文被反复发回模型，从而降低 token 用量。
- **在开始前就设好模型和 effort level 。** 会话中途切换任一项都会打掉你的 prompt 缓存，进而推高 token 成本。
- **用 @-mention 文件，而不是光写文件名。** 文件会直接附在你的消息里，省去一次 Read 调用；也不用让 Claude 自己去找。
- **给噪声大的命令加静默标志，或者丢到 subagent 里跑。** 命令的输出和文件一样会被加进对话，并停留到会话结束。
- **在新会话里跑一次 `/context` 。** 它会显示哪些东西已加载（`CLAUDE.md`、MCP 工具定义），方便你裁掉一切不必要的部分。
- **在你离开键盘前跑一次 `/compact` 。** prompt 缓存在一小时后过期，趁还在缓存里总结一段对话要便宜得多。

## 最大化价值

直到最近，你用来写代码的工具还是"一口价"（甚至免费）。你的编辑器在"你这一下午修一个测试"还是"修五十个测试"之间收费不变，所以单个任务本身并没有"自己的价格"。

但用上 Claude Code 这类智能体编码工具之后，价格就出现了。同一个完成的任务，因为你的使用方式不同，花费也可能不同。

在一次会话里，Claude 读了那个测试与它对应的文件，做了修改，几回合就搞定。在另一次会话里，它先在仓库里 grep 了一番，又读了十几个文件才走到同一处，而这几轮里每一轮都把"自打今早以来读到对话里的所有东西"一并捎带进去。

![]()

修的是同一个东西，但你花了不同数量的 token，而模型在这整个过程里还不得不去想它根本不需要的十个文件。

"高效使用 token"并不意味着整体上少用一些，而是要确保你用的那些，真的都花在你真正要求的事上。

那么我们先看看**什么决定了单个 token 的价格**，再看**什么决定了一次会话要发多少 token**，顺路讲讲这对"怎么跑一次会话"意味着什么。

## **什么决定了一个 token 的价格**

你是按 token 计费的，但你真正买的是"推理"——GPU（或 TPU，或模型恰巧跑在什么上面）对你那些 token 跑一遍模型所花的时间。

三件事决定了一个 token 要花多少时间：你跑的是哪个模型、它是输入 token（进去）还是输出 token（出来）、以及它是否走了缓存。

### 模型

更大的模型无论对输入 token 还是输出 token 都会做更多工作。哪个模型更适合哪种工作，本身是一个独立的话题，我们在 [*Choosing a Claude model and effort level in Claude Code*](https://claude.com/blog/claude-model-and-effort-level-in-claude-code) 里专门讲过。

对本文，你只需要知道：下文要谈的一切都会被"模型价格"乘起来——当问题真的很难或很模糊时用大模型，常规活儿用小模型。

![]()*曲线仅作示意，不代表真实基准数据。*

### 输入与输出 token

一个请求在 GPU 上分两个阶段走，定价不同。

第一阶段是 **prefill**，模型读取你的请求和上下文：系统提示、`CLAUDE.md`、你的消息，以及从那以后加进对话的所有东西（Claude 读过的文件、它跑过的命令输出）。这些是你的输入 token。

第二阶段是 **decode**，它生成输出 token：它的思考、调用的工具、你看到的文字。这一步一次只产出一个 token；一段 200 token 的回复，就是把模型连续跑 200 次。**每个 token 的 decode 让 GPU 忙得更久**，所以输出价格大约是输入的 5 倍。

![]()

一次会话里大量输出 token 是思考 token，而模型在每轮"想多少"由 effort level 控制。和模型一样，你用 `/effort` 选定的级别会作为默认被记到下一次会话。

**小贴士：** 在一个新会话里跑一次 `/model` 和 `/effort`，看看你到底跑的是什么。它俩都会记住你上次的设定——你希望这个选择是有意为之的。

**小贴士：** 如果你已经知道这一会话是体力活，那 `MAX_THINKING_TOKENS=0` claude 可以关掉本次会话的思考（在 Fable 5 上无效），这是比 `/effort` low 更下一档的开关。

### Prompt 缓存

如果一条请求的开头一段 token 与服务器刚处理过的一条请求完全一致，那么这段共享开头得到的中间状态也是一样的，所以服务器可以直接把上次留下的状态留着，只 prefill 之后新增的部分。这叫 prompt 缓存。

从缓存里读取按输入价格的 0.1x 计费，因为服务器只是加载状态、不再计算。把 token 写进缓存比普通输入稍贵，最高可达 2x，因为服务器之后还要保留这份状态。但写入每个 token 只发生一次，0.1x 的读取却会在之后的每一轮重复。

Claude Code 在每次请求时都会管理 prompt 缓存，没什么需要打开的。但它可以被打掉，所以知道怎么避免成本骤升很重要。

假设我们输入"修复 `utils.test.ts` 里那个失败的测试"。Claude Code 会这么发出请求：

- Claude Code 把第一条请求拼起来：系统提示（包含工具定义）、你的 `CLAUDE.md`、你的消息，然后发出去（输入 token）。此时缓存是空的，所以所有内容都被 prefill 并写入缓存。
- 模型不读测试就没法修，所以它先思考一下，然后回一个 Read 调用读 `utils.test.ts`（输出 token）。Claude Code 读了这个文件，把它追加到对话里，再把整段发出去（输入 token）。这一次，请求 1 的所有内容都以十分之一的价格从缓存读回，唯一按全价 prefill 的只有新增的部分：Read 调用与文件本身。
- 现在模型想要被测文件（输出）。又一次 Read，又一次追加，一切再发一遍：请求 1 与请求 2 走缓存，第二个文件按全价（输入）。
- 模型回了一个 Edit（输出）。Claude Code 把它应用、把结果追加进去、再全部发一遍：Edit 与结果是新增的，前面都是缓存读（输入）。
- 模型跑 `npm test`（输出）。Claude Code 把测试输出追加进来、再全部发一遍：测试输出是唯一新增的部分（输入）。
- 测试通过，模型回了一段简短的总结（输出）。没有工具调用意味着没什么可追加，也就没有请求 6，对话结束。

总共五条请求，对应一次小修。每一轮都包含到那时为止的整段对话。一回合典型是不对称的：几万 token 进去，几百 token 出来。但**只有这一轮里新增的部分才按全价 prefill**。

这就是一整轮的全部账单：历史的缓存读、新增部分的全价输入、回复的输出价。

这一套在订阅上同样适用。你不会直接看到这些价格，但消耗你额度的，正是同样的请求。

缓存必须从请求最开头起完全匹配，而请求总是按相同顺序发出：工具定义 → 系统提示 → 对话（`CLAUDE.md` 顶在最前面）。

如果这段前缀有任何变化，前缀之后的全部都要重新 prefill。把工具结果追加到对话末尾是最理想的情形，因为它后面没有内容。会"把缓存整段打掉"的是那些改变请求更靠前部分、或者改变缓存键值的东西：

- **`/model`**：每个模型有各自的缓存，所以下一轮整段对话又会被按全价 prefill。（这包括 opusplan——它在你进出 plan mode 时都会切换模型。）
- **`/effort:`**：effort level 也是缓存键的一部分，情形一样。这也是 `/model` 和 `/effort` 在会话中切换时都会让你确认的原因。
- **Fast mode**：同样是键的一部分，重新 prefill 会按 fast mode 价计费。所以如果你要开，**在会话一开始就开**。（关掉的话，缓存层面是免费的。）
- **`/compact`**：对话被一段更短的版本替换，里面的内容都不再匹配（前面的系统提示会保留）。写总结本身在旧对话还在缓存里时很便宜，所以"长休息前"做比"长休息后"做便宜得多。
- **时间**：每一轮都会重置计时器，但缓存会在订阅上一小时后、API key 上五分钟后过期（`ENABLE_PROMPT_CACHING_1H=1` 可以把它延长到一小时）。比这更久才回来，下一轮会重新 prefill 整段对话。恢复一个老会话几乎也总是这样：那时缓存通常已经没了，系统提示在启动时也得重建。

这并不等于说永远别换模型或 effort。它只是说明有"便宜的时刻"（会话开始或刚做完 `/clear` 之后）也有"贵的时刻"（长会话进行中）。

**小贴士：** 如果最后几轮去到了一个你不想要保留的地方，用 `/rewind` 回到它们之前，而不是跑 `/compact`。Rewind 只是把那些轮从末尾剪掉，前面所有内容仍然在缓存里，不花钱。Compact 重写整段对话，总会有成本。

## **什么决定了一次会话发多少 token**

要明白的最关键一点是：**没有什么 token 只发一次**。一切进了对话的东西——Claude 读过的文件、它跑过的命令输出——在之后的每一轮里都会再发一遍，直到会话结束。

它们走了缓存，所以每次重发都很便宜，但"便宜"不是"免费"，并且它也在占用模型每一轮都要绕着思考的上下文空间。

这基本上就是一次会话的全部成本模型：上下文里塞了多少 token、它们会停留多少轮、以及你同时跑着多少个上下文。

### **什么会进入上下文**

有些东西在你打字之前就已经在上下文里了：工具定义、系统提示、`CLAUDE.md`，以及所有启动时加载的东西。

**小贴士：** 在一个新会话里跑 `/context`，看你还没敲任何东西之前上下文里已经装了啥。把 `CLAUDE.md` 限定为具体指令，把工作流相关的指令挪到 skills 里——它们只在被用时才加载。如果这会话用不到某个 MCP server，用 `/mcp` 关掉它。

会话中几乎所有新增的东西都是**工具结果**：Claude 读的文件、它跑的命令的输出。

Claude 读多少，主要取决于它得自己摸索多少。你如果说"测试挂了"，它得先去搞清楚是哪个测试：几次 grep、开几个文件看哪个相关，而这一通结果会在远比你需要它们的时间更长的时段里停留在上下文里。

"修复 `utils.test.ts` 里那个失败的测试" 跳过了搜索环节，只花一次 Read 调用；"修复 `@utils.test.ts` 里那个失败的测试" 甚至连 Read 调用都省了。

![]()

**小贴士：** 当你指代文件时，用 @-mention，而不是手敲路径。Claude Code 会把文件直接附在你的消息里、抢在任何请求发出之前，所以它就出现在第一条请求里，也省了一次 Read 调用。文件本身在上下文里占的体积不变，所以你每次会话只 @ 一次就够——它会一直留在那儿，之后再 @-mention 通常会把第二份副本也附上。

另一项会塞满上下文的，是 Claude 跑过的命令输出。每次它跑你的测试、build、或 git log，打印出来的东西就会像一份它读过的文件那样被追加到对话里，并停留同样多轮。

真正巨大的输出其实没事：超过 30,000 个字符后，Claude Code 会把输出写入一个文件，只在对话里留一小段预览和路径（想改的话用 `BASH_MAX_OUTPUT_LENGTH`）。

问题出在 30,000 以下。一个测试运行器逐行打印 400 条通过的测试——这条没超限，但 400 行从此就成了剩下每一轮对话的一部分。

Claude 自己经常会用 flags 或 tail 帮你处理这事；如果你不愿把这事完全交给 Claude，文档里有一个小 hook 可以在命令跑之前改写它们，只把真正重要的几行带回来。

**小贴士：** 把你一天到晚要跑的那两三条命令放进 `CLAUDE.md`，带上静默标志，就像你自己手敲那样（例如"用 `npx vitest run <file> --reporter=dot` 跑单个测试文件"）。这是个小改动，但能给之后的每次会话省下一轮对话和几百行输出。

### 它会停留多少轮

一次很长的会话比把同样工作分散到几次短会话贵，而且贵得超出你的想象，因为第 40 轮还要把前 39 轮再读一遍。你希望会话里的上下文又短又贴题，所以不要把一个任务的上下文带去下一个：新任务开始时 `/clear`，同一任务前面部分搞完时 `/compact`。

![]()

**小贴士：** 如果你以后还会回到这个会话，先 `/rename` 再 `/clear`。`/compact` 时告诉它要保留什么；如果总是一样，也可以放一段"Compact instructions"到 `CLAUDE.md` 里。如果你在用 1M 上下文模型但想要 auto-compact 这张"安全网"回到原来的位置，`/autocompact 200k` 可以设回去（需要 Claude Code v2.1.221+）。

也要留意你没在打字时发生的回合。`/loop` 在你设置它的会话里也算一整回合，每一次都拖着一整段对话；而如果自上一轮起已经超过一小时，那还是额外的 cache miss。在另一个终端里开一个新会话，从那里跑 loop。

### Subagents

把某件事从你的上下文里挪出去的另一种方式，是让它在另一个上下文里发生——这就是 subagents 的用途。一个 subagent 拥有自己的上下文窗口、自己的系统提示、自己的工具，以及你的 `CLAUDE.md`，但没有你那整段对话。它跑自己的回合，唯一回到主会话的是它的答复。其他一切在它结束后就被丢弃。

"没有你那整段对话"的代价是 subagent 有时不得不重读主会话已经读过的内容，并且要为它自己的回合付费。对小任务来说这就是纯开销。

它开始划算的时刻，是某个任务会产生一大堆你不需要保留的输出，比如翻一份日志。Claude 自己在这种场景下经常主动召一个 subagent；如果它没召，你也可以直接要一个（"用 subagent 翻这份日志"）。但请记住：**主会话只能拿到 subagent 主动汇报的内容**。

![]()

**小贴士：** 如果你反复把某个噪声任务交出去，给它一个专属的 subagent 定义，写明 `model: haiku`（或 sonnet）。否则它会跑在你主会话所用的那个模型上。

## 优先看哪里

上面这些里，有四件事值得盯着，按大致成本从高到低排列：

![]()

1. **同一个会话里跑了多久。** 长会话拖得越久，每一轮重复算的 token 越多。用 `/clear` 切分任务，必要时 `/compact`。
2. **什么时候切换模型或 effort。** 一旦会话跑起来再换，prompt 缓存就被打掉了。在新会话或刚 `/clear` 之后换。
3. **进了上下文的内容。** 命令输出、未 @-mention 的文件、临时调试日志——它们会跟着你走完整个会话。给噪声命令加静默标志、用 `@` 提早附文件、必要时把任务丢给 subagent。
4. **`CLAUDE.md` 的精简程度。** 它在每条请求的前缀里。把它限定为真正普适的指令，把工作流相关的内容挪到 skills 里。
