# 在 Claude Code 中选择模型与 effort level

*原文标题：Choosing a Claude model and effort level in Claude Code*

> 原文链接：https://claude.com/blog/claude-model-and-effort-level-in-claude-code

**核心要点：**

- Claude 模型选择决定的是一组固定的权重，也就是模型整体的能力区间。模型可以通过上下文或引导来影响，但其基础的知识库和能力是固定的。
- Effort level 不仅仅是"思考时间"。它控制的是 Claude 在你的请求上整体投入多少工作，包括读取的文件数、调用的工具数、以及在回话前会推进多少步。
- 把小模型留给常规任务，把大模型留给更复杂或更模糊的任务。优先使用每个模型的默认 effort level，再按工作类型做整体性的偏好调整，而不是逐任务调。
- 如果 Claude 掌握了所有相关上下文、显然已经尽力，却还是答错了——这是该换更强模型的信号。如果 Claude 是因为漏读文件、没跑测试、或者中途放弃重构才出错——那是该升 effort level 的信号。

## **Claude Code 的 effort level 与模型选择**

Claude Code 提供了两个看起来"会让回答更好"的设置：模型设置和 effort level。你可能认为 Claude Fable 5 这样的大模型会比 Claude Sonnet 更聪明，更高的 effort level 意味着 Claude 在回答前会思考得更久。

第一个假设是对的：在行业标准基准上，我们的最大模型确实更强。

但 effort level 不仅仅是"思考时间"。effort level 控制的是 Claude 在你的请求上整体投入多少工作。这确实包含模型思考了多久，但也包括：

- 它读取多少个文件；
- 它做多少验证；
- 它在多步任务中会推进多远才与你核对。

在更高的 effort level 下，Claude 会在回来找你之前采取更多动作（譬如读文件、跑测试、反复核对）。在更低的 effort level 下，它宁愿向你多问一些上下文，也不愿消耗 token 自己摸黑试探。

## **模型选择是如何工作的**

当你按下回车，Claude Code 会把你的消息与系统提示、工具定义、你的 `CLAUDE.md`、对话历史以及上下文中的所有文件打包在一起，作为一次请求发送给 API。

![]()Claude Code 拿到的所有内容都被打包到一次 API 请求里。在服务端，文本在抵达模型之前先被分词（tokenize）。

不过模型并不会以纯文本的形式"看到"这些内容。服务端先做的第一件事是**分词**：文本被切分成若干片段，每一片段都被映射到模型训练时所用的固定词表里的一个整数。比如 `const` 可能映射到 1978，`await` 可能映射到 4293。从这一步开始，你的提示词就只是一个整数数组。

![]()分词器把文本切成片段，再把每个片段映射到固定词表里的一个整数。上一行的每个 chunk 在下一行对应它的 token ID（仅作示意）。

模型的工作就是拿到这个数组，预测下一个 token 是哪个。它会对词表中每一个 token 计算一个*概率*，再从概率最高的几个里选。比如在 `const x = await` 之后，一个训练良好的模型会给 `fetch` 一个很高的概率，给 `banana` 一个接近零的概率。

![]()模型的预测是对词表中每个 token 的一个概率。最高猜测与一个无关猜测之间的差距是巨大的。

把输入 token 变成这些概率的，是**权重**（也叫 *parameters*）。这些是数十亿个数字，组织成若干大型矩阵。为了预测一个 token，模型把你的输入过一遍这些矩阵——一条很长的矩阵乘法链——最后读出概率。模型"知道"的一切就住在这些权重里。

**每个模型的权重在训练时就已经定型，在你发送请求时它们是只读的。** 你的提示词、`CLAUDE.md`、上下文都不改变它们。（如果你遇到过 inference 一词，它的意思就是：在训练完成、权重固定之后使用模型。）

![]()提示词进去，概率出来。中间那些权重并不会改变。

Claude 关于 TypeScript、流行框架、地道 Go 写法或任何通用编程知识的一切，全都编码在训练时的权重里。

你的提示词和上下文依然可以 *引导* 预测（把真实的代码摆在 Claude 面前就是 *引导*，效果很好），但它们不会"加"进权重本身。

如果某个库在模型训练时还不存在，它就不会出现在权重里。你可以把文档塞进上下文，Claude 会用起来，但那叫 *引导* 而不是 *教学*。Claude 的回复只会受这一次请求影响，底层模型并没有记住这个信息。

所以当 Claude 自信地调用了一个根本不存在的 API（也就是幻觉），那是权重根据训练模式生成了一段 *看起来* 合理的 token 序列，而不是一次"查询失败"。

那么换模型究竟改了什么？它切换的是 **哪一组冻结的权重** 来处理你的请求。

模型不会一次性生成整个回答。它先预测一个 token，把它追加到序列，再重新跑一遍整个计算来预测下一个。一段 200 token 的回复，就是对权重的 200 次独立前向计算。这个循环就是你大部分等待时间和输出成本的来源。

![]()序列每一步只增长一个 token。模型每次都会重读整个数组来预测下一个。

所以**模型设置**决定了*由哪组权重* 来处理你的请求，也决定了每个输出 token 的成本。

它不决定的，是会生成多少个 token。这个数量对同一个提示词来说也可能差异很大，取决于 Claude 决定做多少工作。

这正是 **effort level** 控制的事：*每个回合里* Claude 决定做多少工作。

## **Claude Code 的 effort level 是如何工作的**

Claude Code 处理任务时，它生成的 token 可以分为几类：

- **思考（Thinking）**：你在动作前后看到的流式推理过程。
- **工具调用（Tool calls）**：结构化块，命名一个工具（如 Read 或 Edit）及其参数，由 Claude Code 解析并执行。
- **给你的文本**：计划、进度更新、最终的总结。

这些都来自同一个循环里产生的普通输出 token，按同一费率计费。例如，思考 token 的生成方式与其他输出 token 一样，并会停留在上下文里直到这一回合结束。

当 Claude 开始写代码时，它此前的推理也像它读过的文件一样，构成了下一轮输入的一部分。

![]()Claude 的所有输出都是 token。思考、工具调用和给你的文本都由同一个循环生成。

那么 effort 究竟改变了什么？effort level 会作为请求的一部分与你的提示词一起发送给模型。模型在训练时就学会了如何响应不同的 effort level，这种学到的行为被"烤"进了冻结的权重里。

当你的请求抵达时，effort level 是模型响应的又一个输入——和你的提示词文本一样。这决定了 Claude 的行为基调：在它认为任务完成之前，需要多彻底、多确定。

**这一行为会在每一回合被重新评估**，并以"产出更多 token 来换取更高置信度的答案"作为结果。

![]()同样的提示词，两个 effort level。高 effort 路径生成的 token 大约是 7 倍，以达到更高置信度的答案。

在更高的 effort level 下，Claude 通常会先制定一个计划，effort level 也会影响这个计划的深度与广度。不过计划本身并不是一成不变的：当 Claude 从它的动作中得到结果后，它会更新已经完成的进度以及它对累积结果的确定度。

所以当一个三假设调试计划的"步骤 1"就找到了 bug 时，"继续调查假设 2 和 3"就不再是必要动作了。Claude 通常会显式地说"第一个检查就找到了，所以剩下的检查可以跳过"，并往前推进。你在 Claude Code 里会看到任务清单在运行中被修订，就是这种情况。

在更高的 effort level 下，Claude 会更倾向于对额外假设做双重检查或验证正确性，但它一般不会在简单任务上人为放大使用量。事实上，我们团队在模型训练时非常关注"过度思考"现象，因为那会拉低效率。

## **如何选择 effort level**

我们的建议是：**对大多数任务，使用模型的默认 effort level。** 默认 level 下，Claude 会按照大多数人愿意在任务上花多少 token 来调度使用量。

把 effort 视为一个手动开关，用来调节 Claude 工作得有多深入、多持久。当你对自己的领域或工作类型在"彻底 vs. 速度"上有明确偏好时，请慎重选择。建议更多作为整体偏好来设定，而不是逐任务决定。

[Claude Opus 4.8 发布](https://www.anthropic.com/news/claude-opus-4-8) 后的一些实测心得可能对你有帮助：在我们的测试里，对同一任务使用 Opus 4.8 的默认 effort 设置，产出结果优于 Opus 4.7 的默认 effort 设置，而两者消耗的 token 数大致相当。

## **Claude 出错时该改什么**

当 Claude 答错时，你的本能不应该是去拧旋钮，而是先审视你提供的上下文：提示词是不是太模糊？Claude 是否连上了正确的工具？是否配置了合适的 skills？

如果给一个 *不该* 高 effort 的任务调高了 effort，修复常常在更上游——在你的上下文里、你的 `CLAUDE.md` 里，或者任务本身的范围上。

但假设你已经提供了清晰的上下文，Claude 仍然答错，这时你该问自己的是：它到底是 *没尽力*，还是 *不够懂*？

![]()两个问题，一个回退方向。用这个启发式来挑起点，而不是当作硬性规则。

### **模型：问题本身太难**

当问题本身确实困难时，选更大的模型。比如处理细微 bug、不熟悉的领域、架构决策。在小模型无论给多少上下文都自信地给出错误答案时，更大的模型能帮上忙。

更大的模型也更擅长处理歧义；而对于小模型，给出明确指令指明执行路径，往往是更有效的成功配方。

工作很常规时，选更小的模型。比如你可以精确描述的编辑、机械性的修改、或者关于已在上下文中的代码的问题。为用不到的能力付费毫无意义。

如果 Claude 掌握了所有相关上下文、显然已经尽力却还是错了，那是该换更大模型的信号。如果你已经在用更大的模型，工作流也已经常规化了一段时间，那降回小模型通常能在不影响输出质量的前提下提升速度、降低成本。

### **Effort：Claude 没尽力**

如果 Claude 出错是因为它跳过了文件、没跑测试、或者没对自己的工作做双重检查，那就升 effort level。这种情况在你当前选的 effort level 低于模型默认时最常见。

**Fable vs. Opus vs. Sonnet：专家、熟手与多面手**

我很喜欢用这样一个比喻来描述两者设置的关系：Fable 是见过几乎没人见过的难题的"专家"，Opus 是"熟手"，Sonnet 是非常优秀的"多面手"。effort level 决定了他们三人在你的任务上花多少时间。

**低 effort 的 Opus** 就像与一位熟手共度五分钟：他带来的是你的代码库里找不到的经验——以前见过的模式、知道要核验的坑、只有解决过大量类似问题才会有的那种直觉。但只给五分钟，意味着只能快速扫一遍代码，而不是仔细地读。

**高 effort 的 Sonnet** 就像把整个下午交给一位非常出色的多面手：他会读完所有东西、跑起来、对自己的工作反复检查，最后彻底搞懂 *你的具体代码*。他带来较少的那种"我恰好见过这种情况"的识别力。

**即便是低 effort 的 Fable**，也是那位专家在大家一筹莫展时扫一眼题目，仍然能发现别人看不见的东西。这种识别力是你付费最多去买的能力，所以把它留给真正需要它的任务才划算。

这三者并没有哪个永远更优。模型设置大致决定 *有多强*；effort 设置大致决定 *有多细*。多数真实任务对两者都有需求。

## **Effort、模型与 token 消耗**

那么模型选择、effort 和 token 消耗是如何共同作用的？这取决于任务。

对常规工作、在同一个 effort level 下，两个模型通常都能答对。更大的模型会因为额外的验证步骤消耗更多 token、且单 token 价格更高。这就是为什么在常规任务流里降级到小模型，能在不损失质量的前提下真正省钱。

![]()曲线仅作示意，针对的是单个简单到两者都能快速完成的任务，不代表真实基准数据。

对更困难的、多步的工作，等式就不同了。小模型必须拼到能力的极限，消耗更多迭代次数；而更大的模型用更少的步骤就能达到同样的质量门槛。

你为更大的模型付了更高的单 token 价格，但在真正把小模型逼到极限的任务上，单任务的整体成本反而可能更低。更重要的是，更大的模型能完成小模型即便在最高 effort 设置下也无法完成的任务。

这一点在 Fable 上最为明显：在长时多步任务上，它拉开了最大的距离。在我们的测试里，它完成了一些 Opus 和 Sonnet 在任何 effort level 都无法触及的工作。它的单 token 成本也最高，这是把它留给确实需要它的另一条理由。

![]()曲线仅作示意，针对的是单个能逼到两者极限的困难任务，不代表真实基准数据。

上面这些图里最关键的一点是：effort level 决定的是 Claude **愿意沿曲线走多远**，但这并不等于 Claude **需要走那么远**才能完成任务。

还有一个细节：effort 塑造 token 消耗，但并不限制它。整个系统里的硬上限只有 [max_tokens](https://platform.claude.com/docs/en/build-with-claude/extended-thinking#max-tokens-and-context-window-size-with-extended-thinking)，它在达到时会把回复从中间截断。这是一把钝刀子，主要跟 API 开发者相关。更柔和的控制，比如 [task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets#task-budgets-are-advisory-not-enforced) 或者在提示词里让 Claude "保持简洁"，是更有用的工具。它们是模型训练时学会遵循的"指引"——当接近上限时，模型会倾向于收尾——而不是它会撞上的墙。

## **从默认起步，再去动旋钮**

大多数时候，你不应该去想这两个设置。当结果不达预期时，先问："Claude 是懂得不够，还是尽力不够？"再据此调整。
