# Datadog 如何为 Claude Code 打造一台"通用母机"

*原文标题：How Datadog built a "universal machine tool" for Claude Code*

> 原文链接：https://claude.com/blog/how-datadog-built-a-universal-machine-tool-for-claude-code

Datadog 让一位 agent 编写规约，由一个确定性内核写出应用代码。

## 智能体、机械化与工业化

Datadog 全体工程师都使用 AI 编码工具来开发生产代码，其中 Claude Code 至少驱动了三分之二的工作流。借助 Claude Code，他们在软件开发生命周期中生成个性化流程，分为四个明显不同的类别：

- **针对性改动：** 数十处棘手的 bug 修复、性能优化、以及与现有服务的桥接。
- **大型重构：** 三天内重构一个自定义 protobuf 解析器；不到三个月把一项指标控制从 FoundationDB 改写到 Postgres。
- **替换大块模块：** 新的分片算法与自动扩缩容设计的重做。
- **构建整套系统：** 用 Postgres 替代 MongoDB、构建 BYOC 控制平面、从零搭建摄取流水线。

然而，当工作沿着这张地图铺开时，他们看到：一方面"生成"变得更加复杂，另一方面"验证"变得更加模糊。

## 流程问题

对工程师而言，所谓的"心流"原本意味着意图和代码之间的直接关系：理解问题、写代码、测试、评审、上线、运维、再来一遍。有了 agent，抽象正在快速变化。

> "你不再直接写代码，而是在塑造工作。你要决定 agent 该看到什么、它有哪些工具、什么叫成功、怎么检测失败……就像每个人都突然被提拔到了管理层之上三级，而他们当年入职可不是为了当管理者的，"Datadog 工程副总裁 Sesh Nalla 说。

借助 [Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview) 等方式，Datadog 的会话持续时间更长，有时长达数天。每个 agent 都会发明自己的工具、自己的粘合代码、自己的约定。agent 变得显著更有用，但也需要人弥合"agent 执行"与"为人设计的工具"之间的鸿沟。

机床就是你在制造业里看到的那些夹具、卡具、量具与铣床。它们生产出精密、可重复的零部件，再用这些零件组装成更大、更复杂的机器——发动机、飞机、核反应堆、月球着陆器。它们是工业化的突破，让零部件变得可组合、可检验、可替换。

Temper 是 Sesh 所描述的 Datadog 对"agent 系统的通用母机"的尝试。换言之，是让 agent 能够以安全、精确的方式构建它们所需之物所需的最小内核。

> "我觉得这是我们需要一个更具结构性方案的时刻，"Sesh 说。"如果 agent 要构建并运维我们系统中、数据库中的大片关键模块，它们需要等价的'母机'概念。Temper 就是 Datadog 的那台母机。"

## 通往 Temper 的路

机械化意味着 agent 现在承担了更多工作。工业化则意味着工作变得可重复、可验证、可控、可规模化。在 Datadog，这一过程并不是一蹴而就：通往 Temper 的路经过了另外三个项目——Courier、BitsEvolve 和 Helix。每一项都暴露出下一项的瓶颈，也让他们得以提升雄心。

2024 年，他们推出了 [**Courier**](https://www.datadoghq.com/blog/engineering/formal-modeling-and-simulation/)——一套分布式队列系统。整个系统花了他们一年时间全手工、从零搭建。

> "难点不在搭建各个部分，而在于让它们之间的交互可观测、可测试、可验证，"Sesh 说。"因此我们在形式化建模与仿真上做得很严……找出那些出错代价高昂、或难以挽回的环节，在那些地方提升严谨度。"

2025 年 9 月，他们构建了 [**BitsEvolve**](https://www.datadoghq.com/blog/engineering/self-optimizing-system/)——一个闭环的进化式优化引擎。由一组模型组成"委员会"生成代码变体，再由一连串 [基准](https://www.datadoghq.com/blog/ai/production-grounded-code-optimization/)、测试、生产可观测性来决定哪些能"活下来"。

> "这是我第一次隐约看到，软件的某些部分可以像生物体一样被'培养'——通过带反馈的变异与适应来生长，"Sesh 说。

但前提是：进化只与它所适应的环境一样好，而 BitsEvolve 的瓶颈就在这个反馈环上。随后他们构建了 [**Helix**](https://www.datadoghq.com/blog/ai/fully-autonomous-optimization/)——一套可比肩 Kafka 的流式服务。Claude Code 在一位人类"指挥"下完成了大部分构建工作。

> "让我们难以置信的是，几天之内我们就拥有了一个功能齐备的、可比肩 Kafka 的系统，"Sesh 说。"[它搭建得很快] 我们开始让它影子运行，发现了它有 2 倍到 5 倍降本的机会。"

不过，要走到生产环境，还有很长的路要走：运营上的硬化只能靠时间和不止一个人的经验慢慢积累，目前 Helix 仍在逐步推广中。

> "瓶颈又一次移动了——agent 已经能构建系统的大块……但人类仍然要通过为人设计的工具与机制，把工作协调推进到生产环境，"Sesh 说。

Datadog 需要一种方式，让 agent 能够在经过验证、策略驱动的运行时环境中构建自己的工具。这个运行时就是 [**Temper**](https://github.com/nerdsane/temper)。

## Temper

Agent 写代码的速度比任何团队手工评审都快，但它们也会犯错。

对 Sesh 而言，"agent 生成什么"与"什么通过验证"之间的鸿沟，正是失败模式堆积之处。简单地把 agent 包在一套传统代码库外面，只把它当作吞吐量问题处理，并没有真正弥合验证缺口。

Temper 把这个等式反转了过来：agent 产出的不是应用代码，而是规约。内核读取每份规约，通过四层分析进行验证，然后部署规约所描述的运行系统。由于规约既是被验证的对象，也是被执行的对象，**被验证的与正在运行的之间没有漂移**。

> "Temper 改变了系统的 *中心*。Agent 不再需要为每一个局部需求不断发明互不相连的工具。相反，它产出的是精确的规约——描述意图与问题领域的规约。它就是一台母机，就像夹具或数控机床，你给它规约说螺距该怎么切。它极具可重复性。你可以运行它们，用它们造飞机那样复杂的东西，"Sesh 说。

因此在这种情况下，agent 不会每次都临场拼凑最终机制。它可以产出一份精确的规约，与 Temper（或者类似 Temper 的机制）一起迭代，先让事情跑通，再把这件事固化成可重复、可检验、可复用的东西，让你真的能在你的代码库周围建起一座软件工厂。

每一项能力都由三份契约来描述：

- **行为契约（Behavior）：** 必须成立的状态、迁移、前置条件与安全属性。
- **数据契约（Data contract）：** 实体类型、它们的属性，以及每种类型支持的动作，以机器可解析的形式发布，让 agent 在没有文档的情况下也能发现完整 API。
- **授权契约（Authorization）：** 默认拒绝、基于范围的审批，拒绝被记录为"待定决策"，由人来审批并热加载到策略引擎。

每份规约在被内核加载前，都要通过四层独立分析：

- **符号推理（Symbolic reasoning）：** 证明每个守卫都是可满足的、每个不变量都是归纳成立的。
- **穷尽状态探索（Exhaustive state exploration）：** 访问每一个可达状态。
- **确定性仿真（Deterministic simulation）：** 用种子化的故障注入——丢包、延迟、重排序、崩溃——运行真实的生产代码路径，使失败在相同种子下精确可复现。
- **随机属性测试（Randomized property testing）：** 跑约一千条伪随机动作序列，并把任何违例收缩到最小的反例。在一份小型规约上，这一整套级联用时远小于一秒。

## Helix 的"黑暗工厂"

Simon Willison 让"dark factory"（黑暗工厂）这个词流行起来——一种让 agent 在虚拟工厂车间里无人工持续作业的软件流程。在 Helix 黑暗工厂里，Temper 扮演三个角色。

它是面向托管 agent 的 **agent 控制平面**——会话、角色、工作队列、生命周期。它是 **工具构建层**，让 agent 用小型 Temper 应用打通 SDLC 工具（Git、CI、部署）。它还是 **Helix 控制 API**，围绕数据平面执行工作负载的生命周期接口。

> "惊喜在于它开始让人感觉比'agent 基础设施'更具普遍性。很多软件，如果你眯起眼睛看，本质上就是数据库 API 之上的控制逻辑：状态、变更策略、生命周期迁移、与外部系统的集成。Temper 某种意义上是通用的——它可以套用到任何符合我所描述形态的软件上，"Sesh 说。

## 为什么不直接做个 CRUD 应用？

> "Claude Code 用 TypeScript 或 Python [搭一个 CRUD 应用] 完全没问题。但在一个普通的 CRUD 应用里，控制逻辑散落在路由、数据库约束、服务代码、后台任务与文档各处。它可能有不错的测试与覆盖率，但通常以状态机形式存在的运营模式，被隐含在代码库里，"Sesh 说。

> "Temper 把这台状态机显式化。Agent 产出的是精确的规约，而不是任意代码。编译步骤位于 LLM 之外，就像你把 Rust 代码交给 Rust 编译器。迁移表是数据，而不是埋在服务方法里的意大利面式控制流。Agent 可以在策略之下动态修改它、安全地热重载它，而不必走 CI，"他解释道。

## 这将走向何方

Temper 背后的理念是：每一件产物都应该小到能装进你脑子里。像航空、金融系统那样的高保障软件几十年来就是这么造的；只是靠人来达到这种严谨性，对一般软件来说代价太高，直到 agent 登场才出现转机。

工业革命之所以成为可能，是因为母机让零部件变得可组合、可检验、可替换，让我们能造出越来越大、越来越复杂的机器。

> "如果 agent 能在这种纪律化的工厂里自主构建软件，那我们也许不必止步于黑暗工厂。用这种方式造出来的软件，开始让人感觉像是一种我们可以培育、培养、并通过反馈、选择与适应来进化的有机体，"Sesh 说。

## Datadog 团队的最佳实践

**你真正的瓶颈是生成，还是验证？**
**先假定是验证。** Agent 写代码已经比任何团队手工评审更快；"被生成的"与"被证明的"之间的鸿沟，才是失败模式堆积之处。把投入放在那里，而不是放在更高的吞吐量上。

**Agent 真正应该产出什么？**
控制逻辑的规约（而非代码），以及任意代码的"自带证明"。把编译与证明放在 LLM 之外——把规约交给一个确定性内核，让"被验证的产物"和"运行中的产物"是同一份。

**你的控制逻辑是显式的，还是散落在代码库各处的？**
把状态机从路由、服务方法、后台任务里抽出来，让它成为数据：一张 agent 能读、能改、能在策略下热重载的迁移表。

**每件产物人类能"装进脑子里"来理解吗？**
如果不能，你就回到了起点。让每一份产物的体量都小到足以推理。
