Markdown 已经成为 Agent 与我们交流的主流文件格式。它简洁、便携、具备基本的富文本能力，也方便手动编辑。Claude 甚至出乎意料地擅长在 Markdown 文件里用 ASCII 画图。
Markdown 已经成为 Agent 与我们交流的主流文件格式。它简洁、便携、具备基本的富文本能力，也方便手动编辑。Claude 甚至出乎意料地擅长在 Markdown 文件里用 ASCII 画图。
但随着 Agent 越来越强大，我开始觉得 Markdown 成了一种制约。超过百行的 Markdown 文件，我读起来很吃力。我想要更丰富的可视化呈现——颜色、图表——而且要方便分享。
与此同时，我也越来越少亲自编辑这些文件，更多时候是把它们当作规格说明、参考资料、头脑风暴的输出物来使用。偶尔需要修改，我通常也是提示 Claude 来改，这就消解了 Markdown 最大的优势之一。
我开始倾向于把 HTML 作为输出格式，也越来越多地看到 Claude Code 团队的其他人这样做——原因就在这里。

## 为什么选 HTML？
信息密度
HTML 能承载比 Markdown 丰富得多的信息。它当然可以做简单的文档结构，比如标题和格式排版，但还能表达各种更复杂的信息，例如：
用表格呈现结构化数据
用 CSS 表达设计语言
用 SVG 绘制插图
用 script 标签嵌入代码片段
用 JavaScript + CSS 实现交互元素
用 SVG 和 HTML 描绘工作流
用绝对定位和 canvas 处理空间数据
用 img 标签嵌入图片
我甚至可以这样说：Claude 能读取的几乎任何信息，都可以用 HTML 高效地表达出来。这使它成为模型向你传递深度信息、供你审阅的极佳媒介。
如果没有这种能力，模型往往会在 Markdown 里做一些效率更低的事——比如画 ASCII 图，或者用 Unicode 字符来估色，后者是我最印象深刻的奇技淫巧，就像 Claude Code 截图里那样。
可读性与视觉清晰度
随着 Claude 能处理的工作越来越复杂，它写出的规格说明和计划文档也越来越长。在实际使用中，我发现自己通常不会真正通读超过百行的 Markdown 文件，更别提让组织里的其他人去读了。
但 HTML 文档就容易阅读得多。Claude 可以在视觉层面优化文档结构，用标签页、插图、链接等方式方便导航，甚至做到移动端自适应，让你在不同设备上以最合适的方式阅读。
易于分享
Markdown 文件分享起来相当麻烦，因为大多数浏览器无法原生渲染。你通常得把它作为附件发送。
而 HTML 文件，只要上传到某个地方（比如 S3），就能直接分享链接。同事可以在任何地方打开，随时引用。
把规格说明、报告或 PR 描述做成 HTML，别人真正去读它的概率会高出许多。
双向交互
HTML 可以让你与文档产生互动。比如，你可以让 Claude 在文档里加入滑块或旋钮来调整某个设计参数，或者让你调整算法中的不同选项来观察效果变化。你也可以让它提供一个"复制到提示词"的按钮，把你的调整结果粘贴回 Claude Code。
关于这种双向交互的更多示例，可以参阅我关于 Playgrounds 的那篇文章：https://x.com/trq212/status/2017024445244924382
数据摄取
为什么要用 Claude Code 来生成 HTML 文件，而不是 Claude.ai 或 Claude Design 呢？最重要的原因之一，是 Claude Code 能摄取的上下文之丰富。
举个例子：写这篇文章时，我让 Claude Code 遍历我的代码目录，找出所有我生成过的 HTML 文件，对它们进行分组和归类，然后生成一个 HTML 文件，用图表来呈现每种类型。你在本文中看到的那些图表，正是这样得来的。
除了文件系统，Claude Code 还可以通过 MCP（如 Slack、Linear 等）、浏览器（借助 Claude in Chrome）、Git 历史记录等方式获取额外的上下文。
它让人愉悦
用 Claude 创建 HTML 文档本身就更有乐趣，让我觉得自己更投入、更有参与感——光这一点就足够了。

## 如何上手
我有点担心有人读完这篇文章就去弄一个 /html 技能插件。这样做或许也有一定价值，但我想强调的是：你根本不需要做太多准备。直接告诉 Claude"生成一个 HTML 文件"或"做一个 HTML artifact"就够了。
关键在于你清楚自己想要这个 artifact 做什么，以及打算怎么用它。随着时间推移，你可能会沉淀出属于自己的技巧，但现在，我建议从零开始直接提示，先感受不同场景下的用法。

## 使用场景
为了让这些更加具体，我针对不同场景制作了许多 HTML 文件。你可以在这里查看全部内容：https://thariqs.github.io/html-effectiveness/
规格说明、规划与探索
HTML 是 Claude 深入思考问题的丰富画布。当我开始处理一个问题时，我不再期待用一份简单的 Markdown 计划搞定，而是会生成一张由多个 HTML 文件组成的网络。比如，我可能先让 Claude Code 进行头脑风暴，探索几种不同方向；然后让它深入展开其中一个，也许还会加上交互原型或代码片段；最后，当我感觉方向对了，再让它输出一份实施计划。计划满意后，我会开一个新的会话，把所有这些文件作为上下文传入，让它开始实现。
在验证阶段，我也会让验证 Agent 读入这些文件，这样它就能对需求有更全面的理解。
示例提示词：
> 我不确定新手引导页面该走哪个方向。请生成 6 种明显不同的方案——在布局、基调和信息密度上都要有所区别——并排展示在一个 HTML 文件的网格里，方便我横向对比。每个方案都标注它所做的权衡取舍。
> 请用 HTML 文件编写一份详尽的实施计划，加入一些交互原型、数据流示意图，以及我可能需要审阅的关键代码片段。让它读起来轻松易懂。
适用场景：
探索某个功能的多种实现方式
对比多个视觉设计方案
代码审查与理解
在 Markdown 文件里读代码相当费劲。但用 HTML，我们可以渲染 diff、添加注释、绘制流程图、展示模块关系等。用它来理解 Agent 编写的代码、做代码审查，或向审查者说明一个 PR——我发现这往往比 GitHub 默认的 diff 视图更好用。现在每次提 PR，我都会附上一份 HTML 代码解读文件。
示例提示词：
> 帮我审查这个 PR，为它创建一个 HTML artifact。我对其中的流式处理和背压逻辑不太熟悉，请重点讲解这部分。渲染出实际的 diff，在行内页边添加注释，按严重程度为发现的问题标色，并用你认为合适的其他方式来清晰呈现概念。
适用场景：
创建 PR 说明
审查 PR
深入理解某段代码
设计与原型
Claude Design 基于 HTML，因为 HTML 的表达力极强，即便你的最终交付物并不是 HTML。Claude 可以先在 HTML 里勾勒设计草图，再用你实际使用的语言（React、Swift 等）来实现。
你也可以对交互效果进行原型验证，比如动画、交互行为等。可以让 Claude 加入滑块、旋钮，让你精确调试到满意为止。
示例提示词：
> 我想给结账按钮做一个新原型：点击后播放一段动画，然后快速变成紫色。请创建一个 HTML 文件，提供若干滑块和选项供我调试这个动画，并加一个"复制参数"按钮，让我能把调好的参数复制出来。
适用场景：
创建设计系统 artifact
调整组件
可视化组件库
为令人愉悦的动画效果制作原型
报告、研究与学习
Claude Code 非常擅长跨多个数据源综合信息，并将其转化为易读的报告。你可以提示 Claude 检索你的 Slack、代码库、Git 历史、互联网等，然后生成极具可读性的报告——给自己看、给管理层看、给团队看，都行。
你可以将其组织成一份长篇 HTML 文档、一个交互式说明页，甚至是幻灯片形式的演示文稿。让 Claude 用 SVG 绘制图表来辅助可视化。
例如，在写提示词缓存系列文章时，我让 Claude 读取 Git 历史后，以 HTML 格式为我准备了一份关于提示词缓存所有变更的深度研究文件，供我仔细阅读。
示例提示词：
> 我搞不清楚我们的限流器到底是怎么工作的。请读取相关代码，生成一个单页 HTML 解读文档：包含 token bucket 流程图、3 到 4 段带注释的关键代码片段，以及底部的"注意事项"部分。针对只读一遍的读者来优化。
适用场景：
总结某个功能的工作原理
向自己解释某个概念
向上级汇报的周报
向管理层提交的事故报告
SVG 插图、流程图、技术架构图等
定制化编辑界面
有时候，纯文字框很难表达清楚你想要什么。这种情况下，我会让 Claude 为我当前处理的内容量身构建一个一次性编辑器——不是产品，不是可复用的工具，就是一个为这一份数据专门打造的单 HTML 文件。
关键在于最后要有一个导出口：一个"复制为 JSON"或"复制为提示词"的按钮，把我在界面上做的操作转化成可以粘贴回 Claude Code 的内容。
示例提示词：
> 我需要重新排列这 30 张 Linear 工单的优先级。请做一个 HTML 文件，把每张工单做成可拖拽的卡片，分布在"现在 / 接下来 / 之后 / 砍掉"四列中。按你的最优判断预排序，并加一个"复制为 Markdown"按钮，导出最终排序，每个桶附上一行理由说明。
> 这是我们的功能开关配置。请为它构建一个表单式编辑器：按功能域分组，展示开关之间的依赖关系，如果我启用了某个前置条件未满足的开关就给出警告，并加一个"复制变更"按钮，只输出被修改的键值对。
> 我在调试这个系统提示词。请做一个左右对比编辑器：左边是可编辑的提示词，变量槽位高亮显示；右边是三组示例输入，实时渲染填入变量后的完整内容。加上字符数和 token 数统计，以及一个复制按钮。
适用场景：
对任意内容（工单、测试用例、反馈）进行排序、分类或分桶
编辑有约束的结构化配置（功能开关、环境变量、带限制的 JSON/YAML）
调试提示词、模板或文案，实时预览效果
整理数据集：审批/拒绝行、为示例打标签、导出筛选结果
对文档、对话记录或 diff 添加注释并导出
选取难以用文字描述的数值：颜色、缓动曲线、裁剪区域、Cron 表达式、正则表达式

## 常见问题
在向许多人分享我切换到 HTML 这件事的过程中，我遇到了一些反复被问到的问题。
Token 效率更低，不是吗？
Markdown 通常用的 token 更少，但我发现 HTML 更强的表达力，加上我真正去读它的概率大幅提升，综合来看产出更好。Opus 4.7 拥有 100 万 token 的上下文窗口，token 用量的增加在上下文层面根本感觉不到。
现在什么情况下还会用 Markdown？
说实话，我几乎已经在所有场景下停用 Markdown 了——但我可能是偏 HTML 极端的那一类人。
怎么查看 HTML 文件？
我通常直接在本地浏览器里打开（可以让 Claude 来帮你打开），或者上传到 S3，需要分享时发链接就行。
生成速度比 Markdown 慢，不是吗？
确实更慢！HTML 的生成时间大概是 Markdown 的 2 到 4 倍。但我认为结果值得这个代价。
版本控制怎么处理？
这确实是 HTML 最大的缺点之一。与 Markdown 相比，HTML 的 diff 噪声大、难以审阅。
怎么让 Claude 做出符合我审美的东西，不要太丑？
前端设计插件可以帮助 Claude 生成更好看的 HTML 文件。但如果想匹配你所在公司的风格，你可以让 Claude 指向你的代码库，生成一个设计系统 HTML 文件，然后用这个文件作为其他 HTML 文件的样式参考。
始终在线，始终在场
综上所述，我认为自己使用 HTML 的真正原因，是它让我感觉与 Claude 的协作更加同步。我曾经一度担心，因为不再深读计划文档，我只能任由 Claude 自行做决定。
但我现在可以高兴地说：使用 HTML 之后，我比以往任何时候都更有参与感。希望你也能感受到这一点。
