## 核心摘要

AI 带来的真正变化，不是程序员少写了多少代码，而是企业必须重新设计从意图、实现、验证到生产反馈的整个软件生产系统。

**四份核心材料**：
- Google《The New SDLC with Vibe Coding: From Ad-hoc Prompting to Agentic Engineering》
- LangChain《The Agent Development Lifecycle》
- Anthropic《The AI-Native SDLC Playbook》
- OpenAI《Building an AI-Native Engineering Team》

**共同结论**：AI 对软件工程最大的影响，不是提高某个开发环节的效率，而是迫使企业重新设计整个软件开发生命周期。

---

## 四份报告的核心观点

### 1. Google：Vibe Coding → Agentic Engineering

从宏观层面描述了软件开发从 vibe coding 走向 agentic engineering 的过程，提出：
- **Context Engineering**：上下文工程
- **Harness Engineering**：系统与工具链工程
- **Factory Model**：工厂模型
- **开发者角色转变**：从 Conductor 转向 Orchestrator

核心分界不是"是否使用 AI"，而是 AI 输出周围是否存在充分的规格、测试、约束、反馈和人工判断。

### 2. LangChain：Agent Development Lifecycle

将视角延伸到 Agent 产品的生产环境，把生命周期概括为：

```
Build → Test → Deploy → Monitor
```

并在外层加入持续迭代和治理。**特别强调**：
- 传统软件监控关注服务是否正常运行
- Agent 监控还必须回答：它是否选择了正确工具、遵循了正确路径、使用了正确上下文，以及是否真正完成了任务

### 3. Anthropic：AI-Native SDLC Playbook

提供了一套更接近企业落地的流程蓝图，从 intent.md、spec.md、plan.md，到代码、测试、Pull Request、审查记录和生产事故，每个阶段都产生一个既能被人理解、又能被 Agent 继续处理的版本化制品。

**关键区分**：
- **Skills**：告诉 Agent"应该怎样做"（建议性控制）
- **Hooks**：从技术上限制 Agent"不能怎样做"（确定性机制）

### 4. OpenAI：Building an AI-Native Engineering Team

把重点放在团队工作方式上，通过三种责任关系重新划分人机边界：

- **Delegate**：Agent 承担第一轮分析和机械执行
- **Review**：人类负责复核完整性
- **Own**：人类继续拥有产品意图、架构取舍、质量和生产风险的最终责任

## 四份材料共同强调的核心判断

1. **代码生成正在从稀缺能力变成基础能力**
2. **软件交付的瓶颈正在向需求、验证、审查和治理迁移**
3. **模型能力不能单独决定工程结果，Context 与 Harness 同样重要**
4. **测试、Evals、运行轨迹和生产反馈必须形成持续闭环**
5. **人类不会退出软件开发，但会从主要实施者转向意图定义者、系统设计者和风险责任人**

## AI-Assisted vs AI-Native 的五个本质区别

### 第一：意图成为正式工程输入

传统流程中，需求分散在会议记录、即时通信、工单和人的记忆中。

AI Native 流程中，意图必须被结构化和版本化：
- 说明问题是什么、为什么值得解决
- 影响哪些用户和系统
- 有哪些约束、哪些内容不在范围内
- 怎样才算成功

### 第二：组织知识变成可执行上下文

AI Native 团队把这些知识转化为：
- 规则文件
- Skills
- 工具定义
- 检索系统
- 代码示例
- 验证命令

### 第三：验证与生成同时发生

AI Native 开发要求 Agent 在把结果交给人类之前，先运行构建、测试、lint、静态分析和必要的视觉检查，并根据真实结果自行迭代。

"完成"不再意味着 Agent 停止生成，而意味着它能够提交可检查的证据。

### 第四：治理发生在行动时

安全和合规要求不能只写在政策文件或 Prompt 里：
- 哪些目录不可修改
- 哪些凭据不可读取
- 哪些网络不可访问
- 哪些生产操作必须审批

都需要由权限、沙箱、Hook、CI 和身份系统强制执行。

### 第五：生产反馈重新进入开发循环

生产事故、用户反馈和 Agent 运行轨迹不再只是事后分析材料，而是需要转化为新的需求、回归测试、Eval 样本、规则或监控信号。

```
Intent → Spec → Plan → Build → Verify → Review → Deploy → Observe → New Intent
```

## 从 Vibe Coding 到 Agentic Engineering

### Vibe Coding 的价值与局限

**价值**：原型、个人工具、一次性脚本和探索性工作能够显著降低创造软件的门槛。

**问题**：生产软件不能只满足"看起来可以运行"。边界条件、错误处理、依赖真实性、架构一致性、权限最小化、长期可维护性都是必须回答的问题。

### 风险分级自治

不同任务可以位于不同的风险等级：

- **原型和探索**：允许较高自由度
- **普通业务功能**：Agent 实现并自测，但由工程师批准计划和合并
- **身份、支付、数据和基础设施变更**：需要更严格的架构、安全和生产审批

真正成熟的团队，不会要求所有任务采用同一种自治程度，而是根据风险、可逆性和验证能力动态决定人机边界。

## 新的软件生产链：意图制品到生产反馈

Anthropic 提出的制品链：

```
intent.md → spec.md → plan.md → 代码与测试 → PR与审查记录 → 事故记录 → 新intent.md
```

### 规划：让最初的意图少经历几次转述

Agent 可以结合代码库判断哪些服务会受影响、现有能力能否复用、需求中是否存在明显矛盾。

但优先级、商业价值和战略方向仍然必须由人决定。

### 设计：在代码产生之前处理风险

安全、合规或架构问题可以在规格产生时就被读取和应用。

但架构取舍（一致性与可用性、短期速度与长期维护、复杂度与扩展性、构建与采购）仍然依赖业务背景和组织战略。

### 构建：先审查计划，再生成代码

Agent 先阅读意图、规格和代码库，形成实现计划，说明：
- 哪些文件和模块需要变化
- 实施顺序是什么
- 存在哪些风险和集成点
- 哪些方案被考虑过但没有选择
- 哪些测试能够证明功能正确

工程师在代码产生之前修正计划，因为此时改变方向的成本最低。

---

## 测试正在从阶段变成语言

在 AI Native SDLC 中，测试不仅用于检查代码，也成为向 Agent 表达意图的一种方式。

自然语言很容易产生歧义，而可执行测试能够更精确地说明系统在给定条件下应该怎样表现。

### 独立验证原则

- 在实现前确定关键验收条件
- 验证新测试在功能实现前确实会失败
- 将实现与最终验证放在不同会话或不同 Agent 中
- 禁止修复任务删除或弱化失败测试
- 对 UI 工作加入截图或浏览器验证
- 对模型、Prompt、Skill 和工具更新运行回归 Evals
- 将生产事故转化为永久回归案例

---

## 普通软件需要测试，Agent 产品还需要 Evals

### 两种 AI Native 的区分

**使用 Agent 开发普通软件**：测试主要验证确定性行为（输入是否产生预期输出，状态是否正确变化，接口是否符合契约）

**开发的软件本身就是 Agent**：需要额外验证它是否调用了正确工具、遵循了正确路径、使用了正确上下文、是否真正完成了任务

### Agent 可观测性必须回答的问题

- 它做了什么？
- 为什么这样做？
- 做得是否正确？

"服务没有报错"并不等于"任务成功完成"。

---

## 真正决定效果的，往往不是模型，而是 Harness

### 模型只是推理引擎

让 Agent 能够完成实际工程任务的，是包围在模型之外的一整套 Harness：

- 项目指令和规则文件
- 代码库、架构和领域知识
- 工具、API 和 MCP 服务
- 会话状态与持久记忆
- 沙箱和执行环境
- 权限、身份和凭据
- 任务分解与 Agent 编排
- Hooks 与审批门禁
- 日志、轨迹、成本和质量监控

### Prompt Engineering → Context Engineering

好的上下文工程不是向模型提供尽可能多的信息，而是在正确时间提供完成任务所需的高信号信息。

成熟团队需要像管理代码一样管理上下文：明确所有者、版本、审查流程、适用范围和回归测试。

---

## Skills 与 Hooks：建议性控制 vs 确定性机制

### Skills（建议性控制）

适合编码组织知识，例如安全审查步骤、API 设计规范、品牌要求和文档流程。

### Hooks（确定性机制）

如果某条规则必须始终成立，就需要确定性机制：
- 受保护路径禁止 Agent 修改
- 凭据、个人数据和生产秘密不能进入上下文
- Shell 命令只能在隔离环境中运行
- 网络访问采用域名白名单
- Agent 使用独立身份和短期凭据
- 所有代码变更必须通过 Pull Request
- Agent 不能自行批准自己生成的代码
- 生产部署必须获得命名责任人的明确授权
- 所有允许、拒绝和覆盖行为都要留下审计记录

## 工程师不会消失，但工作的重心正在变化

### OpenAI 的 Delegate / Review / Own 框架

**Delegate**：边界明确、重复、风险较低并且可以自动验证的任务（脚手架、常规接口、测试初稿、依赖维护、文档更新、日志关联）

**Review**：Agent 可以提供第一版，但需要人类检查其完整性和影响的工作（设计方案、性能分析、测试覆盖、代码审查、故障诊断）

**Own**：组织必须由人承担责任的事项（产品方向、核心架构、风险接受、重大安全决策、生产授权）

### 工程师角色的转变

- 定义意图和成功标准
- 设计架构和工程边界
- 分解与调度 Agent 任务
- 维护上下文与 Harness
- 设计测试、Evals 和反馈机制
- 审查例外并接受剩余风险
- 对最终结果承担责任

**重要提醒**：如果工程师缺少调试、安全、性能和架构判断，就更难识别那些"看起来正确"却包含隐蔽错误的 AI 输出。

**AI 放大的不是工具本身，而是团队原有的工程文化。**

---

## 多 Agent 并不天然等于高效率

并行 Agent 增加的是在制品数量，不一定增加最终吞吐量。

### 并行度的真正上限

不是平台允许启动多少 Agent，而是团队能够认真评估多少结果。

### 合理做法

- 只并行处理文件和依赖相对独立的任务
- 为每个任务使用独立分支或 Worktree
- 将研究、验证、代码简化等重复工作交给职责明确的子 Agent
- 限制同时在制的任务数量
- 将审查质量和返工率与并发数一起观察

## AI Native SDLC 的经济账，不能只看 Token

### Vibe Coding 的隐藏成本

- 反复提示和修复造成的 Token 浪费
- 不一致代码带来的维护负担
- 缺失测试导致的生产缺陷
- 安全问题的后期整改
- 工程师理解陌生 AI 代码所需的时间
- 模型和工具升级后的行为漂移

### Agentic Engineering 的前期投入

- 规格、测试、Evals
- 规则文件、Skills
- 沙箱、Hook
- 可观测性和共享基础设施

### 更合理的经济指标

"每个被接受变更的综合成本"，而不是单次模型调用价格。

## 如何衡量 AI Native 转型是否成功

### 最危险的指标

代码行数、生成次数和 Pull Request 数量。它们奖励产量，却不代表价值。

### 四组有意义指标

#### 交付效率
- 从意图提出到验证通过的时间
- 从计划批准到 PR 合并的时间
- 部署频率
- 审批门等待时间
- 每名工程师可管理的并行工作量

#### 质量与可靠性
- 首次实现通过 CI 的比例
- 每次变更的返工轮次
- 严重问题在合并前被发现的比例
- 缺陷逃逸率
- 变更失败率与 MTTR

#### Agent 质量
- Eval 通过率及关键场景覆盖率
- 工具调用正确率
- 不必要调用和重复循环
- 人工纠正频率
- 生产事故进入回归集所需时间

#### 成本与治理
- 每个被接受变更的 Token 与基础设施成本
- 人工审查分钟数
- Agent 越权和门禁阻止次数
- 审计轨迹完整率
- 政策覆盖率与例外数量

## 企业应该从哪里开始？

### 第一阶段：建立一个可验证的工作流

- 选择范围清楚、风险较低但真实存在的任务（测试补充、文档更新、小型缺陷修复、依赖维护）
- 为代码库建立精简的规则文件
- 将构建、测试和 lint 封装成 Agent 可以直接运行的命令
- 记录 Agent 的执行轨迹、人工修改和失败原因
- Agent 只创建分支或 Pull Request，不直接修改主分支和生产环境

### 第二阶段：建立制品链与确定性边界

- 开始使用正式的意图、规格和计划制品
- 让 Agent 在实现前完成代码库分析和计划
- 将反复出现的组织知识封装为 Skills
- 对不可违反的安全和质量要求增加 Hooks、沙箱、CI 门禁、分支保护和最小权限
- 引入独立验证会话或审查 Agent

### 第三阶段：形成持续评估和生产反馈

- 建立初始 Eval 数据集
- 在模型、Prompt、Skill 和工具变化时执行回归评估
- 将真实生产事故转化为测试案例和 Eval
- 允许 Agent 进行只读运维分析、日志关联和低风险修复建议
- 为开发、测试、预发布和生产设置不同的自治等级

### 第四阶段：运行受控的闭环

- 生产事件可以自动触发 Agent 进行诊断，生成新的意图或修复 PR
- 但闭环不等于无条件自治
- 高风险操作仍应通过确定性检查、独立评审和明确的人类授权

### 组织应当始终能够回答的问题

1. Agent 做了什么？
2. 它为什么这样做？
3. 使用了哪些数据和工具？
4. 哪些证据证明结果可以接受？
5. 谁或哪条政策授权了关键行动？
6. 失败后的影响范围是否受控？
7. 同类失败是否已经进入下一轮改进？

如果这些问题无法回答，继续扩大 Agent 权限只会放大不确定性。

---

## 结语：生成不再稀缺，判断才是

AI Native SDLC 揭示的，并不是一个"AI 替代程序员"的简单未来。

**真正揭示的是**：真正决定软件质量的，从来不仅是代码本身，而是代码之前的意图、代码周围的约束、代码之后的验证，以及组织是否愿意为最终结果负责。

当代码生成变得充裕，验证、判断和方向就成为新的稀缺资源。

**未来最有竞争力的团队**，不一定是拥有最多 Agent、生成最多代码的团队，而是最早学会把组织知识变成可执行上下文，把质量标准变成自动反馈，把安全政策变成技术边界，并把人类注意力集中到真正需要判断的地方的团队。

**成熟度的真正分界线**：当 Agent 出错时，团队能否及时发现错误、限制影响、解释原因，并确保同类错误不再发生。

- 如果不能 = 仍然只是速度更快的 vibe coding
- 如果能够 = 真正开始走向 agentic engineering，以及完整意义上的 AI Native SDLC
