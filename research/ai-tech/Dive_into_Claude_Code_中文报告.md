## 摘要

Claude Code 是一款 Agent 驱动的编码工具，能够代表用户运行 Shell 命令、编辑文件和调用外部服务。本研究通过分析其公开可用的 TypeScript 源代码，全面描述其架构，并与 OpenClaw 进行对比——后者是一个独立的开源 AI Agent 系统，从不同部署场景出发回答了相同的设计问题。我们的分析识别出驱动架构的 **五项人类价值、理念与需求**（人类决策权、安全与保障、可靠执行、能力增强、情境适应性），并通过 **十三项设计原则** 将其追溯到具体实现选择。系统的核心是一个简单的 while 循环：调用模型、运行工具、重复执行。然而，大部分代码生活在这个循环周围的系统中：包含七种模式和基于 ML 分类器的权限系统、用于上下文管理的五层压缩管道、四种扩展机制（MCP、插件、Skills 和 Hooks）、子 Agent 委托与编排机制，以及面向追加的会话存储。与 OpenClaw（多渠道个人助手网关）的比较表明，当部署场景改变时，相同的设计问题会产生不同的架构答案：从单动作安全评估到周边级访问控制，从单一 CLI 循环到网关控制平面内的嵌入式运行时，从上下文窗口扩展到网关范围的能力注册。最后，我们识别出未来 Agent 系统的 **六个开放设计方向**，基于最新的实证、架构和政策文献。

## 1 引言

AI 辅助软件开发已从 GitHub Copilot（Chen et al., 2021）等自动补全风格工具，经过 Cursor（Cursor, 2026）等 IDE 集成助手，发展到能够自主规划多步修改、执行 Shell 命令、读写文件并迭代自身输出的完全 Agent 化系统。Claude Code（Anthropic, 2026a）是由 Anthropic（Anthropic, 2026c）发布的 Agent 驱动的编码工具。

其官方文档描述了一个"Agent 循环"，该循环规划和执行动作以实现目标，可以调用工具、评估结果并继续直到任务完成¹。这一从建议到自主行动的转变引入了在基于补全的工具中没有任何对应的架构需求。这些需求定义了一个设计空间——一组跨越安全、上下文管理、扩展性和委托等主题的反复出现的问题，每个编码 Agent 都必须应对。本研究使用源代码级分析来展示一个生产系统如何回答这些问题。

尽管采用率不断增长，但 Anthropic 发布的 Claude Code 用户文档并不包含详细的架构描述。本研究使用源代码分析来描述架构设计决策。Anthropic 对 132 名工程师和研究人员的内部调查（Huang et al., 2025）报告称，约 27% 的 Claude Code 辅助任务是本来不会在沒有该工具的情况下尝试的工作，表明该架构实现的是质上的新工作流程，而非仅仅加速现有流程。

¹ https://code.claude.com/docs/en/how-claude-code-works.

## 2 设计哲学、设计原则与架构动机

生产级编码智能体是由人类构建、为人类服务的，其架构决策反映了构建者所认为重要的东西。本节识别了驱动 Claude Code 设计的人类价值观，追踪它们通过反复出现的设计原则，并构建了组织第 3 至第 9 节分析的设计空间问题框架。

Anthropic 的安全智能体框架阐述了一个核心张力："智能体必须能够自主工作；它们的独立运作正是其价值所在。但人类应该保留对目标追求方式的控制权"（Anthropic, 2025a）。Claude 的宪章通过培养"可应用于具体情境的良好判断力和正确价值观"（Anthropic, 2026b）来解决这一问题，而非通过僵化的决策程序。这些承诺，结合关于开发者实际使用该工具的经验发现（Huang et al., 2025; McCain et al., 2026），指向了塑造架构的五个人类价值观。

### 2.1 五大价值观与哲学

**人类决策权威。** 人类保留对系统所做事情的最终决策权威，通过一个权力层级结构（Anthropic，然后是操作员，然后是用户）来明确谁对什么拥有权威（Anthropic, 2026b）。系统的设计使得人类能够行使知情控制权：他们可以实时观察操作、批准或拒绝提议的操作、中断兼容的进行中操作，以及事后审计。当 Anthropic 发现用户批准了 93% 的权限提示（Hughes, 2026）时，回应不是添加更多警告，而是重新构建问题：在定义的边界内（沙箱、自动模式分类器）智能体可以自由工作，而不是用户一旦习惯就停止审查的逐操作批准（Dworken and Weller-Davies, 2025）。

**安全、安保与隐私。** 系统保护人类及其代码、数据和基础设施免受伤害，即使人类疏忽或犯错时亦然。这与人类决策权威不同：权威关乎人类选择的能力，而安全则关乎系统即使在该能力丧失时也要保护的义务。Anthropic 的安全智能体框架分别将保护智能体交互安全和在扩展交互中保护隐私作为核心承诺（Anthropic, 2025a）。自动模式威胁模型（Hughes, 2026）明确针对四类风险：过度急切的行为、无意的错误、提示注入和模型错位。

**可靠执行。** 智能体做人类真正想要的事情，保持跨时间的连贯性，并在宣布成功前支持验证其工作。这一价值观跨越单轮正确性（它是否忠实地解读了请求？）和长期可靠性（它在上下文窗口边界、会话恢复和多智能体委托中是否保持连贯？）。Anthropic 的产品文档（Anthropic, 2026d）描述了一个智能体重复直到任务完成的三阶段循环：收集上下文、执行操作、验证结果。智能体设计指导（Schluntz and Zhang, 2024）进一步强调每一步都要从环境的"ground truth"评估进度。安全带设计指导（Rajasekaran, 2026）同样指出"智能体倾向于自信地赞扬工作"，即使质量一般，这促使了生成与评估的分离。

**能力增强。** 系统在每单位努力和成本上实质性地增加人类能够完成的事情。Anthropic 的内部调查（Huang et al., 2025），在第 1 节中讨论，表明架构启用的是质上的新工作流程，而非仅仅是加速现有流程：约 27% 的任务代表了本来不会被尝试的工作。系统的创建者将其描述为"一个 Unix 工具而非传统产品"，由最小的构建块组成，这些构建块"有用、可理解且可扩展"（Cherny and Wu, 2025）。架构投资于确定性基础设施（上下文管理、工具路由、恢复）而非决策脚手架（显式规划器或状态图），前提是越来越强大的模型从一个丰富的操作环境中获益更多，而非从限制其选择的框架中获益。

**情境适应性。** 系统适应用户的特定情境（他们的项目、工具、惯例和技能水平），并且这种关系随时间改善。扩展架构（CLAUDE.md、skills、MCP、hooks、plugins）在不同上下文成本层级提供可配置性（第 6 和 7 节）。纵向数据（McCain et al., 2026）显示人类-智能体关系会演变：自动批准率从少于 50 个会话时的约 20% 增长到 750 个会话时的超过 40%。这种被描述为由模型、用户和产品"共同构建"的自主性模式，意味着系统为信任轨迹而非固定信任状态而设计。MCP 向 Linux 基金会的智能体 AI 基础基金会（The Linux Foundation, 2025）的捐赠反映了这个价值观的生态系统维度。

### 2.2 设计原则

这些价值观通过十三个设计原则来操作化，每个原则都回答了生产级编码智能体必须解决的一个反复出现的问题。表 1 总结了这些原则；后续章节（第 3-9 节）追踪每个原则的具体实现选择。

这些原则可以对照三个主要的替代设计家族来理解。首先，基于规则的编排：LangGraph（LangChain, Inc., 2024）等框架将决策逻辑编码为带有类型边的显式状态图，选择脚手架而非最小安全带。其次，容器隔离执行：SWE-Agent 和 OpenHands（Yang et al., 2024; Wang et al., 2024b）依赖 Docker 隔离而非分层策略执行。第三，作为安全机制版本控制：像 Aider（Gauthier, 2024）这样的工具使用 Git 回滚作为主要安全网，而非优先拒绝评估。Claude Code 的原则集与众不同之处在于结合了最小决策脚手架与分层策略执行、基于价值观的判断与优先拒绝默认值，以及渐进上下文管理与可组合扩展性。

### 2.3 从价值观到架构

每个价值观通过其原则追踪到具体的架构决策：

**人类决策权威** 促使优先拒绝评估、渐变信任谱系、仅追加状态（可审计历史）、外部化可编程策略，以及价值观优于规则（第 5 至 7 节和第 9 节）。

**安全、安保与隐私** 促使纵深防御、优先拒绝默认值、可逆性加权评估、外部化策略，以及隔离的子智能体边界（第 5 和 8 节）。

**可靠执行** 促使上下文作为稀缺资源、仅追加持久状态、优雅恢复、隔离的子智能体边界，以及纵深防御（第 4 和 7 至 9 节）。

**能力增强** 促使最小脚手架、可组合扩展性、可逆性加权风险、上下文管理，以及优雅恢复（第 4 至 6 节）。

**情境适应性** 促使透明基于文件的记忆、可组合扩展性、渐变信任谱系，以及外部化可编程策略（第 5 至 7 节）。

这些映射也揭示了架构不做什么：它不向模型的推理施加显式规划图，不提供单一统一扩展机制，也不跨恢复点恢复所有与会话相关的信任相关状态。这些缺席与上述原则集一致。

### 2.4 评估视角：长期能力保持

上述五个价值观描述了架构被设计来服务的对象。本文还应用了第六个关注点——架构是否保持长期人类能力——作为评估视角。这一关注点是真实的：Anthropic自己对 132 名工程师和研究人员的调查（Huang et al., 2025）记录了一个"监督悖论"，其中过度依赖 AI 可能导致监督它所需的技能萎缩，而独立研究（Shen and Tamkin, 2026）发现 AI 辅助条件下的开发者在理解测试中得分低 17%。然而，这一关注点并未在架构或 Anthropic 声明的设计价值观中作为主要驱动力得到显著反映。因此，我们将其不是作为平等价值观而是作为横切关注点来处理：在第 11 节中对所有五个价值观应用这个问题，询问短期增强是否以长期人类理解、代码库一致性和开发者pipeline为代价。

## 3 架构概述

构建生产级编码智能体需要回答几个反复出现的设计问题：推理应该在哪里运行、需要多少个执行引擎、采用什么安全姿态，以及将什么资源作为约束性限制。Claude Code 的架构可以被解读为对这些问题的其中一套答案。在实现层面，系统有七个组件，通过主数据流连接：用户通过多个接口之一提交提示，进入共享的智能体循环。智能体循环组装上下文、调用 Claude 模型、接收可能包含工具使用请求的响应、通过权限系统路由这些请求，并将批准的操作分派给与执行环境交互的具体工具。在此过程中，状态和持久化机制记录对话记录、管理会话身份，并支持恢复、分叉和回滚操作。

### 3.1 设计问题与运行示例

描述围绕四个在生产级编码智能体中反复出现的设计问题组织，每个问题都将一个或多个表 1 中识别的设计原则具体化。每个问题在此处介绍，包括 Claude Code 的答案、可能的替代方案说明，然后通过第 4 至 9 节逐步演示。

**推理应该在哪里运行？** 在 Claude Code 中，模型推理要做什么；安全带负责执行操作。模型在其响应中作为 tool_use 块发出工具使用请求，安全带解析这些请求、检查权限、将它们分派给工具实现，并收集结果（query.ts）。模型从不直接访问文件系统、运行 shell 命令或发出网络请求。这种分离有一个安全后果：因为推理和执行占据不同的代码路径，被攻陷或被对抗性操纵的模型无法覆盖安全带中实现的沙箱、权限检查或优先拒绝规则。模型与外部世界的唯一接口是通过结构化的 tool_use 协议，安全带在执行前验证该协议。社区对提取源代码的分析估计，Claude Code 代码库中只有约 1.6% 构成 AI 决策逻辑，其余 98.4% 是操作基础设施，这一比例说明了核心智能体推理层有多薄。替代设计在脚手架端推理上投入更多：Devin 维护显式规划和任务跟踪结构，而 LangGraph（LangChain, Inc., 2024）通过开发者定义的状态图路由控制流。

**需要多少个执行引擎？** Claude Code 使用一个单一的 queryLoop() 函数来执行，无论用户是通过交互式终端、无头 CLI 调用、Agent SDK 还是 IDE 集成进行交互（query.ts）。只有渲染和用户交互层有所不同。其他系统使用模式特定的引擎：例如，IDE 集成可能遵循与 CLI 工具不同的代码路径，以表面特定优化换取统一性。

**默认安全姿态是什么？** Claude Code 的默认安全姿态是优先拒绝加人类升级：拒绝规则覆盖询问规则覆盖允许规则，未识别操作升级给用户而非静默允许（permissions.ts）。多个独立安全层（权限规则、PreToolUse 钩子、启用时的自动模式分类器以及可选的 shell 沙箱）并行应用，因此任何一个都可以阻止操作（第 5 节）。这结合了表 1 中的优先拒绝加人类升级和纵深防御与分层机制原则。替代方法将信任边界转移到其他地方：SWE-Agent 和 OpenHands（Yang et al., 2024; Wang et al., 2024b）依赖基于容器的隔离来包含任意执行，而 Aider（Gauthier, 2024）使用基于 git 的回滚作为主要安全网。

**什么是约束性资源约束？** 在 Claude Code 中，上下文窗口（旧型号为 200K，Claude 4.6 系列为 1M）是约束性资源。在每次模型调用之前执行五种不同的上下文减少策略（query.ts），还有其他几个子系统决策（延迟加载指令、延迟工具模式、仅摘要子智能体返回）存在以限制上下文消耗（第 7 节）。五层管道存在是因为没有单一压缩策略能解决所有类型的上下文压力。预算减少针对溢出大小限制的单个工具输出。Snip 处理时间深度。Microcompact 对缓存开销做出反应。Context collapse 管理非常长的历史记录。Auto-compact 作为最后手段执行语义压缩。每个层在不同的成本效益权衡下运作，较早、较便宜的层在较昂贵的层之前运行。替代架构将其他资源作为主要瓶颈，例如计算预算（限制模型调用或工具调用的数量）或工作内存（维护显式草稿板而非依赖对话历史）。

**运行示例。** 为了使这些原则具体化，我们将一个单一任务贯穿第 3 至 9 节："修复 auth.test.ts 中失败的测试"。在本节中，用户通过 Claude Code 的接口之一提交提示。后续章节追踪请求通过查询循环、权限门、工具池、上下文窗口、子智能体委托和会话持久化。

### 3.2 高层系统结构

七组件模型（图 1）直接映射到源文件：

1. **用户**：提交提示、批准权限、审查输出。
2. **接口**：交互式 CLI、无头 CLI（claude -p）、Agent SDK 和 IDE/桌面/浏览器。所有表面都馈入相同的循环。
3. **智能体循环**：模型调用、工具分派和结果收集的迭代循环，实现为 query.ts 中的 queryLoop() 异步生成器。
4. **权限系统**：优先拒绝规则评估（permissions.ts）、自动模式 ML 分类器，以及基于钩子的拦截（types/hooks.ts）。
5. **工具**：最多 54 个内置工具（19 个无条件的，35 个有条件地基于功能标志和用户类型），通过 assembleToolPool() 组装（tools.ts），与 MCP 提供的工具合并。插件通过 MCP 服务器和 skill/命令注册表间接贡献。
6. **状态与持久化**：主要是仅追加的 JSONL 会话记录（sessionStorage.ts）、全局提示历史（history.ts）和子智能体侧链文件。
7. **执行环境**：带有可选沙箱的 shell 执行（shouldUseSandbox.ts）、文件系统操作、网络获取、MCP 服务器连接和远程执行。

数据流遵循从左到右的主干：用户通过接口提交请求，进入智能体循环。循环向权限系统提议操作；批准的操作到达工具，工具与执行环境交互并将 tool_result 消息返回循环。状态和持久化位于循环旁边，记录记录并加载先前的会话数据。

应用程序入口点 main() 在 main.tsx 中初始化安全设置（包括 NoDefaultCurrentDirectoryInExePath 以防止 Windows PATH 劫持）、注册信号处理器以实现优雅关闭，并分派到适当的执行模式。

### 3.3 分层子系统分解

五层分解（图 3）将七组件模型扩展为更细粒度的视图，将每层映射到特定的源目录。

**表面层（入口点和渲染）。** src/entrypoints/ 目录包含启动路径，包括带有 coreTypes.ts、controlSchemas.ts 和 coreSchemas.ts 的 SDK 入口。src/screens/ 目录组合全屏布局，src/components/ 通过 ink 框架提供终端 UI 构建块。交互式 CLI 启动带有实时流、权限对话框和进度指示器的终端 UI。无头 CLI（claude -p）创建一个 QueryEngine 实例用于单次处理。Agent SDK 通过异步生成器发出类型化事件。

**核心层（智能体循环、压缩管道）。** queryLoop() 异步生成器（query.ts）实现迭代智能体循环，消费来自状态层的组装上下文并将工具请求分派到安全/动作层。在每次模型调用之前，五层顺序压缩器（query.ts:365–453）管理上下文压力：预算减少、snip、microcompact、context collapse 和 auto-compact（第 4.3 和 7.3 节）。

**安全/动作层（权限系统、钩子、扩展性、工具、沙箱、子智能体）。** 权限系统（permissions.ts）实现优先拒绝规则评估，最多有七种权限模式（如果也计算内部专用 bubble 和功能门控 auto）（types/permissions.ts），以及一个集成自动模式 ML 分类器（yoloClassifier.ts），提供两阶段快速过滤和工具安全的链式思维评估（第 5 节）。跨越 27 种事件类型的钩子管道（coreTypes.ts；types/hooks.ts 中的输出模式）可以阻止、重写或注释工具请求；其中 5 个与安全相关，而其余 22 个用于生命周期和编排目的（第 6 节）。扩展性子系统允许插件和技能向运行时注册工具和钩子。通过 assembleToolPool()（tools.ts）的工具池组装合并内置工具和 MCP 提供的工具。批准的 shell 命令通过限制文件系统和网络访问的 shell 沙箱（shouldUseSandbox.ts），独立于权限系统。通过 AgentTool（AgentTool.tsx, runAgent.ts）的子智能体生成通过与所有其他工具相同的 buildTool() 工厂分派，使用隔离的上下文窗口重新进入 queryLoop() 并仅向父级返回一个摘要（第 8 节）。

**状态层（上下文组装、运行时状态、持久化、记忆、侧链）。** 上下文组装是一个记忆化状态加载器，而非路由中枢：getSystemContext()（context.ts）计算会话级系统上下文包括 git 状态，getUserContext()（context.ts）加载 CLAUDE.md 层级和当前日期。两者都被缓存以供重用：系统上下文被附加到系统提示，而用户上下文作为用户上下文消息添加。src/state/ 目录管理运行时应用程序状态。会话记录作为主要仅追加的 JSONL 文件存储在项目特定路径（sessionStorage.ts）。CLAUDE.md + 记忆子系统提供四级指令层级（claudemd.ts），从托管设置到目录特定文件，加上 Claude 在对话期间写入的自动记忆条目（第 7.2 节）。侧链记录（sessionStorage.ts:247）将每个子智能体的对话存储在单独的文件中，防止子智能体内容膨胀父上下文（第 8.3 节）。全局提示历史记录在 history.jsonl（history.ts）中维护。恢复和分叉操作从记录重建会话状态（conversationRecovery.ts）。

**后端层（执行后端、外部资源）。** 通过可选沙箱（BashTool.tsx, PowerShellTool.tsx）的 shell 命令执行、远程执行支持（src/remote/）、跨多种传输变体包括 stdio、SSE、HTTP、WebSocket、SDK 和 IDE 特定适配器的 MCP 服务器连接（services/mcp/client.ts），以及 src/tools/ 中的 42 个工具子目录实现具体工具逻辑。

### 3.4 QueryEngine：一个澄清

QueryEngine.ts 的类文档指出："QueryEngine 拥有对话的查询生命周期和会话状态。它将 ask() 的核心逻辑提取为一个可独立使用的类，可被无头/SDK 路径和（在未来阶段）REPL 使用。" 该类是非交互式表面的对话包装器，而非引擎本身。它的构造函数接受一个 QueryEngineConfig，包括初始消息、中止控制器、文件状态缓存和其他每对话状态。它的 submitMessage() 方法是一个异步生成器，协调单个回合。共享查询路径位于 query()（query.ts）中，它包装一个内部 queryLoop()；QueryEngine 委托给 query()。

这种区别在架构上很重要：交互式 CLI 也调用 query()，完全绕过 QueryEngine。共享代码路径是循环函数，而非引擎类。

### 3.5 权限和安全层

默认安全原则通过七个独立层实现。请求必须通过所有适用层，任何单一层都可以阻止它：

1. **工具预过滤**（tools.ts）：在任意调用之前将空白拒绝的工具从模型的视图中移除，防止模型尝试调用它们。
2. **优先拒绝规则评估**（permissions.ts）：拒绝规则始终优先于允许规则，即使允许规则更具体。
3. **权限模式约束**（types/permissions.ts）：活动模式决定匹配无显式规则的请求的基线处理。
4. **自动模式分类器**：当启用时，基于 ML 的分类器评估工具安全性，可能拒绝规则系统会允许的请求。
5. **Shell 沙箱**（shouldUseSandbox.ts）：批准的 shell 命令可能仍在限制文件系统和网络访问的沙箱内执行。
6. **恢复时不还原权限**（conversationRecovery.ts）：会话范围的权限在恢复或分叉时不还原。
7. **基于钩子的拦截**（types/hooks.ts）：PreToolUse 钩子可以修改权限决策；PermissionRequest 钩子可以与用户对话框并行异步解决决策（或者在协作模式下，在它之前解决）。

这些层在第 5 节中有详细描述。

## 6 扩展性：MCP、插件、Skills 与钩子

编码智能体的一个反复出现的设计问题是如何构建扩展表面：单一统一机制、少量专业化机制，还是具有不同上下文成本的分层堆栈。这里的分析说明了表 1 中的两个设计原则：可组合多机制扩展性和外部化可编程策略。回到运行示例，当 Claude 尝试修复 auth.test.ts 且之前的 npm test 请求已由权限系统调解（第 5 节）时，下一个问题是什么扩展启用的操作表面可用于该修复。当 Claude Code 中一个回合开始时，模型看到的不仅是内置工具如 BashTool 和 FileReadTool，还有来自 MCP 服务器的数据库查询工具、来自 .claude/skills/ 的自定义 lint skill，以及来自已安装插件贡献的工具。这些通过四个机制在智能体循环的不同点扩展：MCP 服务器提供外部工具集成，插件打包和分发组件 bundle，skills 注入领域特定指令，钩子拦截工具执行生命周期。Anthropic 的文档（Anthropic, 2026d）提出了更广泛的视图，将 CLAUDE.md（第 7 节）和子智能体（第 8 节）以及此处分析的四个机制并列。我们将 CLAUDE.md 和子智能体放在各自的章节中，因为它们在不同的子系统中运作（分别是上下文构建和委托），但上下文成本排序具有架构意义：它揭示了每个扩展点如何在表达力与有界上下文窗口之间进行权衡。

### 6.1 四种扩展机制

这些机制在不同的源目录中实现（图 5），并服务于不同的集成模式：

**MCP 服务器。** 模型上下文协议是主要的外部工具集成路径。MCP 服务器从多个范围配置：项目、用户、本地和企业，运行时还会合并额外的插件和 claude.ai 服务器（services/mcp/config.ts）。MCP 客户端（services/mcp/client.ts）支持多种传输类型：stdio、SSE、HTTP、WebSocket、SDK，加上 IDE 特定变体（sse-ide、ws-ide）和内部 claudeai-proxy。每个连接的服务器贡献作为 MCPTool 对象的工具定义。专用的内置工具 ListMcpResourcesTool 和 ReadMcpResourceTool 提供对 MCP 资源的访问。

**插件。** 插件具有双重角色：它们既是打包格式也是分发机制。PluginManifestSchema（utils/plugins/schemas.ts）接受十种组件类型：命令、智能体、skills、钩子、MCP 服务器、LSP 服务器、输出样式、通道、设置和用户配置。插件加载器（utils/plugins/pluginLoader.ts）验证清单并将每个组件路由到各自的注册表：命令和 skills 通过 SkillTool 元工具暴露，智能体出现在 AgentTool 消耗的定义中，钩子合并到钩子注册表中，MCP 和 LSP 服务器折叠到其标准配置中，输出样式修改响应格式。因此，单个插件包可以同时跨多个组件类型扩展 Claude Code，使插件成为第三方扩展的主要分发载体。

**Skills。** 每个 skill 由带有 YAML frontmatter 的 SKILL.md 文件定义。parseSkillFrontmatterFields() 函数（loadSkillsDir.ts）解析 15+ 个字段，包括显示名称、描述、允许的工具（授予 skill 访问额外工具的权限）、参数提示、模型覆盖、执行上下文（'fork' 用于隔离执行）、关联的智能体定义、工作量级别和 shell 配置。Skills 可以定义自己的钩子，这些钩子在调用时动态注册。捆绑的 skills 在启动时在内存中注册。当调用时，SkillTool 元工具将 skill 的指令注入上下文。

**钩子。** 源代码定义了 27 种钩子事件，跨越工具授权（PreToolUse、PostToolUse、PostToolUseFailure、PermissionRequest、PermissionDenied）、会话生命周期（SessionStart、SessionEnd、Setup、Stop、StopFailure）、用户交互（UserPromptSubmit、Elicitation、ElicitationResult）、子智能体协调（SubagentStart、SubagentStop、TeammateIdle、TaskCreated、TaskCompleted）、上下文管理（PreCompact、PostCompact、InstructionsLoaded、ConfigChange）、工作区事件（CwdChanged、FileChanged、WorktreeCreate、WorktreeRemove）和通知（coreTypes.ts、coreSchemas.ts）。其中，15 个具有事件特定的输出模式，具有丰富的字段，支持权限决策、上下文注入、输入修改、MCP 结果转换和重试控制（types/hooks.ts）。通过设置和插件配置的持久化钩子命令使用四种命令类型：shell 命令（type: command）、LLM 提示钩子（type: prompt）、HTTP 钩子（type: http）和智能体验证器钩子（type: agent）（schemas/hooks.ts）。运行时还支持非持久化回调钩子（type: callback），供 SDK 和内部仪表化使用（types/hooks.ts）。钩子来源包括启动时的 settings.json、插件和托管策略；skill 钩子在调用时动态注册（utils/hooks.ts）。五个工具授权事件在第 5.3 节中详述。

### 6.2 工具池组装

tools.ts 中的 assembleToolPool() 函数被记录为"合并内置工具和 MCP 工具的单一真实来源"。组装遵循五步管道：

1. **基础工具枚举。** getAllBaseTools()（tools.ts）返回最多 54 个工具的数组：19 个始终包含（如 BashTool、FileReadTool、AgentTool、SkillTool），还有 35 个根据功能标志、环境变量和用户类型有条件地包含。Anthropic 内部用户获得额外的内部工具。Worktree 模式启用 EnterWorktreeTool 和 ExitWorktreeTool。智能体群体启用团队工具。当 Bun 二进制文件中嵌入搜索工具可用时，专用 GlobTool 和 GrepTool 被省略。

2. **模式过滤。** getTools()（tools.ts）应用模式特定过滤。在 CLAUDE_CODE_SIMPLE 模式下，只有 Bash、Read 和 Edit 可用（或者在 REPL 分支中的 REPLTool；加上适用的协调器工具）。每个工具的 isEnabled() 方法被调用以进行运行时可用性检查。

3. **拒绝规则预过滤。** filterToolsByDenyRules()（tools.ts）在任何调用之前将空白拒绝的工具从模型的视图中移除。

4. **MCP 工具集成。** 来自 appState.mcp.tools 的 MCP 工具通过拒绝规则过滤并与内置工具合并。

5. **去重。** 工具按名称去重，内置工具优先于 MCP 工具。

REPL.tsx（通过 useMergedTools 钩子）和 AgentTool.tsx（构建工作线程工具集时）都调用此函数，确保所有执行路径的一致组装。在请求时，延迟工具可能对模型的上下文隐藏，直到通过 ToolSearch 显式查询（tools.ts）。

基于智能体的扩展（通过 .claude/agents/*.md 的自定义智能体定义和插件贡献的智能体）在第 8 节中介绍，因为智能体与上述四种机制有根本不同：它们创建新的隔离上下文窗口，而非扩展当前上下文。

### 6.3 为什么是四种机制？

鉴于每个额外的扩展机制都会增加开发者必须学习的外围面积，一个自然的问题是为什么 Claude Code 使用四种不同机制而非合并为一或两种。答案在于观察到不同类型的扩展性对上下文窗口施加不同的成本，单一机制无法覆盖从零上下文生命周期钩子到模式密集型工具服务器的完整范围，而不会对扩展作者强制执行不必要的权衡。

如表 2 所总结，每种机制以部署复杂度换取不同类型的扩展性。MCP 服务器提供运行时工具集成（模型获得新的可调用工具），代价是服务器管理开销和工具模式消耗的上下文预算。Skills 以最低上下文成本塑造智能体的思维方式（而不仅仅是它拥有什么工具），因为只有 frontmatter 描述（而非完整内容）留在提示中。钩子提供跨切面的生命周期控制（阻止、重写或注释工具调用），默认情况下没有上下文占用，尽管钩子可以选择注入额外上下文。插件将其他三种的任意组合打包成可分发包，作为打包和分发层而非不同的运行时原语。渐变上下文成本排序（钩子为零，skills 为低，插件为中等，MCP 为高）意味着廉价扩展可以广泛扩展而不耗尽上下文窗口，而昂贵的扩展则保留用于真正需要新工具表面的情况。

一些智能体框架提供单一扩展机制，通常是工具专用 API，所有自定义都作为额外的可调用工具到达。其他使用两层，将工具与配置或指令注入分离。Claude Code 的四种机制方法可以容纳更广泛的扩展模式，从零上下文事件处理器到完整外部服务集成，但增加了开发者在决定对于给定集成任务使用哪种机制时面临的学习曲线。

**表 2 每种扩展机制独特提供的内容。上下文成本指的是机制活跃时消耗的有界上下文窗口的比例。**

| 机制 | 独特能力 | 上下文成本 | 插入点 |
|---|---|---|---|
| MCP 服务器 | 外部服务集成（多传输） | 高（工具模式） | model()：工具池 |
| 插件 | 多组件打包+分发 | 中等（各异） | 全部三个点 |
| Skills | 领域特定指令+元工具调用 | 低（仅描述） | assemble()：上下文注入 |
| 钩子 | 生命周期拦截+事件驱动自动化 | 默认零 | execute()：pre/post 工具 |

## 7 上下文构建与记忆

智能体如何管理其上下文窗口并持久化用户指令是一个核心设计选择，不同系统在基于文件的透明度、数据库支持检索和不透明学习的表示之间进行选择。此处的设计选择实现了表 1 中的两个原则：上下文作为稀缺资源与渐进管理，以及透明基于文件的配置和记忆。

至此，运行示例中的任务已累积了状态：原始请求、npm test 权限结果、第 6 节中组装的工具池，以及到目前为止收集的任何文件读取或命令输出。本节询问这些不断增长的状态如何在下次模型调用之前打包到 Claude Code 的有界上下文窗口中。

在调用模型之前，智能体循环从工具池（第 6 节）、CLAUDE.md 文件、自动记忆和对话历史组装上下文窗口。以下小节涵盖组装顺序、CLAUDE.md 层级和多步压缩管道。

### 7.1 上下文窗口组装

上下文窗口（图 6）从以下来源组装，部分在初始组装时，部分在回合期间后期注入：

1. 系统提示，结合输出样式修改和任何 --append-system-prompt 标志内容。
2. 通过 getSystemContext()（context.ts）获取的环境信息：git 状态（在远程模式或禁用 git 指令时跳过）和可选的缓存破坏注入（由 BREAK_CACHE_COMMAND 门控）。每个会话记忆化一次。
3. 通过 getUserContext()（context.ts）获取的 CLAUDE.md 层级：四级指令文件层级（第 7.2 节）。也是记忆化的。
4. 路径范围规则：当智能体读取匹配目录中的文件时延迟加载的条件和目录匹配规则。
5. 自动记忆：异步预取的上下文相关记忆条目。
6. 工具元数据：skill 描述、MCP 工具名称和延迟的工具定义（通过 ToolSearch，按需）。
7. 对话历史：向前携带，受压缩约束。
8. 工具结果：文件读取、命令输出、子智能体摘要。
9. 压缩摘要：替换较旧的历史段。

### 7.2 CLAUDE.md 层级与自动记忆

一个设计原则塑造了记忆系统：存储的上下文应该可以被用户检查和编辑。CLAUDE.md 文件是纯文本 Markdown，而非结构化配置或 opaque 数据库条目。这种透明选择以表达力换取可审计性：用户可以读取、编辑、版本控制和删除智能体看到的任何指令（MindStudio Team, 2026）。替代记忆架构说明了这种权衡。检索增强方法使用基于嵌入的查找来呈现相关先前上下文，以可审计性为代价获得灵活性：用户不能轻易看到或编辑检索系统认为相关的内容。数据库支持的记忆提供结构化查询但需要额外基础设施且对版本控制不透明。Claude Code 的基于文件的方法使智能体看到的每条指令都可以直接读取、编辑和与代码库一起提交。该系统不使用嵌入或向量相似性索引进行记忆检索；相反，它使用 LLM 对记忆文件头部的扫描来按需选择最多五个相关文件，以文件粒度而非条目粒度呈现。基于嵌入的系统可以更精细地检索各个条目，代价是可审计性和维护索引所需的基础设施。

CLAUDE.md 文件遵循多级加载层级。源头部（claudemd.ts）定义了四种记忆类型：

1. **托管记忆**（例如 Linux 上的 /etc/claude-code/CLAUDE.md）：所有用户的 OS 级策略。
2. **用户记忆**（~/.claude/CLAUDE.md）：私人全局指令。
3. **项目记忆**（项目根目录中的 CLAUDE.md、.claude/CLAUDE.md 和 .claude/rules/*.md）：纳入代码库的指令。
4. **本地记忆**（项目根目录中的 CLAUDE.local.md）：gitignore 的，用于私人项目特定指令。

文件发现从当前目录向上遍历到根目录，在每个目录中检查所有项目和本地记忆文件。离当前目录更近的文件具有更高优先级（稍后加载）。

文件按"优先级逆序"加载：稍后加载的文件获得更多模型注意力。对于根到 CWD 目录，来自 .claude/rules/*.md 的无条件规则在启动时急切加载。对于 CWD 下方的嵌套目录，即使是无条件规则也会在智能体读取匹配目录中的文件时延迟加载。这意味着模型的指令集可以在对话期间随探索代码库的新部分而演变。

CLAUDE.md 内容作为用户上下文（一条用户消息）传递，而非系统提示内容（context.ts）。这个架构选择有一个重要含义：因为 CLAUDE.md 内容作为对话上下文而非系统级指令传递，模型对这些指令的遵守是概率性的而非保证的。以优先拒绝顺序评估的权限规则（第 5 节）提供确定性执行层。这在指导（CLAUDE.md，概率性）和执行（权限规则，确定性）之间创建了有意分离。该函数调用 setCachedClaudeMdContent() 来缓存加载的内容以供自动模式分类器使用，以避免 CLAUDE.md 加载器和权限系统之间的导入循环。

记忆文件支持 @include 指令用于模块化指令集（processMemoryFile() at claudemd.ts）。语法变体包括 @path、@./relative、@~/home 和 @/absolute。该指令仅在叶子文本节点中工作（不在代码块内）。在实现中，包含文件被首先推送，包含的文件在其后追加，通过跟踪处理的路径防止循环引用，不存在的文件被静默忽略。

### 7.3 压缩管道

五层压缩管道（第 4.3 节）通过渐变压缩实现"上下文作为瓶颈"原则（query.ts）。Claude Code 应用五层顺序压缩，而非单一策略，每层都有增加的攻击性（三个由功能标志门控；预算减少始终活跃，而 auto-compact 是用户可配置的）。这种渐变方法与更简单的替代方案形成对比：许多智能体框架使用单次截断（丢弃最旧的消息）或单次摘要步骤。渐变设计反映了一个惰性降级原则：首先应用最低破坏性压缩，仅在更便宜的策略证明不足时升级。这种方法的代价是复杂性。五个相互作用的压缩层，几个由功能标志门控，创造了对用户难以完全预测的行为。Auto-compact 在记录中产生可见摘要，microcompact 发出边界标记，但 context collapse 在用户可见输出下操作。更简单的单次方法牺牲信息但更容易推理。

1. **预算减少**（始终活跃）：每工具结果的大小限制。
2. **Snip**（HISTORY_SNIP）：轻量级较旧历史修整。
3. **Microcompact**（CACHED_MICROCOMPACT）：细粒度缓存感知压缩。
4. **上下文折叠**（CONTEXT_COLLAPSE）：历史读取时虚拟投影。
5. **Auto-compact**（默认启用，可禁用）：完整模型生成的摘要。

buildPostCompactMessages() 函数（compact.ts）返回以下压缩输出结构：[boundaryMarker, ...summaryMessages, ...messagesToKeep, ...attachments, ...hookResults]。边界标记通过 annotateBoundaryWithPreservedSegment() 注释了 preserved-segment 元数据，记录 headUuid、anchorUuid 和 tailUuid 以支持读取时链式修补。这种大部分仅追加的设计意味着压缩从不修改或删除先前写入的记录行；它仅追加新的边界和摘要事件。

## 4 回合执行：智能体查询循环

当用户提交"修复 auth.test.ts 中失败的测试"时，输入进入一个响应式循环，这是编码智能体几种可能的编排模式之一。本节考察 Claude Code 对简单 while-loop 架构的选择，并端到端地追踪该循环的一个回合，说明表 1 中的三个设计原则：最小脚手架与最大化操作安全带，上下文作为稀缺资源与渐进管理，以及优雅恢复与韧性。

### 4.1 查询管道

每个回合遵循固定序列（图 2，query.ts）：

1. **设置解析**。queryLoop() 函数解构不可变参数，包括系统提示、用户上下文、权限回调和模型配置。

2. **可变状态初始化**。单个 State 对象存储跨迭代的所有可变状态，包括消息、工具上下文、压缩跟踪和恢复计数器。循环的七个"继续点"各自通过整体对象赋值而非单独字段变更来覆盖此对象。

3. **上下文组装**。getMessagesAfterCompactBoundary() 函数从上次压缩边界向前检索消息，确保压缩内容由其摘要而非原始消息表示。

4. **模型前上下文塑形器**。五个塑形器顺序执行（第 4.3 节）。

5. **模型调用**。for await 循环遍历 deps.callModel() 以流式传输模型的响应，传递组装的消息（预先添加用户上下文）、完整系统提示、思维配置、可用工具集、中止信号、当前模型规范，以及包括快速模式设置、工作量值和备用模型在内的附加选项。

6. **工具使用分派**。如果响应包含 tool_use 块，它们流向工具编排层（第 4.2 节）。

7. **权限门**。每个工具请求通过权限系统（第 5 节）。

8. **工具执行和结果收集**。工具结果作为 tool_result 消息添加到对话中，循环继续。

9. **停止条件**。如果响应不包含 tool_use 块（仅文本），则回合完成。

queryLoop() 函数定义为 AsyncGenerator，在执行过程中产生 StreamEvent、RequestStartEvent、Message、TombstoneMessage 和 ToolUseSummaryMessage 事件。这种基于生成器的设计使得流式输出能够到达 UI 层，同时在循环内保持单一同步控制流。

Claude Code 的响应式循环遵循 ReAct 模式（Yao et al., 2022）：模型生成推理和工具调用，安全带执行操作，结果反馈到下一次迭代。替代编排模式包括显式基于图的路由（LangChain, Inc., 2024），其中控制流定义为带有类型边的状态机，以及树搜索方法（Zhou et al., 2023），在提交之前探索多个动作轨迹。Anthropic 自己的文档（Schluntz and Zhang, 2024）识别了五种可组合工作流模式（提示链、路由、并行化、编排器-工作者和评估器-优化器），其中 Claude Code 主要使用编排器-工作者模式进行子智能体委托（第 8 节），同时保持核心循环响应式。这种响应式设计以简单性和延迟换取搜索完整性：每个回合提交一个动作序列，无需回溯。

### 4.2 工具分派与流式执行

当模型响应包含 tool_use 块时，系统选择两个执行路径之一。主要路径使用 StreamingToolExecutor，它开始执行从模型响应流式传入的工具，减少多工具响应的延迟。回退路径使用 toolOrchestration.ts 中的 runTools()，它遍历 partitionToolCalls() 产生的分区。两条路径都将工具分类为并发安全或互斥。只读操作可以并行执行，而像 shell 命令这样的状态修改操作被串行化。

StreamingToolExecutor（StreamingToolExecutor.ts）通过两个协调机制管理并发执行：

- **兄弟中止控制器**。当任何 Bash 工具出错时触发，立即终止其他进行中的子进程，而非让它们运行完成。
- **进度可用信号**。当新输出准备好时唤醒 getRemainingResults() 消费者。结果被缓冲并按工具接收的顺序发出，因此即使工具并行运行，输出顺序也保持一致。这很重要，因为模型期望工具结果与其 tool-use 请求的顺序相同。这种并发读、串行写的执行模型位于完全串行分派和更积极的推测性方法（如 PASTE（Sui et al., 2026），它在模型仍在生成时推测性预执行预测的未来工具调用，通过推测隐藏工具延迟）之间的中间地带。

工具结果收集阶段遍历来自流式执行器或同步 runTools() 生成器的更新。每个更新可能携带工具结果、附件或进度事件。一个特殊检查检测 hook_stopped_continuation 附件：如果 PostToolUse 钩子信号该回合不应继续，则设置 shouldPreventContinuation 标志。结果通过 normalizeMessagesForAPI() 归一化以适应 Anthropic API，过滤后仅保留用户类型消息。

### 4.3 模型前上下文塑形器

五个上下文塑形器在每次模型调用之前在 query.ts 中顺序执行，每个操作 messagesForQuery 数组。五个塑形器按顺序运行，较早的步骤在较晚的步骤应用更广泛压缩之前执行较轻的缩减。

**预算减少**。（applyToolResultBudget()）。对工具结果执行每条消息大小限制，用内容引用替换超大数据输出。豁免工具（那些 maxResultSizeChars 非有限的工具）保留其完整输出。内容替换被持久化以用于智能体和会话查询源，以支持恢复时的重建。预算减少在 microcompact 之前运行，因为 microcompact 仅通过 tool_use_id 操作，从不检查内容；两者可以干净地组合。

**Snip**。（snipCompactIfNeeded()，由 HISTORY_SNIP 门控）。一种轻量级修剪，删除较旧的历史段，返回 {messages, tokensFreed, boundaryMessage}。snipTokensFreed 值被传递给 auto-compact，因为主令牌计数器从最近助手消息上的 usage 字段派生上下文大小，该消息以其 pre-snip input_tokens 仍然附加的方式存活 snip；因此除非显式传递，否则 snip 的节省对计数器不可见。

**Microcompact**。细粒度压缩，始终运行基于时间的路径，可选地运行缓存感知路径（由 CACHED_MICROCOMPACT 门控）。当缓存路径启用时，边界消息推迟到 API 响应之后，以便它们可以使用实际的 cache_deleted_input_tokens 而非估算。返回 {messages, compactionInfo}，其中 compactionInfo 可能包含 pendingCacheEdits。

**上下文折叠**。由 CONTEXT_COLLAPSE 门控。对话历史的读取时投影。源代码注释解释："不产生任何内容；折叠视图是对 REPL 完整历史的读取时投影。摘要消息存在于折叠存储中，而非 REPL 数组中。这使得折叠跨回合持久化。"与其他塑形器不同，上下文折叠不改变 REPL 存储的历史；它通过 applyCollapsesIfNeeded() 用投影视图替换 messagesForQuery 数组，因此模型看到折叠版本，而完整历史可用于重建。

**Auto-compact**。第五个塑形器，通过 compact.ts 中的 compactConversation() 触发完整模型生成的摘要。此函数执行 PreCompact 钩子，使用 getCompactPrompt() 创建摘要请求，并调用模型生成压缩摘要。结果馈入 buildPostCompactMessages()（compact.ts）。Auto-compact 仅在所有四个先前塑形器运行后上下文仍超过压力阈值时触发。

### 4.4 恢复机制

查询循环为边缘情况实现了多个恢复机制：

- **最大输出令牌升级**：当响应达到输出令牌上限时，系统可以使用升级的限制重试，受 GrowthBook 标志和不存在现有覆盖或环境变量上限的约束。每个回合最多允许三次恢复尝试（MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3）。
- **反应式压缩**（由 REACTIVE_COMPACT 门控）：当上下文接近容量时，反应式压缩仅汇总足够释放空间的最小内容。hasAttemptedReactiveCompact 标志确保每个回合最多触发一次。
- **提示过长处理**：如果 API 返回 prompt_too_long 错误，循环首先尝试上下文折叠溢出恢复和反应式压缩。只有在这些失败后，才以 reason:'prompt_too_long' 终止。
- **流式回退**：onStreamingFallback 回调处理流式 API 问题，允许循环使用不同策略重试。
- **备用模型**：fallbackModel 参数允许在主模型失败时切换到备用模型。

### 4.5 停止条件

多个条件可以终止循环：

1. **无工具使用**：模型仅产生文本内容（主要停止条件）。
2. **最大回合数**：达到可配置的 maxTurns 限制。
3. **上下文溢出**：API 返回 prompt_too_long。
4. **钩子干预**：PostToolUse 钩子设置 hook_stopped_continuation。
5. **显式中止**：abortController 信号触发。

回合管道决定工具请求如何编排和恢复。下一节检查决定每个请求是否允许执行的门。

## 5 工具授权与控制边界

生产级编码智能体采用不同的安全架构：分层策略执行、操作系统级沙箱或基于版本控制的回滚。Claude Code 结合了前两者，实现了表 1 中的四个设计原则：优先拒绝加人类升级、渐变信任谱系、纵深防御与分层机制，以及可逆性加权风险评估。

当 Claude 决定执行工具时（例如，通过 BashTool 运行 npm test 来重现 auth 测试失败），请求进入图 4 所示的权限管道。每个工具调用都通过权限系统，默认行为是拒绝或询问而非静默允许。这一默认行为受一个记录的行为模式驱动：Anthropic 的自动模式分析（Hughes, 2026）发现用户批准了约 93% 的权限提示，表明批准疲劳使交互式确认在行为上变得不可靠，成为唯一的安全机制。因为用户习惯性地不经过仔细审查就批准，系统必须独立于人类警惕性来保持安全。这驱动了对优先拒绝评估、全部拒绝预过滤和沙箱作为独立层的架构承诺，这些层无论用户是否注意都在运作。

### 5.1 权限模式与规则评估

七种权限模式存在于类型定义中（types/permissions.ts 中的 5 种外部模式；有条件添加的 auto；类型联合中的 bubble）：

1. **plan**：模型必须创建计划；仅在用户批准后执行。
2. **default**：标准交互使用。大多数操作需要用户批准。
3. **acceptEdits**：工作目录内的编辑和某些文件系统 shell 命令（mkdir、rmdir、touch、rm、mv、cp、sed）被自动批准；其他 shell 命令需要批准。
4. **auto**：基于 ML 的分类器评估不通过快速路径检查的请求（由 TRANSCRIPT_CLASSIFIER 门控）。
5. **dontAsk**：不提示，但仍执行拒绝规则。
6. **bypassPermissions**：跳过大多数权限提示，但安全关键检查和绕过免疫规则仍适用。
7. **bubble**：用于子智能体权限升级到父终端的内部专用模式。

五种外部可见模式（acceptEdits、bypassPermissions、default、dontAsk、plan）在 EXTERNAL_PERMISSION_MODES 数组中定义。auto 模式仅在 TRANSCRIPT_CLASSIFIER 功能标志激活时有条件地包含。bubble 模式存在于类型联合中但不在任一模式数组中；它用于子智能体权限升级的内部用途（第 8 节）。

权限规则按优先拒绝顺序评估（permissions.ts）。toolMatchesRule() 函数首先检查拒绝规则：拒绝规则始终优先于允许规则，即使允许规则更具体。广泛拒绝（"拒绝所有 shell 命令"）不能被窄泛允许（"允许 npm test"）覆盖。规则系统支持工具级匹配（按工具名称）和内容级匹配（匹配特定工具输入模式，如 Bash(prefix:npm)）。

七种模式跨越渐变自主权谱系，从 plan（用户在执行前批准所有计划）经过 default 和 acceptEdits 到 bypassPermissions（最小提示）。这一梯度反映了一个反复出现的设计张力：随着自主权增加，系统必须从交互式批准转向自动化安全检查。其他智能体系统以不同方式解决这一张力。SWE-Agent 和 OpenHands（Yang et al., 2024; Wang et al., 2024b）使用 Docker 容器隔离，将智能体的整个执行环境沙箱化，而非评估单个工具调用。Aider（Gauthier, 2024）依赖 Git 作为安全网，通过版本控制使所有更改可逆。Claude Code 的方法在可选容器沙箱之上分层多个策略执行机制，以简单性换取对单个动作的细粒度控制。

### 5.2 授权管道

完整授权管道按以下阶段执行：

**预过滤**。在任何工具请求到达运行时评估之前，filterToolsByDenyRules()（tools.ts）会在工具池组装时将全部拒绝的工具从模型的视图中完全移除。文档说明："使用与运行时权限检查相同的匹配器，因此像 mcp__server 这样的 MCP 服务器前缀规则会在模型看到之前就从该服务器移除所有工具。"这防止模型尝试调用被禁止的工具，从而避免浪费调用。

**PreToolUse 钩子**。注册的钩子作为权限管道的一部分触发。PreToolUse 钩子可以返回 permissionDecision（拒绝或询问）或 updatedInput（修改工具输入参数）（types/hooks.ts）。钩子允许不会绕过后续基于规则的拒绝或安全检查。在交互式路径中，用户对话框首先排队，钩子异步运行；协调器和类似的后台智能体路径在显示对话框之前等待自动化检查。

**规则评估**。优先拒绝规则引擎评估请求。MCP 工具通过其完全限定的 mcp__server__tool 名称匹配，服务器级规则匹配该服务器的所有工具。

**权限处理器**。useCanUseTool.tsx 中的处理器根据运行时上下文分支到四个路径之一：

1. **协调器**：用于多智能体协调模式。尝试自动化解决（分类器、钩子、规则）然后回退到用户交互。
2. **Swarm 工作器**：处理具有自己解决逻辑的多智能体 swarm 中的工作器智能体。
3. **推测分类器**：当 BASH_CLASSIFIER 启用且工具是 BashTool 时，推测分类器将预先启动的分类结果与超时竞争。如果分类器以高置信度返回，工具会立即被批准，无需用户交互。
4. **交互式**：后备路径。通过终端 UI 呈现标准用户批准对话框。

在协调器和某些后台路径中，自动化解决会在用户交互之前尝试。在标准交互路径中，对话框可以首先显示，而钩子或分类器检查继续并行运行。当分类器或拒绝规则阻止操作时，系统将拒绝视为路由信号而非硬性停止：模型收到拒绝原因，修改其方法，在下一次循环迭代中尝试更安全的替代方案。PermissionDenied 钩子事件（第 6 节）使外部代码能够以编程方式观察和响应这些拒绝。这种面向恢复的设计意味着权限执行塑造智能体的行为，而不仅仅是停止它。

### 5.3 自动模式分类器与钩子生命周期

自动模式分类器（yoloClassifier.ts）在启用时参与权限决策。当 TRANSCRIPT_CLASSIFIER 启用时，分类器加载三个提示资源：

- 一个基础系统提示。
- 一个外部权限模板。
- 对于 Anthropic 内部用户，一个单独的内部模板。

分类器根据对话记录和权限模板评估拟议的工具调用，产生允许、拒绝或请求人工批准。isUsingExternalPermissions() 函数检查 USER_TYPE 和 forceExternalPermissions 配置标志以选择适当的模板。

在源代码中定义的 27 个钩子事件（coreTypes.ts）中，有五个直接参与权限流程，每个都有特定的 Zod 验证输出模式（types/hooks.ts）：

- **PreToolUse**：可以返回 permissionDecision（拒绝或询问，但允许不会绕过后续检查）、permissionDecisionReason 和 updatedInput（修改参数）。
- **PostToolUse**：可以注入 additionalContext，对于 MCP 工具返回 updatedMCPToolOutput 以在结果进入上下文之前修改结果。
- **PostToolUseFailure**：可以为错误特定指导注入 additionalContext。
- **PermissionDenied**：可以在自动模式拒绝后提供重试指导。
- **PermissionRequest**：可以返回允许或拒绝的决定。在协调器和类似路径中，这可以在用户对话框之前解决。在标准交互路径中，它也可以与对话框一起运行。

对于非 MCP 工具，tool_result 在 PostToolUse 钩子触发之前发出。对于 MCP 工具，结果延迟到 post 钩子运行之后，使 updatedMCPToolOutput 能够生效。

### 5.4 Shell 沙箱

Shell 沙箱为 Bash 和 PowerShell 命令提供额外保护层（shouldUseSandbox.ts）。shouldUseSandbox() 函数检查沙箱是否全局启用、调用是否选择退出，以及命令是否匹配任何排除模式。

启用时，沙箱提供独立于应用程序级权限模型的文件系统和网络隔离。一个命令可以权限批准但仍然被沙箱化，或者权限拒绝且永远不会到达沙箱检查。这两个系统在不同轴上运作：授权与隔离。

分层安全架构基于独立性假设：如果某一层失败，其他层会捕获违规。然而，几个层共享常见的性能约束。安全研究人员（Adversa.ai, 2026）记录了包含超过 50 个子命令的命令会回退到单个通用批准提示，而不是运行每个子命令的拒绝规则检查，因为每个子命令解析导致 UI 冻结。此示例表明，当各层共享失败模式时，纵深防御可能会降级，这是安全与性能之间的结构性张力，在第 11.3 节进一步分析。

权限管道控制工具请求是否执行。下一节探讨是什么首先决定存在哪些工具：可扩展性架构，它组装模型的动作表面。

## 6 可扩展性：MCP、插件、技能和钩子

对于编码智能体，一个反复出现的设计问题是如何构建扩展表面：单一统一机制、少数量专用机制，还是具有不同上下文成本的分层堆栈。

这里的分析说明了表 1 中的两个设计原则：可组合多机制可扩展性和外部化可编程策略。回到运行示例，一旦 Claude 尝试修复 auth.test.ts，并且早期的 npm test 请求已由权限系统调解（第 5 节），下一个问题是修复可用的扩展启用动作表面。当在 Claude Code 中开始一轮对话时，模型看到的不仅是内置工具如 BashTool 和 FileReadTool，还有来自 MCP 服务器的数据库查询工具、来自 .claude/skills/ 的自定义 lint 技能，以及来自已安装插件贡献的工具。这些通过四种机制在不同循环点扩展智能体：MCP 服务器提供外部工具集成，插件打包和分发组件包，技能注入领域特定指令，钩子拦截工具执行生命周期。Anthropic 的文档（Anthropic, 2026d）呈现了更广阔的视角，包括 CLAUDE.md（第 7 节）和子智能体（第 8 节）以及这里分析的四机制。我们将 CLAUDE.md 和子智能体放在各自章节中，因为它们在不同的子系统中运作（上下文构建和委托），但上下文成本排序具有架构意义：它揭示了每个扩展点如何在表达性与有界上下文窗口之间进行权衡。

### 6.1 四种扩展机制

这些机制在不同的源代码目录中实现（图 5），并服务于不同的集成模式：

**MCP 服务器**。Model Context Protocol 是主要的外部工具集成路径。MCP 服务器从多个范围配置：项目、用户、本地和企业，以及在运行时合并的额外插件和 claude.ai 服务器（services/mcp/config.ts）。MCP 客户端（services/mcp/client.ts）支持多种传输类型：stdio、SSE、HTTP、WebSocket、SDK，以及 IDE 特定变体（sse-ide、ws-ide）和内部 claudeai-proxy。每个连接的服务器贡献 MCPTool 对象的工具定义。专用内置工具 ListMcpResourcesTool 和 ReadMcpResourceTool 提供对 MCP 资源的访问。

**插件**。插件具有双重角色：它们既是打包格式也是分发机制。PluginManifestSchema（utils/plugins/schemas.ts）接受十种组件类型：命令、智能体、技能、钩子、MCP 服务器、LSP 服务器、输出样式、通道、设置和用户配置。插件加载器（utils/plugins/pluginLoader.ts）验证清单并将每个组件路由到各自的注册表：命令和技能通过 SkillTool 元工具呈现，智能体出现在 AgentTool 消耗的定义中，钩子合并到钩子注册表，MCP 和 LSP 服务器折叠到其标准配置，输出样式修改响应格式。因此，单个插件包可以同时跨多个组件类型扩展 Claude Code，使插件成为第三方扩展的主要分发载体。

**技能**。每个技能由带有 YAML frontmatter 的 SKILL.md 文件定义。parseSkillFrontmatterFields() 函数（loadSkillsDir.ts）解析 15+ 个字段，包括显示名称、描述、允许的工具（授予技能访问额外工具的权限）、参数提示、模型覆盖、执行上下文（'fork' 用于隔离执行）、关联的智能体定义、工作量级别和 shell 配置。技能可以定义自己的钩子，这些钩子在调用时动态注册。打包的技能在启动时注册在内存中。调用时，SkillTool 元工具将技能的指令注入上下文。

**钩子**。源代码定义了 27 个钩子事件，跨越工具授权（PreToolUse、PostToolUse、PostToolUseFailure、PermissionRequest、PermissionDenied）、会话生命周期（SessionStart、SessionEnd、Setup、Stop、StopFailure）、用户交互（UserPromptSubmit、Elicitation、ElicitationResult）、子智能体协调（SubagentStart、SubagentStop、TeammateIdle、TaskCreated、TaskCompleted）、上下文管理（PreCompact、PostCompact、InstructionsLoaded、ConfigChange）、工作区事件（CwdChanged、FileChanged、WorktreeCreate、WorktreeRemove）和通知（coreTypes.ts、coreSchemas.ts）。其中，15 个具有支持权限决策、上下文注入、输入修改、MCP 结果转换和重试控制的富字段事件特定输出模式（types/hooks.ts）。通过设置和插件配置的持久化钩子命令使用四种命令类型：shell 命令（type: command）、LLM 提示钩子（type: prompt）、HTTP 钩子（type: http）和智能体验证器钩子（type: agent）（schemas/hooks.ts）。运行时还支持由 SDK 和内部仪器使用的非持久化回调钩子（type: callback）（types/hooks.ts）。钩子来源包括启动时的 settings.json、插件和托管策略；技能钩子在调用时动态注册（utils/hooks.ts）。五个工具授权事件在第 5.3 节中详述。

### 6.2 工具池组装

tools.ts 中的 assembleToolPool() 函数被记录为"组合内置工具和 MCP 工具的唯一真实来源"。组装遵循五步管道：

1. **基础工具枚举**。getAllBaseTools()（tools.ts）返回多达 54 个工具的数组：19 个始终包含（如 BashTool、FileReadTool、AgentTool、SkillTool），另外 35 个根据功能标志、环境变量和用户类型有条件包含。Anthropic 内部用户获得额外的内部工具。Worktree 模式启用 EnterWorktreeTool 和 ExitWorktreeTool。智能体 swarm 启用团队工具。当 Bun 二进制文件中嵌入搜索工具可用时，专用 GlobTool 和 GrepTool 被省略。

2. **模式过滤**。getTools()（tools.ts）应用模式特定过滤。在 CLAUDE_CODE_SIMPLE 模式中，只有 Bash、Read 和 Edit 可用（REPL 分支中的 REPLTool；加上下面的协调器工具）。每个工具的 isEnabled() 方法被调用以进行运行时可用性检查。

3. **拒绝规则预过滤**。filterToolsByDenyRules()（tools.ts）在任何调用之前从模型的视图中剥离全部拒绝的工具。

4. **MCP 工具集成**。来自 appState.mcp.tools 的 MCP 工具通过拒绝规则过滤并与内置工具合并。

5. **去重**。工具按名称去重，内置工具优先于 MCP 工具。

REPL.tsx（通过 useMergedTools 钩子）和 AgentTool.tsx（在构建工作器工具集时）都调用此函数，确保所有执行路径的一致组装。在请求时，延迟的工具可能对模型的上下文隐藏，直到通过 ToolSearch 明确查询（tools.ts）。

基于智能体的扩展（通过 .claude/agents/*.md 的自定义智能体定义和插件贡献的智能体）在第 8 节中介绍，因为智能体从根本上不同于上述四种机制：它们创建新的隔离上下文窗口，而不是扩展当前上下文。

### 6.3 为什么是四种机制？

鉴于每个额外的扩展机制都会增加开发者必须学习的内容面积，一个自然的问题是为什么 Claude Code 使用四种不同的机制而不是合并成一两种。答案在于观察到不同类型的可扩展性对上下文窗口施加不同的成本，并且单一机制无法涵盖从零上下文生命周期钩子到模式重型工具服务器的完整范围，而不强制扩展作者做出不必要的权衡。

如表 2 所总结的，每种机制都为了不同类型的可扩展性而权衡部署复杂性。MCP 服务器提供运行时工具集成（模型获得新的可调用工具），代价是服务器管理开销和工具模式消耗的上下文预算。技能塑造智能体的思考方式（不仅仅是它有什么工具），上下文成本最低，因为只有 frontmatter 描述（不是完整内容）留在提示中。钩子提供横切生命周期控制（阻止、重写或注释工具调用），默认情况下没有上下文占用，尽管钩子可以选择注入额外上下文。插件将其他三种机制组合成可分发包，充当打包和分发层而不是不同的运行时原语。渐变的上下文成本排序（钩子为零，技能为低，插件为中，MCP 为高）意味着便宜的扩展可以广泛扩展而不会耗尽上下文窗口，而昂贵的扩展保留用于真正需要新工具表面的情况。

一些智能体框架提供单一扩展机制，通常是工具专用 API，所有自定义都作为额外的可调用工具到达。其他使用两层，将工具与配置或指令注入分开。Claude Code 的四种机制方法可以容纳更广泛的扩展模式，从零上下文事件处理器到完整外部服务集成，但它增加了开发者在决定为给定集成任务使用哪种机制时面临的学习曲线。

### 3.6 上下文作为瓶颈：超越压缩

除了五层压缩管道（详见第 7 节），其他几个子系统决策反映了上下文作为瓶颈的约束：

- **CLAUDE.md 延迟加载**：基础 CLAUDE.md 层级在会话开始时加载，但只有当智能体读取这些目录中的文件时，才加载额外的嵌套目录指令文件和条件规则，防止未使用的指令消耗上下文。
- **延迟工具模式**：当 ToolSearch 启用时，一些工具在初始上下文中仅包含其名称；完整模式按需加载。
- **子智能体仅摘要返回**：子智能体仅向父级返回摘要文本，而非其完整对话历史（第 8 节）。
- **每工具结果预算**：单个工具结果有可配置的大小上限，防止单个冗长输出消耗不成比例的上下文。

## 7 上下文构建与记忆

智能体如何管理其上下文窗口并持久化用户指令是一个核心设计选择，不同系统在此选择上各有侧重：基于文件的透明度、数据库支持的检索，以及不透明的习得表征。这些设计选择实现了表1中的两个原则：上下文作为稀缺资源与渐进管理，以及透明基于文件的配置和记忆。

至此运行示例，任务已积累了状态：原始请求、npm test权限结果、第6节中汇编的工具池，以及到目前为止收集的任何文件读取或命令输出。本节探讨如何将这些不断增长的状态打包到Claude Code的有界上下文窗口中，以便进行下一次模型调用。

在调用模型之前，智能体循环从工具池（第6节）、CLAUDE.md文件、自动记忆和对话历史中汇编出一个上下文窗口。以下小节涵盖汇编顺序、CLAUDE.md层级结构以及多步压缩管道。

### 7.1 上下文窗口汇编

上下文窗口（图6）由以下来源汇编而成，其中一些在初始汇编时加载，另一些在回合后期注入：

1. **系统提示**，包含输出样式修改和任何 --append-system-prompt 标志内容。
2. **环境信息**通过 getSystemContext()（context.ts）：git status（在远程模式或禁用git指令时跳过）以及可选的内部构建缓存中断注入（由 BREAK_CACHE_COMMAND 控制）。每个会话仅缓存一次。
3. **CLAUDE.md层级**通过 getUserContext()（context.ts）：四级指令文件层级（第7.2节）。同样被缓存。
4. **路径作用域规则**：条件性和目录匹配规则，在智能体读取匹配目录中的文件时延迟加载。
5. **自动记忆**：异步预取的情境相关记忆条目。
6. **工具元数据**：技能描述、MCP工具名称和延迟工具定义（通过ToolSearch，按需加载）。
7. **对话历史**：向前携带，受压缩约束。
8. **工具结果**：文件读取、命令输出、子智能体摘要。
9. **压缩摘要**：替换较旧的历史片段。

**表2 各扩展机制的独特能力。上下文成本指该机制激活时消耗的有界上下文窗口的比例。**

| 机制 | 独特能力 | 上下文成本 | 注入点 |
|------|----------|------------|----------|
| MCP服务器 | 外部服务集成（多传输） | 高（工具模式） | model()::tool pool |
| 插件 | 多组件打包与分发 | 中（可变） | 全部三个点 |
| 技能 | 领域特定指令+元工具调用 | 低（仅描述） | assemble()::context injection |
| 钩子 | 生命周期拦截+事件驱动自动化 | 默认零成本 | execute()::pre/post tool |

将其他三种机制组合成可分发包的机制，作为打包和分发层而非独立的运行时原语。渐进式上下文成本排序（钩子为零，技能为低，插件为中，MCP为高）意味着廉价扩展可以广泛扩展而不会耗尽上下文窗口，而昂贵扩展则保留给真正需要新工具表面的情况。

一些智能体框架提供单一扩展机制，通常是工具-only API，所有自定义都作为额外可调用工具到达。其他使用两层架构，将工具与配置或指令注入分离。Claude Code的四机制方法可以容纳更广泛的扩展模式，从零上下文事件处理程序到完整外部服务集成，但这增加了开发者在决定对于给定集成任务使用哪种机制时面临的学习曲线。

### 7.2 CLAUDE.md层级与自动记忆

一个设计原则塑造了记忆系统：存储的上下文应对用户可检查和可编辑。CLAUDE.md文件是纯文本Markdown，而非结构化配置或不透明的数据库条目。这种透明度选择以表达性换取可审计性：用户可以读取、编辑、版本控制和删除智能体看到的任何指令（MindStudio Team, 2026）。替代记忆架构说明了这种权衡。检索增强方法使用基于嵌入的查找来呈现相关的先前上下文，在可检查性方面的代价获得灵活性：用户无法轻易看到或编辑检索系统认为相关的内容。数据库支持的记忆提供结构化查询，但需要额外的基础设施，并且对版本控制不透明。Claude Code的基于文件的方法使智能体看到的每条指令都可以直接读取、编辑，并与代码库一起提交。该系统不使用嵌入或向量相似性索引进行记忆检索；相反，它使用基于LLM的内存文件头扫描来按需选择最多五个相关文件，以文件粒度而非条目粒度呈现。基于嵌入的系统可以更精确地检索单个条目，代价是牺牲可检查性和维护索引所需的基础设施。

CLAUDE.md文件遵循多级加载层级。源头（claudemd.ts）定义了四种记忆类型：

1. **托管记忆**（例如Linux上的/etc/claude-code/CLAUDE.md）：所有用户的操作系统级策略。
2. **用户记忆**（~/.claude/CLAUDE.md）：私有全局指令。
3. **项目记忆**（CLAUDE.md、.claude/CLAUDE.md和项目根目录中的.claude/rules/*.md）：纳入代码库的指令。
4. **本地记忆**（项目根目录中的CLAUDE.local.md）：被git忽略，用于私有项目特定指令。

文件发现从当前目录遍历到根目录，检查每个目录中的所有项目和本地记忆文件。更接近当前目录的文件具有更高优先级（后加载）。

文件按"优先级逆序"加载：后加载的文件获得更多模型注意力。对于根到CWD目录，来自.claude/rules/*.md的无条件规则在启动时急切加载。对于CWD以下的嵌套目录，即使是无条件规则也会在智能体读取匹配目录中的文件时延迟加载。这意味着模型的指令集可以在对话过程中随着代码库新部分的探索而演进。

CLAUDE.md内容作为用户上下文（用户消息）传递，而非作为系统提示内容（context.ts）。这种架构选择有一个重要含义：因为CLAUDE.md内容作为对话上下文而非系统级指令传递，模型对这些指令的遵循是概率性的而非保证的。在拒绝优先顺序中评估的权限规则（第5节）提供了确定性执行层。这创建了指导（CLAUDE.md，概率性）和执行（权限规则，确定性）之间的有意分离。`setCachedClaudeMdContent()`函数缓存加载的内容以供自动模式分类器使用，以避免CLAUDE.md加载器和权限系统之间的导入循环。

记忆文件支持@include指令用于模块化指令集（claudemd.ts中的`processMemoryFile()`）。语法变体包括@path、@./relative、@~/home和@/absolute。该指令仅在叶文本节点中工作（不在代码块内部）。在实现中，包含文件被首先推送，被包含的文件在其后追加，通过跟踪处理路径来防止循环引用，不存在的文件被静默忽略。

### 7.3 压缩管道

五层压缩管道（第4.3节）通过渐进式压缩（query.ts）实现了"上下文作为瓶颈"原则。Claude Code不是使用单一策略，而是按顺序应用五层，每层都有越来越强的压缩力度（三层由功能标志控制；预算缩减始终激活，而自动压缩可由用户配置）。这种渐进式方法与更简单的替代方案形成对比：许多智能体框架使用单次通过截断（删除最旧的消息）或单一摘要步骤。渐进式设计反映了一种惰性降级原则：首先应用破坏性最小的压缩，仅在更便宜的策略证明不足时才升级。这种方法的代价是复杂性。五个相互作用的压缩层，几个由功能标志控制，创造了对用户难以完全预测的行为。自动压缩在转录本中产生可见摘要，微压缩发出边界标记，但上下文折叠在没有用户可见输出的情况下操作。更简单的单次通过方法牺牲了信息，但更容易推理。

压缩管道的五层：

1. **预算缩减**（始终激活）：每个工具结果的大小限制。
2. **剪断**（HISTORY_SNIP）：轻量级较旧历史修剪。
3. **微压缩**（CACHED_MICROCOMPACT）：细粒度缓存感知压缩。
4. **上下文折叠**（CONTEXT_COLLAPSE）：读取时对历史的虚拟投影。
5. **自动压缩**（默认启用，可禁用）：完整模型生成的摘要。

`buildPostCompactMessages()`函数（compact.ts）返回以下压缩输出结构：`[boundaryMarker, ...summaryMessages, ...messagesToKeep, ...attachments, ...hookResults]`。边界标记通过`annotateBoundaryWithPreservedSegment()`使用保留段元数据进行注释，记录headUuid、anchorUuid和tailUuid以启用读取时链修补。这种mostly-append设计意味着压缩从不修改或删除先前写入的转录本行；它仅追加新的边界和摘要事件。

`compactConversation()`函数（compact.ts）包含几个设计选择。预压缩钩子首先触发，允许钩子注入的自定义指令。GrowthBook功能标志控制压缩路径是否重用主对话的提示缓存（代码注释记录了2026年1月的实验："false路径是98%的缓存未命中，成本约为fleet cache_creation的0.76%"）。压缩后，附件构建器从实时应用状态重新宣布运行时状态（计划、技能和异步智能体），因为压缩丢弃先前的附件消息但不丢弃底层状态。

当系统将工作委托给子智能体时，上下文隔离变得更加关键，每个子智能体都在自己的有界上下文窗口中运行。

## 8 子智能体委托与编排

多智能体编排是编码智能体的一个关键设计维度，其选择涉及父子层级、同级对话框架（Wu et al., 2024）和图结构工作流引擎（LangChain, Inc., 2024）。Claude Code 的委托架构实现了表 1 中的隔离子智能体边界原则，以及优先拒绝加人类升级（权限覆盖）和可逆性加权风险评估（子智能体工具限制）的相关方面。

当 Claude 确定 auth 测试修复需要首先探索认证模块的结构时，它可以将此探索委托给一个子智能体。委托机制是 Agent 工具（AgentTool.tsx），Task 保留作为传统别名。模型使用包含委托提示、可选子智能体类型以及隔离模式、权限覆盖和工作目录配置的结构化输入来调用 Agent。

### 8.1 Agent 工具与委托标准

Agent 工具输入模式（图 7）使用功能门控字段，在其支持功能被禁用时省略可选参数。isolation 字段为内部用户提供 ['worktree', 'remote']，为外部用户提供 ['worktree']，在构建时确定。cwd 字段由功能标志门控。run_in_background 字段在后台任务被禁用或启用 fork-subagent 模式时被省略。

Claude Code 根据功能标志和入口点提供多达六种内置子智能体类型：

- **Explore**：主要是读取/搜索导向的调查，deny-list 中包含写入和编辑工具。
- **Plan**：创建结构化计划；执行通过标准权限模型进行。
- **General-purpose**：广泛能力的类型，当显式请求时使用（注意：省略类型可能路由到 fork-subagent 路径）。
- **Claude Code Guide**：入职和文档协助，有自己的 permissionMode 覆盖。
- **Verification**：运行验证检查（测试套件、linting）。
- **Statusline-setup**：专为终端状态行配置而设计。

除了内置类型，用户还通过 .claude/agents/*.md 文件定义自定义子智能体，插件通过 loadPluginAgents.ts 贡献智能体定义。每个文件的 markdown 正文用作智能体的系统提示，YAML 前置元数据指定配置字段，包括 description、tools（allowlist）、disallowedTools、model、effort、permissionMode、mcpServers、hooks、maxTurns、skills、memory scope、background flag 和 isolation mode。JSON 格式的智能体定义支持相同字段加 prompt 作为显式字段（loadAgentsDir.ts）。这意味着自定义智能体可以是一个完全配置的隔离子系统，有自己的工具、模型、权限、钩子、内存范围和隔离模式。AgentTool 与 SkillTool 并列作为基础工具池中的元工具，但两者根本不同：SkillTool 将指令注入当前上下文窗口，而 AgentTool 生成一个新的隔离上下文。

权衡是大多数子智能体调用需要一个自包含的提示，因为默认路径不继承父级的对话历史（fork-subagent 路径是例外）。共享完整转录历史的对话框架避免了这种成本，但随着智能体数量增长，存在上下文膨胀的风险。

### 8.2 隔离架构

子智能体隔离支持多种模式（AgentTool.tsx）：

- **Worktree**：创建一个临时 git worktree，给予子智能体自己的仓库副本以修改，而不影响父级的工作树。
- **Remote**（仅内部）：在远程 Claude Code Remote 环境中启动，始终在后台运行。
- **In-process**（默认）：与父级共享文件系统，但在隔离的对话上下文中操作。

子智能体的权限覆盖逻辑（runAgent.ts）涉及几个特定规则。当子智能体定义 permissionMode 时，应用覆盖，除非父级已经处于 bypassPermissions、acceptEdits 或 auto 模式，因为这些模式始终优先，因为它们代表关于安全/自主权衡的显式用户决策。对于异步智能体，系统通过级联确定是否避免提示：显式 canShowPermissionPrompts 首先，然后是 bubble 模式（始终显示，因为它们升级到父终端），然后是默认值（同步智能体显示提示，异步智能体不显示）。可以显示提示的后台智能体设置 awaitAutomatedChecksBeforeDialog: true，确保分类器和钩子在中断用户之前解析。

这些隔离模式在设计空间的不同点上运作。基于容器的隔离（SWE-Agent 和 OpenHands（Yang et al., 2024; Wang et al., 2024b）使用的）提供更强的资源边界，但需要容器基础设施。仅上下文隔离（AutoGen（Wu et al., 2024）等对话框架使用的）共享文件系统但分离对话历史。Claude Code 的基于 worktree 的隔离通过零外部依赖提供文件系统级分离，利用 Git 的内置机制而非引入容器编排。

当 allowedTools 被显式提供给 runAgent()（runAgent.ts）时，应用两层权限范围模型。来自 --allowedTools 的 SDK 级权限被保留："来自 SDK 消费者的显式权限，应适用于所有智能体"。但会话级规则被替换为子智能体声明的 allowedTools。当 allowedTools 未提供（常见的 AgentTool 路径）时，继承父级的会话级规则而不替换。

### 8.3 侧链转录本

每个子智能体将自己的转录本写为单独的 .jsonl 文件，带有 .meta.json 元数据文件（sessionStorage.ts、runAgent.ts）。这种侧链设计意味着子智能体历史被保留用于调试和审计，但不会膨胀父级的会话文件。只有子智能体的最终响应文本和元数据返回到父级对话上下文；完整的子智能体历史永远不会进入父级的上下文窗口，遵循"上下文作为瓶颈"原则。

runAgent() 函数接受 21 个参数，涵盖智能体定义、提示、权限、工具、模型设置、隔离和回调。

仅摘要返回模型是一个深思熟虑的上下文保护选择：在智能体之间共享完整转录历史的对话框架存在随着智能体数量增长而上下文膨胀的风险。即使是仅上下文并行的隔离也会带来 substantial 成本。Claude Code 的智能体团队消耗的计划模式下标准会话约 7 倍的令牌（Anthropic, 2025b），这使得仅摘要返回在子智能体也处于隔离上下文时更加关键。

对于智能体团队中的多实例协调，安全带使用文件锁定而非消息代理或分布式协调服务（Anthropic, 2025b）。任务通过基于锁文件的互斥从共享列表中认领，锁文件存储在可预测的文件系统路径上。这以吞吐量换取两个属性：零依赖部署（不需要外部基础设施）和完全可调试性（任何智能体的状态都可以通过读取纯文本 JSON 文件进行检查）。

## 9 会话持久化与恢复

会话持久化在编码智能体中涉及设计选择，即仅追加日志、结构化数据库、基于检查点的快照和无状态架构之间，每个都有不同的可审计性、查询能力和部署复杂性权衡。Claude Code 的持久化设计实现了表 1 中的仅追加持久状态原则。会话范围的权限仅存在于内存中，不序列化为转录本，因此恢复时从 CLI 参数和磁盘设置重建权限上下文；重建上下文不认识的请求会退回优先拒绝提示。

当 auth-test 任务到达本节时，会话包含原始提示、工具调用和结果、压缩边界以及探索认证模块的子智能体摘要（第 8 节）。本节询问这些工件中有哪些被持久记录，以及以后可以在不携带会话旧的权限授予的情况下恢复什么。

Claude Code 的持久化机制在事件发生时将对话（消息、工具结果和压缩边界）写入磁盘。

### 9.1 转录本模型

会话转录本存储为项目特定路径下的mostly-append JSONL 文件（明确清理重写为例外）（图 8）。getTranscriptPath() 函数（sessionStorage.ts）计算为 join(projectDir, ${getSessionId()}.jsonl)，其中 projectDir 首先由 getSessionProjectDir()（在恢复/分支期间由 switchSession() 设置）确定，然后回退到 getProjectDir(getOriginalCwd())()。

三个持久化通道独立操作：

1. **会话转录本**：包括 user、assistant、attachment 和 system 消息以及压缩和其他元数据事件的对话记录。项目范围的，每个会话一个文件。
2. **全局提示历史**：仅用户提示，存储在 Claude 配置主目录中的 history.jsonl（history.ts）。makeHistoryReader() 生成器通过 readLinesReverse() 以反向顺序产生条目，支持 Up-arrow 和 ctrl+r 导航。
3. **子智能体侧链**：每个子智能体单独的 .jsonl + .meta.json 文件（第 8.3 节）。

会话转录本存储超越简单消息的多种事件，包括压缩标记、文件历史快照、归属快照和内容替换记录。仅追加 JSONL 格式是选择可审计性和简单性而非查询能力的深思熟虑选择。每个事件是人类可读的、版本可控的，无需专业工具即可重建。数据库支持的替代方案可以对会话历史进行更丰富的查询，但会引入部署依赖并降低透明度。

会话标识系统将 sessionId 与 sessionProjectDir 配对，在恢复或分支期间一起设置。转录本路径必须使用与消息写入时相同的项目目录，以避免钩子在错误的目录中查找。

### 9.2 恢复、分叉与不恢复权限

--resume 标志通过重放转录本来重建对话（conversationRecovery.ts）。Fork 从现有会话创建新会话（commands/branch/branch.ts）。但是，恢复和分叉不恢复会话范围的权限；用户必须在新会话中再次授予它们。这是一个深思熟虑的安全保守设计选择：会话被视为隔离的信任域。在恢复时恢复先前授予的权限会创造便利好处，但会将过时的信任决策带入已改变的上下文风险中。架构选择重新授予而非隐式持久化，接受用户摩擦作为维护信任始终在当前会话中建立的安全不变量的代价。

compact_boundary 标记被仔细设计为与持久化一起工作。annotateBoundaryWithPreservedSegment() 函数（compact.ts）在边界事件中记录 headUuid、anchorUuid 和 tailUuid。这些 UUID 使会话加载器能够在读取时修补消息链：保留的消息在磁盘上保持其原始 parentUuids，加载器使用边界元数据将它们正确链接。这种mostly-append设计意味着压缩从不修改或删除先前写入的转录本行。

Claude Code 中的"检查点"是 --rewind-files 的文件历史检查点，存储在 ~/.claude/file-history/<sessionId>/。这些是用于恢复文件系统变化的文件级快照，而非通用检查点存储。

扩展架构 | 4 种机制，按上下文成本渐进：MCP、plugins、skills、hooks | 清单优先的插件系统，12 种能力类型和中央注册表；独立的 skills 层；内置 MCP（openclaw mcp 命令，支持服务端和出站客户端注册）
记忆与上下文 | CLAUDE.md 4 级层级结构；5 层压缩管道；基于 LLM 的记忆扫描 | workspace 引导文件（AGENTS.md、SOUL.md、TOOLS.md、IDENTITY.md、USER.md，条件性包含 BOOTSTRAP.md、HEARTBEAT.md 和 MEMORY.md）；独立记忆系统（MEMORY.md、每日笔记、可选的 DREAMS.md）；带可插拔提供商的自动压缩；可选的混合搜索（向量+关键词，取决于嵌入提供商）；用于长期晋升的实验性"做梦"机制
多智能体与路由 | 任务委托式子智能体（如 Explore、Plan、通用类型）；worktree 隔离；最终响应文本返回父级 | 两个独立关注点：(a) 多智能体路由，具有隔离的智能体、独立的 workspace 和基于绑定的通道分发；(b) 子智能体委托，可配置嵌套深度（最大 5，默认 1，推荐 2）以及支持通道上的线程绑定会话

Where Claude Code is a CLI coding harness bound to a single repository session, OpenClaw is a persistent control plane for multi-channel personal assistance. The two systems occupy different regions of the agent design space. The value of the comparison lies in showing how the same recurring questions produce different architectural answers when the deployment context changes.

### 10.1 六个比较维度

Table 3 总结了六个维度的比较。每个维度对应两个系统都必须回答的一个设计问题。

**系统范围与部署模型。** Claude Code 作为绑定到单个仓库的临时 CLI 进程运行。每个会话随终端启动和结束。OpenClaw 作为持久化守护进程运行（默认端口 18789，仅本地回环），拥有所有消息表面连接，并通过类型化 WebSocket 协议协调客户端、工具和设备节点。这种系统范围的差异是最根本的架构分歧：它决定了所有其他设计问题的框架方式。一种组合关系也存在：OpenClaw 可以通过其 ACP（Agent Client Protocol）集成将 Claude Code、OpenAI Codex 和 Gemini CLI 作为外部编码工具托管，使两个系统可堆叠而非纯粹互斥。

**信任模型与安全架构。** 两个系统处理不同的威胁模型。Claude Code 假设不受信任的模型在受信任开发者的机器内运作：优先拒绝权限系统（第 5 节）评估每次工具调用，ML 分类器提供自动化安全评估，七种权限模式创建渐变自主性谱系。OpenClaw 假设每个网关实例只有一个受信任操作员。其安全架构从身份和访问控制开始（DM 配对码、发送者允许列表、网关认证），而非逐操作安全分类。工具策略使用按智能体可配置的允许/拒绝列表，而非集中式分类器。沙箱作为可选功能提供，多种后端（Docker、SSH 或 OpenShell）和可配置作用域（按智能体、按会话或共享）；非 main 模式可以在启用时沙箱化所有非 main 会话，但沙箱隔离默认不激活。OpenClaw 安全文档明确声明敌对多租户隔离在共享网关上不是支持的安全边界。这种差异反映了关于信任边界位置的设计选择：Claude Code 将其放在模型和执行环境之间；OpenClaw 将其放在网关周边。

**智能体运行时与工具编排。** 两个系统都实现了智能体循环，但这些循环在各自架构中处于不同位置。在 Claude Code 中，queryLoop() 异步生成器（第 4 节）是系统中心：所有接口都接入其中，它直接管理上下文组装、模型调用、工具调度和恢复。在 OpenClaw 中，智能体运行时（嵌入的 Pi-agent 核心）位于更大的网关调度层内部。网关的智能体 RPC 验证参数、解析会话并立即返回；嵌入的运行器然后执行智能体循环，同时通过网关协议将生命周期和流事件发回。运行通过 per-session 队列和可选的全局通道序列化，防止跨多通道表面的工具和会话竞争。两个系统都遵循 ReAct 模式（Yao et al., 2022），但 OpenClaw 的循环是控制平面内的组件，而非控制平面本身。

**扩展架构。** Claude Code 的四种扩展机制（MCP、plugins、skills、hooks）按上下文成本组织（第 6 节）：hooks 消耗零上下文，skills 消耗低上下文，MCP 服务器消耗高上下文。所有四种都扩展了单个智能体的上下文窗口和工具表面。OpenClaw 使用清单优先的插件系统，具有四个架构层（发现、启用、运行时加载、表面消费）和十二种能力类型，包括文本推理、语音、媒体理解、图像/音乐/视频生成、网络搜索和消息通道。插件将能力注册到中央注册表；网关读取注册表以暴露工具、通道、提供商设置、hooks、HTTP 路由、CLI 命令和服务。OpenClaw 还有一个独立的 skills 层，具有多个来源（workspace、项目级、个人、托管、捆绑和额外目录，workspace skills 优先级最高）以及公共注册表（ClawHub），并通过内置的 openclaw mcp 命令（服务器和出站客户端注册表）支持 MCP。关键架构差异在于 Claude Code 的扩展修改单个智能体的操作表面，而 OpenClaw 的插件在所有智能体间扩展网关的能力表面。

**记忆、上下文与知识管理。** 两个系统都使用透明的基于文件的记忆而非不透明的数据库。Claude Code 加载四级 CLAUDE.md 层级结构，并通过五层压缩管道管理上下文压力（第 7 节）。记忆检索使用对文件头的基于 LLM 的扫描。OpenClaw 在会话开始时将 workspace 引导文件注入系统提示：五个核心文件（AGENTS.md、SOUL.md、TOOLS.md、IDENTITY.md、USER.md）加上条件性的 BOOTSTRAP.md、HEARTBEAT.md 和 MEMORY.md，大文件会被截断。另外，记忆系统管理三种文件类型：MEMORY.md 用于长期持久化事实，带日期戳的每日笔记（memory/YYYY-MM-DD.md），以及可选的 DREAMS.md 用于"做梦"扫一扫总结。当配置了嵌入提供商时，记忆搜索使用结合向量相似性和关键词匹配的混合检索。实验性的"做梦"系统在后台进行整合，对候选进行评分并仅将符合条件的项目从短期记忆晋升到长期记忆。在压缩前，OpenClaw 自动提醒智能体将重要笔记保存到记忆文件，防止上下文丢失。两个系统都共享用户可见、可编辑记忆的设计承诺。OpenClaw 在结构化长期记忆晋升（做梦、每日笔记、记忆搜索）上投入更多，而 Claude Code 在渐进上下文压缩（五层，带缓存感知）上投入更多。OpenClaw 还支持可插拔压缩提供者和会话剪枝，但其压缩管道不如 Claude Code 的五层系统渐进。

**多智能体架构与路由。** 这个维度揭示了最显著的架构差异。Claude Code 的多智能体模型是任务委托：父级生成子智能体（Explore、Plan、通用类型和自定义类型），这些子智能体在隔离的上下文窗口中运作，具有受限的工具集并仅返回摘要结果（第 8 节）。Worktree 隔离提供文件系统级别的分离。OpenClaw 分隔两个不同的关注点。首先，多智能体路由：单个网关可以托管多个完全隔离的智能体，每个都有自己独立的 workspace、认证配置、会话存储和模型配置，通过确定性绑定规则路由到特定通道或发送者。其次，子智能体委托：在单个智能体内部，可以生成具有可配置嵌套深度（最大 5，默认 1，推荐 2）的后台运行，在支持的通道上具有线程绑定会话，以及按深度可配置的工具策略。OpenClaw 的项目愿景明确拒绝将智能体层级框架作为默认架构。这种区别很重要，因为 Claude Code 的子智能体是单个用户编码会话中的从属工作者，而 OpenClaw 的多智能体路由创建真正独立的智能体实例，通过不同通道服务不同用户或目的。

### 10.2 对比揭示了什么

比较 surface 了关于 AI 智能体系统设计空间的三个观察。

首先，第 3.1 节识别的反复设计问题（推理位于何处、采用什么安全姿态、如何管理上下文、如何构建扩展性）适用于编码智能体之外。OpenClaw 回答了所有这些问题，但从多通道个人助手而非仓库绑定编码工具的起点出发。问题是稳定的；答案随部署上下文而变化。

其次，两个系统在多个维度上做出了相反的赌注。Claude Code 投资于渐变逐操作安全评估；OpenClaw 投资于周边级身份和访问控制。Claude Code 将智能体循环作为架构中心；OpenClaw 将网关控制平面作为中心并将智能体循环嵌入为组件之一。Claude Code 的扩展修改单个上下文窗口；OpenClaw 的插件扩展共享网关表面。这些反转并非任意：它们源于不同的信任模型和部署拓扑。

第三，两个系统之间的组合关系具有架构意义。OpenClaw 可以通过 ACP 将 Claude Code 作为外部编码工具托管，这意味着两个系统可组合而非互斥替代。这表明 AI 智能体的设计空间不是扁平分类法而是分层的，网关级系统和任务级工具可以组合。

## 11 讨论

前述各节记录了 Claude Code 如何回答关于循环架构、安全姿态、扩展性、上下文管理、委托和持久化的反复设计问题。每个答案都反映了设计空间中具有真实替代方案和可衡量权衡的定位。本节审视当这些答案被一起阅读时揭示的内容：它们反映的设计哲学（第 11.1 节）、它们创造的价值张力（第 11.2 节）、它们涉及的架构权衡（第 11.3 节）、它们产生的经验预测（第 11.4 节）以及跨子系统反复出现的跨领域承诺（第 11.7 节）。第 2.1 节的五值框架作为贯穿始终的组织视角。

### 11.1 设计哲学

第 2 节介绍的值和设计原则预测了一种投资于操作基础设施而非决策脚手架的架构。实现确认了这一点：第 3 至 9 节记录的架构压倒性地是确定性基础设施（权限门、工具路由、上下文管理、恢复逻辑），LLM 作为无状态补全端点调用。据估计，1.6% 的代码库构成决策逻辑，其余 98.4% 是操作工具带。这个比例并非偶然。

第 2.2 节记录的设计原则支撑了这种方法：工具带创造条件使模型能够良好决策，而非限制其选择。

这种设计与智能体工程中的主导模式背道而驰，LangGraph 等框架将模型输出通过带类型边的显式图节点路由，Devin 等系统将多步规划器与重型操作基础设施配对。Claude Code 而是给予模型在丰富操作工具带内最大的决策自由度。工程复杂性存在不是为了约束模型的决策，而是为了实现它们。这种分层架构中模型推理而工具带执行，提出了一个问题：智能体编码工具是否正在收敛于类似操作系统的抽象，其中核心循环作为内核，其他一切构成操作系统。随着前沿模型在编码任务上的实际能力趋同，周围操作工具带的质量成为主要的差异化因素，验证了一种投资于基础设施而非决策脚手架的架构。对于智能体构建者而言，投资于确定性基础设施（如上下文管理、安全分层和恢复机制）可能比在越来越强大的模型周围添加规划脚手架获得更大的可靠性收益。

综上所述，前述各节表明，生产级编码智能体面临反复的设计选择：推理相对于工具带的位置、迭代循环的结构、默认采用的安全姿态、扩展表面的分区方式、上下文是如何组装和压缩的、子智能体是如何委托和编排的，以及会话如何跨边界持久化。Claude Code 对这些问题的回答形成了一个连贯的设计点，在丰富的操作工具带内优先考虑模型自主性。这种哲学假设丰富的确定性基础设施可以充分支持无约束的模型判断。以下小节检验这个假设在何处受到考验。

### 11.2 价值张力

第 2.1 节识别的五个价值观产生了张力，其中追求一个价值观会限制另一个（表 4）。这些张力不是设计失败；它们是同时追求多个价值观的结构性后果。我们报告有最强证据支持的张力，而非完整的组合集。

两个额外的张力通过长期能力保留的评估视角浮现（第 2.4 节）。一项涉及 16 名经验开发者、跨越 246 项任务的随机对照试验（Becker 等人，2025）发现，AI 工具使开发者慢了 19%，尽管他们感知到提升了 20%。一项跨 807 个仓库的 Cursor 采用因果分析（He 等人，2025）发现代码复杂度增加了 40.7%。一项涉及 54 名参与者的 EEG 研究（Kosmyna 等人，2025）发现 LLM 用户表现出减弱的神经连接，这种减弱在 AI 被移除后仍然持续。研究人员提出了测量 AI 辅助编程中认知卸载的协议，基于对学生使用 AI 构建应用时不理解底层逻辑的担忧（Aiersilan，2026）。这些发现结合 2023 年至 2024 年间入门级科技招聘下降 25%（Rak，2025），表明能力增强与长期可持续性之间的张力延伸到了个人生产力之外，进入了更广泛的开发者渠道。这一证据促使了评估视角，但并不专门针对 Claude Code 的架构；它适用于任何具有有限上下文和工具使用循环的智能体系统。

### 表 4 价值观之间的张力及支持证据

**价值对** | **张力** | **证据**
--- | --- | ---
权威 × 安全 | 批准疲劳 vs. 保护 | 93% 的批准率削弱了人类警惕（Hughes，2026）；安全必须通过分类器和沙箱化来补偿

### 11.3 架构权衡

表 4 中的张力在四个领域中表现为具体的架构权衡。评估视角中记录的长期可持续性问题出现在第 11.4 节的经验预测中。

**安全与自主性。** 权限模式（五种始终存在，加上分类器功能标志激活时的自动模式，以及内部气泡模式）创建了从 plan（用户批准所有计划）经过 default、acceptEdits、auto（ML 分类器）、dontAsk 到 bypassPermissions（跳过大多数提示但安全关键检查保留）的梯度。该进展代表了随自主性增加而单调递减的安全梯度。恢复时不还原权限反映了一种故意倾向于安全的选择：安全状态不会跨会话边界隐式持久化。

安全-自主性梯度不仅受架构设计影响，也受用户行为影响。Anthropic 的自动模式分析（Hughes，2026）发现用户批准约 93% 的权限提示，表明批准疲劳使交互确认在行为上不可靠。纵向使用数据（McCain 等人，2026）显示自动批准率从少于 50 个会话时的约 20% 增长到 750 个会话时的超过 40%，会话持续时间大幅增加。这些模式表明梯度不是通过深思熟虑的模式选择来导航的，而是通过逐渐的习惯化。沙箱化将权限提示频率降低约 84%（Dworken 和 Weller-Davies，2025），将问题重新框架为人类因素问题：不可靠的人类批准的架构响应是减少人类必须做出的决定数量。

更深层次地，第 5 节描述的纵深防御架构依赖于独立假设：如果一个安全层失败，其他层会捕获违规。但 Claude Code 的安全层共享共同性能和经济约束。自动模式分类器是带有直接 token 成本的分隔 LLM 调用。bashSecurity.ts 模块执行带解析延迟的顺序 AST 检查。优先拒绝规则评估对命令结构进行操作。当性能压力推向减少这些成本时，层可能同时降级。安全研究人员（Adversa.ai，2026）记录了超过 50 个子命令的命令回退到单个通用批准提示而不是运行每子命令拒绝规则检查，因为每子命令解析导致 UI 冻结，证明当独立假设被违反时纵深防御失败。

这种张力是结构性的。任何使用模型进行安全评估的基于 LLM 的智能体系统都面临它。相关的评估标准不是任何单个层是否可以被绕过，而是多少个独立层必须同时失败以及它们是否共享故障模式。

**对抗条件下的权限模型。** 独立安全研究提供了对权限架构的经验验证，具体揭示了图 4 中未捕获的时间排序属性。两个独立验证的漏洞在信任前初始化排序上共享根因：在项目初始化期间执行的代码（hooks、MCP 服务器连接和设置文件解析）在交互信任对话框呈现给用户之前运行。这一信任前执行窗口落在优先拒绝评估管道之外（permissions.ts），创建了一个结构性特权阶段，第 5 节记录的安全保证在该阶段中尚不适用。

这种模式揭示了权限管道描述了安全检查的空间排序但未捕获时间维度：具体而言，在会话初始化期间每个机制何时激活。初始化序列（扩展加载，然后信任对话框，然后权限执行）创建了一个窗口，其中扩展架构（第 6 节）在安全架构（第 5 节）完全参与之前运作。这一发现通过添加安全维度完善了扩展性对比简单性的张力：扩展性不仅通过组合复杂性还通过初始化排序创建攻击面。

**上下文效率 vs. 透明度。** 五层压缩管道实现了有效的上下文管理，但压缩对用户基本不可见。当 budget reduction 用引用替换长工具输出时，当 context collapse 用摘要替换消息时（在源代码中描述为"对 REPL 完整历史在读取时的投影"），或者当 snip 修剪较旧历史时，用户没有简单的方法检查丢失了什么。microcompact 的缓存感知行为增加了进一步的不透明性，因为压缩决策受提示缓存影响的方式对用户不可见。

**简单性 vs. 扩展性。** 四种扩展机制支持丰富的自定义但创建组合交互。一个 plugin 贡献了一个修改工具输入的 PreToolUse hook。自动模式分类器读取缓存的 CLAUDE.md 内容。路径作用域规则在新目录被读取时延迟加载，可能会在对话中途改变分类器行为。权限处理器的四个分支在多个点与 hook 管道交互。这些横切关注创建了难以从任何单个配置文件预测的新兴行为。

### 11.4 经验预测与早期信号

本文记录的建筑属性产生了关于代码质量结果的可测试预测，这些预测无法从源代码本身推导出来。有限上下文窗口（第 7 节）阻止智能体同时保持对整个代码库的意识：五层压缩管道保留有用信息但在每个阶段引入有损压缩。这使得建筑上预测智能体生成的代码将表现出比具有完整代码库可见性的代码更高的模式重复和约定违反率。子智能体隔离（第 8 节），其中每个子智能体在自己的上下文窗口中运作，具有独立组装的工具池，复合了这种效应：并行智能体可以独立地重新实现已经存在于别处的解决方案。第 11.1 节的设计哲学信任模型做出好的本地决策，但好的本地决策在模型缺乏全局上下文时可能产生差的全局结果。

在建筑上相似的工具上发表的实证工作提供了与这些预测一致的数据。一项跨 807 个仓库的 Cursor 采用因果分析（He 等人，2025）发现代码复杂度在统计上显著增加，第一个月速度峰值到第三个月消散到基线；上升的复杂度与未来开发速度成比例下降相关，表明收益是自我取消的。一项大规模审计跨 6,275 个仓库的 304,000 次 AI 创作的提交（Liu 等人，2026）发现了可衡量的技术债务，约四分之一的 AI 引入问题持续到最新版本，安全相关问题以显著更高的比率持续。虽然这些研究针对相邻系统，但建筑相似性（有限上下文、工具使用循环、单次生成）表明这些发现与这里分析的设计相关。

Claude Code 的上下文管理管道专门设计用于减轻这些效应：渐进压缩保留最新和最相关的上下文，缓存感知压缩避免在压缩期间使提示缓存失效，读取时投影维护完整历史以供重构，同时向模型呈现压缩视图，子智能体摘要隔离防止探索性噪声在父上下文累积。这些机制是否足以克服有限上下文的结构性限制是一个可直接衡量的经验问题，本文中的源代码级分析无法解决。

### 11.5 局限性

除了第 B.3 节中的方法论局限性外，还适用几个分析约束。记忆化上下文组装函数（getSystemContext() 和 getUserContext() 都使用 lodash memoize at context.ts）意味着 git 状态和 CLAUDE.md 内容被缓存而不是在每个轮次重新计算。对话期间的动态变化可能不会立即反映，尽管压缩可以清除缓存且延迟加载的路径作用域规则提供了部分对策机制。

功能标志创建构建时可变性。在 TRANSCRIPT_CLASSIFIER 为 false 的构建中，整个自动模式分类器被消除。功能门控模块使用动态 require() 而不是静态导入（例如，query.ts 用于上下文折叠），因为 feature() 仅在 if/三元条件下有效，原因是 bun:bundle tree-shaking 约束。不同的构建目标可能产生功能不同的应用程序。

### 11.6 新兴方向

实现的几个方面与更广泛的设计问题相关。更长的上下文窗口将减少压缩压力，潜在地简化渐进管道。多模态工具（截图、图表、UI 预览）将扩展工具表面并创建新的上下文挑战。权限属性的形式验证（例如，证明拒绝规则总是优先，沙箱化命令无法逃逸隔离，或者恢复的会话无法继承过时权限）将提供更强的安全保证。

**架构解耦。** 这里分析的紧密耦合的本地架构是已经发展中的谱系上的一个点。Anthropic 自己的 Managed Agents 工作（Martin 等人，2026）描述了将智能体的组件（session、harness、sandbox）虚拟化，使得"每个都成为一个接口，对彼此很少做假设，每个都可以独立失败或被替换"，类似于操作系统如何将硬件虚拟化为进程和文件的明确类比。Harness Design 论文（Rajasekaran，2026）从不同角度提出了类似观点，观察到"有趣的 harness 组合的空间不会随着模型改进而缩小"；相反，"它移动"。本文记录的架构应因此被读作共同发展的系统的快照而非固定的最优点。

**记忆作为一等子系统。** Hu 等人（2025）的记忆调查认为智能体记忆正在成为不同的认知基底而不是上下文窗口管理的副作用，并将自动化记忆管理、RL 驱动的记忆和可信赖记忆（隐私、可解释性和幻觉稳健性）识别为开放前沿。Claude Code 今天暴露了事实层（CLAUDE.md、自动记忆）和工作层（对话窗口）；体验层（从过去会话中积累的、自动策划的策略手册）是自然的下一个步骤，上下文工程文献（Zhang 等人，2025a）已经开始提供这种积累的机制。

**可观察性与静默失败。** 行业调查显示，部署智能体的主导失败模式不是崩溃而是静默错误。Bessemer 的 2026 年基础设施报告（Wade 等人，2026）估计"78% 的 AI 失败是不可见的"，而 LangChain 的 1,340 名受访者的智能体工程状态调查（LangChain，2026）识别质量而非成本是生产使用的最高障碍，并发现可观察性（近 89% 采用）与离线评估（52.4%）之间存在很大差距。这里分析的架构为操作员提供了对工具调用、hooks 和会话 transcript 的可见性；缩小评估差距可能需要额外的脚手架（生成器-评估器分离、sprint 合同和事后检查，如 Rajasekaran（2026）中讨论的那些）而不是单独的模型改进。

**治理。** 更广泛的治理趋势将约束智能体变得更加自主时的设计空间。国际 AI 安全报告（Bengio 等人，2026）警告"AI 智能体带来更高风险，因为它们自主行动，使人类更难以在失败造成伤害之前进行干预"，而 MIT AI 智能体指数（Staufer 等人，2026）发现只有 13.3% 的索引智能体系统发布智能体特定的安全卡片。新兴监管框架，特别是完全适用于 2026 年 8 月的 EU AI 法案和围绕 AI 生成代码的演变的版权判例，可能会对日志、透明度和人类监督施加外部约束，塑造编码智能体架构的发展方式。

**主动架构。** 特性门控的 KAIROS 系统说明了这种架构如何超越反应式工具使用。KAIROS 实现了一个带基于 tick 的心跳的持久后台智能体：当没有用户消息待处理时，系统注入周期性 <tick> 提示，模型决定是 acting 还是 sleep。该设计直接针对记录的张力：主动 AI 助手将任务完成率提高 12% 至 18%，但在高频下降低用户偏好（Chen 等人，2025）。KAIROS 通过终端焦点意识解决这一问题（当用户不在时最大化自主行动，在场时增加协作）和通过 SleepTool 的经济节流（每次唤醒成本一个 API 调用；提示缓存在五分钟不活动后过期，使 sleep/wake 成为明确的成本优化）。这种将主动性绑定到用户存在和 token 经济学的做法在生产智能体系统中不常见，尽管 KAIROS 无法确认在生产构建中处于 active。

### 11.7 反复出现的设计选择

将六个子系统分析一起阅读揭示了三个跨领域的设计承诺，这些承诺在独立组件中反复出现。

**渐进分层优于单体机制。** 安全、上下文管理和扩展性都使用独立机制的渐进堆栈而不是单一的集成解决方案。权限架构分七层，从工具预过滤通过优先拒绝规则、权限模式、自动模式分类器、shell 沙箱化、恢复时不还原和 hook 拦截。上下文管理分五层压缩阶段、延迟加载的 CLAUDE.md 文件、 deferred 工具模式和摘要唯子智能体返回。扩展性分四种机制（MCP 服务器、plugins、skills 和 hooks），在不同的上下文成本（第 6 节）。在每种情况下，设计都牺牲简单性和可调试性以换取纵深防御，接受层之间的交互可能产生难以从任何单个配置预测的新兴行为。

**优先追加的设计，偏好审计性而非查询能力。** 会话 transcript 是带有读取时链修补的仅追加 JSONL 文件；权限不在会话边界之间还原；上下文压缩对完整历史应用读取时投影而不是破坏性编辑。这一承诺反复出现是因为它保留了恢复、分支和审计会话的能力而不修改先前写入的状态。代价是更丰富的结构化查询（"显示我跨会话修改文件 X 的所有工具调用"）需要事后重建而不是直接查找。

**确定性工具带内的模型判断。** 在所有子系统中，架构信任模型在丰富确定性工具带内的判断，而不是约束其选择。估计的 1.6% 决策逻辑比率从数量上捕捉了这一点：工具带创造条件（工具路由、权限执行、上下文组装、恢复逻辑），使模型能够良好决策。分层权限在智能体边界之间保留安全不变量，assembleToolPool() 将内置和 MCP 工具合并到单个统一接口，但模型保留关于调用哪些工具以及以何种顺序调用的完全自由度。权衡是当有限上下文阻止全局意识时，好的本地决策可能产生差的全局结果，正如第 11.4 节的经验预测所记录的那样。

## 12 未来方向

第 11 节将第 3 至 9 节记录的架构作为一个连贯的设计点进行解读，并揭示了 tensions, trade-offs, and near-horizon directions。本节超越架构本身，记录了第 11.6 节初步命名的六个 open questions，这些问题已被日益增长的外部文献充分阐述，可以具体陈述。六个问题跨越了论文的五价值观框架（第 2.1 节）及其评估 lens（第 2.4 节）：对 Authority 层级的外部治理约束（第 12.5 节）；Safety 方面的可观察性-评估差距（第 12.1 节）；Reliability 方面的跨会话状态和关系持久化（第 12.2 节）；Capability frontier 的四个扩展（第 12.3 节）；作为可靠执行之外一个独立轴的 horizon scaling（第 12.4 节）；以及第 2.4 节评估 lens 重新表述为设计问题而非诊断问题（第 12.6 节）。

与第 11.6 节的表述一致，每个问题都以是否/如何/哪种的形式提出；当被引用来源命名具体机制选择时则使用其名称，否则保持开放。

### 12.1 静默失败与可观察性-评估差距

第 11.6 节报告的可观察性-评估采用差距是反映了缺失的工具层、harness 内部缺失的评估接口，还是模型能力天花板，目前尚无定论。因此，如何呈现该段所述的静默-错误 failure mode 是一个 harness 层面的架构问题，而非模型层面的能力问题。最近的经验性工作在多个分辨率上描述了这一差距。Cemri 等人（2025）编目了十四个跨系统设计问题、智能体间错位和任务验证的失败模式；Pathak 等人（2025）构建了一个专门用于智能体轨迹中异常检测的基准测试；Yao 等人（2024）通过 passk 指标（所有 k 次独立试验成功的概率）暴露了一致性差距；Kapoor 等人（2024）认为当前的智能体基准测试缺乏保留集和成本控制，限制了可观察性实际能诊断的内容。

针对第 4 和 5 节分析的权限管道和工具编排层，两个架构问题仍然开放。首先，第 11.6 节引用的 Rajasekaran（2026）的 scaffolding（生成器-评估器分离、sprint 合同、事后检查，建立在 Madaan 等人（2023）的 self-refine 模式之上）是属于 harness 内部（例如，作为第 6 节中 27 个已记录 hook events 的附加 hook events）还是外部作为单独的评估层，目前尚无定论。其次，现有的 hook 管道（第 6 节）是否可以在其当前上下文成本 envelope 内承载此类 scaffolding，这是一个进一步开放的问题。关闭这一差距"可能需要额外的 scaffolding……而不是单独的模型改进"（第 11.6 节）的观察，将开放工作定位在 harness 层。

### 12.2 持久化：记忆与纵向同事关系

智能体状态和人类-智能体工作关系是否应该跨会话持久化，以及以何种形式，论文在两个不同层次上处理。第 7 节记录了四级 CLAUDE.md 层次结构和自动记忆；第 9 节记录了主要是仅追加的 JSONL transcript（带有显式清理重写作为例外），其会话作用域权限恢复不会还原。这两个层次之间应该有什么（既不是静态指令也不是单个会话 transcript 的持久状态）是一个 open design question。Hu 等人（2025）和 Zhang 等人（2025a）已在第 11.6 节中引用，推动了一个积累层。Packer 等人（2023）将 LLM 重新表述为具有分页记忆的操作系统；Chhikara 等人（2025）构建了一个可在重启后存活的生产导向记忆存储；Xu 等人（2025）提出了一个研究智能体记忆设计；Wang 等人（2024c）捕获了可重用的程序轨迹；Shinn 等人（2023）通过语言强化跨尝试积累自我反思轨迹；Zhang 等人（2025b）和 Huang 等人（2026）的调查映射了候选机制。

同样的持久化问题在人类端反复出现。第 11.6 节已经引用了纵向自主性证据（Huang 等人，2025；McCain 等人，2026）；Dell'Acqua 等人（2025）对 776 名宝洁专业人士的现场实验，以及 Copilot 推广的纵向和组织学研究（Stray 等人，2025）和 AI 团队工作轨迹研究（Xiao 等人，2025），报告了随着协作积累，人类-AI 工作动态的变化。Wang 等人（2023）展示了一个跨任务积累技能库的具身智能体；Mollick（2024）将人类-AI 工作关系表述为共同智能。

单个 substrate 是否可以同时携带用户的个人指令层次结构和共享的组织上下文，同时保留第 7 节记录的 CLAUDE.md 的基于文件的透明度，这是一个开放的架构问题。会话作用域权限如何与这样的 substrate 交互，而不重新引入第 9 节作为 deliberate safety choice 关闭的恢复-还原问题，这是一个进一步的开放问题。

### 12.3 Harness 边界演进：智能体在哪里、何时、对什么、与谁一起行动

第 11.6 节引用了 Rajasekaran（2026）的观察："有趣的 harness 组合的空间不会随着模型改进而缩小；它移动。"这种移动在 harness 运行的位置、它何时行动、它对什么行动，还是它与谁协调方面最为显著，目前尚无定论。源代码级分析（第 3 至 9 节）无法解决。四者中的每一个都有活跃的研究文献，论文仅在 pass 中触及。

**在哪里。** Martin 等人（2026）的 Managed Agents 设计将 session、harness 和 sandbox 虚拟化为可独立替换的接口，扩展了 Packer 等人（2023）应用于上下文窗口管理的虚拟内存类比，以及 Karpathy（2023）更广泛推广的类比；Khattab 等人（2023）将 harness 本身视为编译目标。

**何时。** 第 11.6 节已经介绍了 KAIROS 作为特性门控的说明，由 Chen 等人（2025）报告的 +12%–18% 任务通过率提高和严格限制的高频 Persistent Suggest 变体的强烈偏好惩罚（47% vs. 80–90%）驱动。Liu 等人（2025）、Pu 等人（2025）和 Lee 等人（2025）在编程和 ambient-interface 设置中扩展了主动性设计空间；Pasternak 等人（2025）和 Sun 等人（2025）引入了旨在磨练主动性的基准测试和训练制度；Deng 等人（2025）调查了更广泛的领域。

**对什么。** 视觉-语言-动作工作将 harness 扩展到文本工具返回值之外：Brohan 等人（2024）和 Black 等人（2024）训练执行物理动作的 VLA 策略；Ahn 等人（2022）将计划建立在机器人可供性上；Figure AI（2025）和 Bjorck 等人（2025）等行业系统将类似想法推向人形控制。这些系统面临可逆性加权风险原则（表 1）在成本不对称上的问题，该原则命名但未量化非文本动作的成本。

**与谁一起。** 角色分化的多智能体系统（Hong 等人，2023；Li 等人，2023；Chen 等人，2023；Qian 等人，2024）组合具有不同职责的智能体；多智能体辩论（Du 等人，2024；Liang 等人，2024）和图结构工作流（Zhuge 等人，2024）探索了第 8 节父子/子智能体模式的替代方案；Guo 等人（2024）调查了这个空间。

单个 harness 架构是否可以跨越所有四个扩展，还是 Rajasekaran（2026）描述的"harness 组合"会碎片化为专门的堆栈，这是一个开放的设计问题。when 扩展直接继续表 4 中的 Capability-versus-Adaptability 紧张关系。with-whom 扩展部分映射到 Capability-versus-Reliability，但提出了表 4 本身未覆盖的跨智能体一致性问题。where 和 what 扩展提出了论文当前子系统边界未覆盖的进一步问题：当 harness 组件成为托管服务时哪些治理义务附加（第 12.5 节），以及可逆性加权风险（表 1）如何扩展到物理而非文本效果。这些扩展如何跨轴组合而不是在任何单一轴内组合，不是论文单一子系统分析可以解决的事情。

### 12.4 Horizon Scaling：从会话到科学程序

第 2.1 节将可靠执行定义为跨越"单轮正确性和长期可靠性"。随着自主工作超越单个会话，第 3、4 和 7 至 9 节记录的架构（其主要单位是轮次、会话和子智能体）如何继续支持长期可靠性是一个开放问题。越来越多的文献针对这一 regime。Lu 等人（2024）提出了一个产生草稿手稿的端到端自主研究管道；Beel 等人（2025）对该管道进行了独立的 SIGIR Forum 评估，描述了"自主研究"当前交付的内容及其不足之处。Gottweis 等人（2025）开发了一个跨天而非跨轮次运行的多智能体假设生成系统；Novikov 等人（2025）追求，以前需要人类专家数周的时间尺度进行算法发现。Kwa 等人的 METR 研究测量了前沿智能体以固定可靠性（50% 时间 horizon）成功完成任务的时间以及该 horizon 如何跨模型代际演变，为这个 scaling 问题提供了经验框架。

针对论文的分析，长期 horizon 部署测试了第 7 节的上下文管理管道、第 8 节的 last-assistant-text 返回策略以及第 9 节的仅追加持久化，当会话组合成多会话程序时是否仍然足够。第 11.4 节已经将其框定为"一个可直接测量的经验问题"，源代码分析无法解决。Horizon scaling 在数周的时间尺度上重新表述了这个问题：仅靠 harness 层是否就能弥合差距，是否需要跨会话 memory substrate（第 12.2 节），或者 horizon-scale 工作是否需要超越会话、子智能体和记忆的协调原语，这些都不是论文的会话作用域分析可以解决的事情。

### 12.5 规模化时的治理与监督

新兴的 AI 法规对实施第 2.1 节记录 Anthropic、操作员和用户 Authority 层级的架构添加了外部约束。在该外部约束下，编码智能体架构应该暴露哪些日志、透明度和人类监督功能，目前尚无定论。欧洲委员会的 GPAI 实践守则（European Commission，2025a）和实施指南（European Commission，2025b）详细规定了伴随着 EU AI 法案全面适用性（2026 年 8 月）的通用 AI 义务；MIT AI 智能体指数（Staufer 等人，2026）和国际 AI 安全报告（Bengio 等人，2026）已在第 11.6 节中引用，推动了此约束的披露和监督方面。Bartz v. Anthropic 裁决（bar，2025）在训练数据采购方面添加了输入侧约束（合法收购版权作品），与新兴案例单独处理的 AI 生成代码的输出侧版权问题不同。经合组织关于 AI 治理框架的报告（OECD，2025）和 Nannini 等人（2026）对智能体提供商合规义务的早期分析，勾勒了监管面向的接口可能是什么样子，而不规定具体细节。

对照第 5 节分析的权限管道阅读，当前架构的两个属性在此约束下是开放的。首先，论文记录的优先拒绝评估可以通过会话 transcript（第 9 节）在内部审计，但尚无法以新兴框架（如 GPAI 实践守则（European Commission，2025a））所设想的形式进行外部审计。其次，价值观优于规则原则（论文将其与确定性 guardrails 配对）是否承认合规审查可能要求的显式规则表述，这是一个进一步的开放问题。两个属性都位于 harness 而非模型内部，这可能是未来架构需要暴露新接口的地方。

### 12.6 评估 Lens 重访：长期人类能力

第 2.4 节将长期人类能力保存作为分析 lens 引入，而非共同平等的设计价值观；第 11.2 和 11.4 节用外部证据扩展了 lens（感知与测量生产力对比、理解力丧失、复杂性增加、技术债务持久化、神经连接持久化、早期职业招聘下降）；第 14 节 pivot："未来系统可以将该可持续性差距视为一流设计问题，而非下游评估指标。"这个 pivot 是否可能，以及一流处理需要哪些架构机制，是本节记录的最后开放问题。

两个子问题将测量差距与设计差距分开。首先，是否可以在会话粒度上测量激励 lens 的经验主张。现有的引用在会话到数月的时间尺度上运作（Becker 等人，2025 年的 16 名开发者随机对照试验；Shen 和 Tamkin（2026）的理解测试比较；Kosmyna 等人，2025）的脑电图研究；He 等人（2025）的 807 个仓库因果分析；Liu 等人（2026）的 304,000 次提交审计；Rak（2025）的招聘系列），但第 3、4 和 7 节记录的 harness 未暴露用于理解或约定漂移的 per-session 信号。程序员交互模式（Barke 等人，2023）和 AI 诱导的代码安全回归（Perry 等人，2023）的相关工作勾勒了会话粒度测量；Aiersilan（2026）提出了用于会话级认知卸载探测的协议。其次，架构是否可以响应此类测量（一旦存在）（类似于 Rajasekaran（2026）应用在人类循环、理解保护 surfaces 或尚未命名的机制的生成器-评估器分离的模拟）这是第 14 节提出的设计差距问题。论文对哪种机制类别是适当的不持立场，而本文记录的 harness 是否甚至是该操作的正确位置（与 IDE、组织或人类发展循环相反）是一个架构分析无法判断的问题；第 13 节调查的相关工作和第 14 节的可持续性 pivot 标记了本文结束这个问题的地方。

## 13 相关工作

### 13.1 编码智能体分类学

AI 编码工具可以按其所支持的自住行动程度进行分类（表 5）。内联补全工具（如 GitHub Copilot（Chen 等人，2021））在编辑器内建议代码片段，无需自住行动。包括 Cursor 和 Windsurf 在内的聊天集成产品增加了会话交互和多文件编辑功能，但仍与 IDE 环境耦合。包括 Claude Code、OpenAI 的 Codex CLI 和 Aider（Gauthier，2024）在内的智能体 CLI 工具从命令行运行，能够在单个请求内自主执行 shell 命令、读取和写入文件以及迭代输出。像 Devin、SWE-Agent（Yang 等人，2024）和 OpenHands（Wang 等人，2024b）这样的完全自住系统旨在实现最少的人类监督，通常在沙箱化云环境中运行。

**表 5 按自住行动程度分类的 AI 编码工具。**

| 类别 | 示例 | 模式 |
|------|------|------|
| 内联补全 | Copilot、Tabnine | 编辑器插件 |
| 聊天集成 | Cursor、Windsurf、Cody | IDE 耦合产品 |
| 智能体 CLI | Claude Code、Codex CLI、Aider | 工具使用循环 |
| 完全自住 | Devin、SWE-Agent、OpenHands | 沙箱 + 规划 |

Claude Code 与更高自住程度的智能体共享功能（自动模式分类器、后台智能体执行、远程环境），但默认保留交互式批准。SWE-Bench（Jimenez 等人，2023）和 HumanEval（Chen 等人，2021）等评估基准推动了学术界对编码智能体的大部分关注。本文从源代码审视 Claude Code 的内部架构。

### 13.2 智能体架构模式

Claude Code 的核心循环遵循 ReAct 模式（Yao 等人，2022）：模型生成推理和工具调用，harness 执行操作，结果反馈到下一次迭代。Toolformer（Schick 等人，2023）证明了语言模型可以学习使用工具；Claude Code 使用多达 54 个内置工具和分层权限系统。更大的设计空间已由多项调查绘制。Weng（2023）提出了现在已成为标准的分解为规划、记忆和工具使用，Wang 等人（2024a）编目了早期自住智能体工作。Xu（2026）围绕三个反复出现的权衡（自住性 vs. 可控性、延迟 vs. 准确性、能力 vs. 可靠性）构建领域，这些权衡在我们的整个分析中反复出现，Hu 等人（2024）将智能体设计本身视为对组件、算法和评估函数的搜索问题。本文描述了该空间中的一个特定点。

AutoGen（Wu 等人，2024）、LangChain 和 CrewAI 等多智能体编排框架提供了基于会话的智能体协调。Claude Code 的子智能体委托（第 8 节）包括权限覆盖优先级、两级权限作用域和每个子智能体的独立 transcript 文件。LATS（Zhou 等人，2023）在树搜索框架中统一了推理、行动和规划；Claude Code 的计划权限模式实现了一种更简单的计划然后执行的方法。

从业者写作已收敛到 Claude Code 架构体现的几个反复出现的模式。Anthropic 自己的《构建有效智能体》（Schluntz 和 Zhang，2024）区分了智能体和工作流，并主张使用简单的可组合模式而非繁重的框架。Martin（2026）综合了在生产系统中观察到的七种模式，包括给予智能体文件系统和 shell 访问作为通用操作层，以及按需发现操作而非预先加载每个工具模式。Chase（2025）观察到 Claude Code 的计划工具“基本上是一个空操作”，其价值在于保持智能体在轨道上，而非执行任何外部计算。Wang（2025）认为权威是学术框架最常忽略的元素，称信任为生产智能体设计中“最被忽视的元素”，第 5 节的权限分析试图弥合这一差距。Huyen（2025）使复合错误问题具体化：在 95% 的每步准确率下，100 步任务只有 0.6% 的时间成功，这促使了我们在第 4 和第 5 节中追踪的每步验证模式。

**上下文管理。** 表 6 展示了上下文管理方法的设计空间分类法。Claude Code 的五层压缩管道在升级前在不同粒度级别应用多种策略，具有缓存感知压缩和读取时虚拟视图语义。Zhang 等人（2025a）描述了此设计缓解的两种失败模式（丢失领域细节的摘要，以及迭代上下文重写中的细节丢失），而是提议将上下文视为随时间累积策略的“进化剧本”。Claude Code 的方法与此框架一致，因为 CLAUDE.md 层次结构累积结构化指令而非重复摘要它们。Hu 等人（2025）区分了上下文工程和智能体记忆：上下文工程处理临时汇编，而记忆涵盖持久的事实知识和经验痕迹。Claude Code 的架构以相同方式分离两者，将压缩管道与基于文件的记忆层次结构配对。

**安全与权限。** 生产编码智能体采用沿三个轴变化的安全架构：批准模型（每动作提示、分类器介导的自动化，或无提示的事后审查）、隔离边界（操作系统级容器、文件系统沙箱、权限作用域工具池，或无）和恢复机制（版本控制回滚、会话作用域权限重置，或基于检查点的回退）。SWE-Agent 和 OpenHands（Yang 等人，2024；Wang 等人，2024b）主要依赖 Docker 容器隔离，提供约束所有智能体操作的环境级沙箱。Codex CLI 支持 shell 命令的沙箱模式和批准策略。Aider（Gauthier，2024）使用 Git 作为其主要安全机制，通过版本控制使所有更改可逆。Claude Code 结合了每动作优先拒绝规则、用于自动批准的 ML 分类器、可选 shell 沙箱和会话作用域权限非恢复，叠加多个机制而非依赖单一隔离边界。

**协议与可扩展性。** Claude Code 作为主要外部工具集成的 Model Context Protocol 已成为一个事实标准，拥有大量生态系统及相应的攻击面。Hou 等人（2025）编目了横跨 26 个主要目录的数千个社区开发的 MCP 服务器，并将 MCP 特有的威胁组织为四个攻击者类别和十六种场景，包括工具中毒、拉地毯和跨服务器隐蔽攻击。第 5 节分析的权限和拒绝规则机制以及第 6.2 节的预过滤步骤可以被视为该调查所呼吁的缓解措施的运行时部分。

**软件架构。** 分层架构模式（Garlan 等人，1993）启发了我们的五层分解。基于角色的访问控制模型（Sandhu 等人，2002）为权限模式系统提供了理论支持。浏览器沙箱（Reis 和 Gribble，2009）是一种类似的每进程隔离方法。多智能体系统理论（Wooldridge，2009）有助于解释子智能体委托。

**定位。** 先前的编码智能体工作集中在基准测试（智能体解决问题的能力）、框架（如何组合智能体）和产品（用户可以做什么）上。本文贡献了对生产编码智能体的基于源码的设计空间分析，使用源码级分析和架构比较来揭示设计选择和权衡。它借鉴了软件架构案例研究传统（Garlan 等人，1993），但通过系统识别设计问题、绘制替代方案并对比 Claude Code 与 OpenClaw（一个在不同部署环境中运行的独立 AI 智能体系统）的选择，将其应用于基于 LLM 的智能体。

## 14 结论

本文表明，生产级编码智能体可以被理解为对反复出现的设计问题的一组答案：推理相对于安全带的位置、执行、安全、扩展性、上下文、委托和持久化如何组织，以及这些选择编码了哪些权衡。Claude Code 在该空间中占据了一个清晰的设计点。它赋予模型广泛的本地自主权，同时围绕它构建了密集的确定性安全带，用于权限管理、工具路由、上下文压缩、扩展性和会话恢复。通过第 2 节识别的五个价值观和十三个设计原则来审视，这些选择是连贯的而非随意的：系统始终优先考虑人类决策权威、安全、可靠执行、能力增强和情境适应性。

OpenClaw 的比较通过表明相同的设计问题在不同的智能体系统中反复出现但产生不同答案来强化主要架构发现。Claude Code 在 CLI 安全带内投资于逐动作安全分类和渐进上下文压缩，而 OpenClaw 在多通道网关内投资于周边级访问控制和结构化长期记忆。两个系统甚至可以组合：OpenClaw 通过 ACP 将 Claude Code 作为外部安全带托管。对于智能体构建者而言，因此最重要的开放问题不是如何添加更多自主权，而是如何在时间推移中保持人类能力。正如第 2.4 节的评估视角、第 11 节的分析和第 12 节调查的开放问题所记录的那样，架构提供的有限机制来明确保持长期人类理解、代码库一致性或开发者 pipeline。未来的系统可以将该可持续性差距视为一流设计问题，而非下游评估指标。

## 附录 B 证据基础与方法论

本附录描述了本研究的证据来源、分析过程和认识论限制。

### B.1 证据基础与证据层级

本文的主张在三个证据层级上有依据：

- **层级 A（产品文档化）**：来自官方 Anthropic 文档和工程出版物的主张。这些建立产品意图但可能不反映内部实现。
- **层级 B（代码验证）**：引用提取的 TypeScript 代码库（v2.1.88，从公开可用的 npm 包提取）中的特定文件和函数的主张。这是最强的证据层级。
- **层级 C（重构）**：来自社区分析、OpenClaw 结构比较或从代码模式推断的主张。这些以对冲语言表述。

源语料库包含约 1,884 个文件，总计约 512K 行 TypeScript。OpenClaw 用于校准而非 ground truth。

### B.2 设计空间分析过程

设计问题通过检查每个子系统的反复出现选择点来识别，其中其他生产智能体存在替代设计。通过特定源文件和函数实现（层级 B 证据）追踪 Claude Code 对每个问题的答案。五值框架（人类决策权威、安全、安保与隐私、可靠执行、能力增强和情境适应性）从官方文档和创建者声明（层级 A）中识别，然后通过十三个设计原则追踪到架构决策。长期能力保持作为评估视角而非设计价值单独处理，因为它在架构或 Anthropic 声明的价值中未作为主要驱动力显著反映（第 2.4 节）。Token 经济学作为横切约束，同时约束所有五个价值观，揭示个体子系统选择如何在共同资源压力下相互作用。

### B.3 局限性

- **静态快照**。分析反映一个版本（v2.1.88）。功能标志（例如 TRANSCRIPT_CLASSIFIER、CONTEXT_COLLAPSE）创建构建时可变性；不同的构建目标可能产生功能不同的应用程序。
- **逆向工程认识论**。源代码揭示已实现的结构、控制流、依赖和功能门控。它无法确认设计意图、启用的生产标志、运行时流行度或未发布的行為。
- **单系统分析**。发现描述 Claude Code 的设计空间，而非编码智能体的整个设计空间。泛化受限。
- **OpenClaw 快照**。OpenClaw 分析反映特定开发状态，可能不代表其当前能力。
