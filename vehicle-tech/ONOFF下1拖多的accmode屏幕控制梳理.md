# ONOFF下 1拖多的 accmode屏幕控制梳理 


档位：AvvOff 转AccOn   宠物模式:  不开启       accmode：wakeup，拉起应用                                                       中控：亮屏     副驾：亮屏

档位：AccOn 转 AccOff  宠物模式：持锁           accmode：探测宠物模式持锁，走 setdisplay(1) + kill user100 中控：亮屏    副驾：灭屏

档位：AccOn 转 AccOff  宠物模式：退出           accmode：acclock 取消，走 startAccOFF                                    中控：灭屏    副驾：灭屏

档位：AccOff 转 AccON  宠物模式：一直持锁   accmode：acclock，没有走 startAccOn 无人引导拉起副驾       中控：亮屏    副驾：无法灭屏




你汇总的这个场景矩阵非常清晰，精准地抓住了车载开发中"特殊业务模式（如宠物模式、营地模式、哨兵模式）"与"物理档位切换"交织时的核心痛点。

特别是第四个场景：**当车子在 OFF 状态下由于宠物模式维持中控亮屏，此时用户突然点火（OFF $\rightarrow$ ON），由于中控原本就是亮的，系统没有走标准的 `startAccOn` 流程，导致副驾屏丢失了唤醒引导，或者维持在某种错误的"无法灭屏/无法亮屏"的中间态。**

针对你梳理的这四个场景，我们用前文设计的"状态差驱动（Target vs Current）"**和**"屏幕独立执行管线"架构来逐一拆解和解决。

## 三项核心修正原则（彻底解决第四异常场景）

要解决第四点，必须在 `accmode` 中确立三个铁律：

1. **全局信号（AccOn）是最高优先级广播**：只要挡位切到 ON，所有屏幕的 `TargetState` 必须**强制收敛为 `STATE_ON`**，无论它之前因为什么模式持锁。
2. **"按需触发"代替"整机路由"**：不能因为中控屏已经是亮的，就跳过整个 `startAccOn`。上电流程应该拆解为 `DisplayA.startOn()` 和 `DisplayB.startOn()`，各自比对。
3. **副驾的"生命周期补偿机制"**：如果副驾在 OFF 期间应用被 kill 了（如场景二），那么在进入场景四（OFF $\rightarrow$ ON）时，副驾执行管线发现自己的 `CurrentState == STATE_REAL_OFF`，它必须**主动触发应用拉起（引导 Launcher 跑起来）**。

## 场景流逐一对齐与重构解决方案

我们引入两个关键变量来定义每块屏的状态：

- **`Current`** (当前状态): `ON` (亮且有应用) / `OFF_MUTE` (灭屏且应用被kill)
- **`Target`** (基于当前挡位和锁计算出的目标): `ON` / `OFF`

### 场景一：AvvOff $\rightarrow$ AccOn（宠物模式：不开启）

- **初始状态**：中控 `OFF_MUTE`，副驾 `OFF_MUTE`。
- **变化发生**：挡位变 ON。
- **仲裁结果**：
  - 中控 `Target = ON` (与 Current 不符 $\rightarrow$ 触发亮屏 + 拉应用)
  - 副驾 `Target = ON` (与 Current 不符 $\rightarrow$ 触发亮屏 + 拉应用)
- **最终状态**：中控：**亮**，副驾：**亮**。（完全正常）

### 场景二：AccOn $\rightarrow$ AccOff（宠物模式：开启持锁）

- **初始状态**：中控 `ON`，副驾 `ON`。
- **变化发生**：挡位变 OFF，宠物模式在中控持锁。
- **仲裁结果**：
  - 中控：虽有 OFF 信号，但有宠物模式锁 $\rightarrow$ `Target = ON`。因为 `Target == Current`，**中控不做任何动作，保持亮屏与应用运行**。
  - 副驾：OFF 信号，且无锁 $\rightarrow$ `Target = OFF`。与 Current 不符 $\rightarrow$ **触发执行管线：灭副驾屏 + `kill user100`（清空副驾应用）**。
- **最终状态**：中控：**亮**，副驾：**灭**。（符合预期）

### 场景三：AccOn $\rightarrow$ AccOff（宠物模式：未开启/退出）

- **初始状态**：中控 `ON`，副驾 `ON`。
- **变化发生**：挡位变 OFF，无任何锁。
- **仲裁结果**：
  - 中控 `Target = OFF` (与 Current 不符 $\rightarrow$ 执行 `startAccOff` $\rightarrow$ 灭屏杀应用)
  - 副驾 `Target = OFF` (与 Current 不符 $\rightarrow$ 执行 `startAccOff` $\rightarrow$ 灭屏杀应用)
- **最终状态**：中控：**灭**，副驾：**灭**。（完全正常）

### 场景四（核心痛点）：AccOff $\rightarrow$ AccON（宠物模式：一直持锁）

- **初始状态（承接场景二）**：中控 `ON`（宠物模式运行中），副驾 `OFF_MUTE`（背光灭且应用已杀）。
- **变化发生**：用户上车，挡位从 AccOff 切回 AccOn。

#### ❌ 旧逻辑失效原因分析：

旧逻辑是"整机式"的。系统检查发现中控已经是亮屏持锁状态，认为系统"已经是在类似 ON 的状态下了"，导致没有触发全局的 `startAccOn` 广播，副驾屏成了被遗忘的孤儿，既没有收到上电指令，也没有人引导拉起副驾的应用桌面。

#### 新架构收敛解决工作流：

当挡位切到 AccOn，`accmode` 独立计算两块屏的收敛策略：

```
       [ 触发 AccOff -> AccOn 信号 ]
                    |
                    v
         accmode 策略中心重新计算
                    |
      +-------------+-------------+
      |                           |
      v                           v
|【中控屏 (Display 0)】      【副驾屏 (Display 1)】
- Target = ON               - Target = ON
- Current = ON              - Current = OFF_MUTE
      |                           |
      v                           v
 [Target == Current]         [Target != Current]
      |                           |
      v                           v
 保持原样，无缝衔接          【触发副驾独立唤醒管线】
 (宠物模式丝滑切入常驻桌面)   1. SurfaceFlinger 打开物理背光
                             2. 发送独立引导指令：
                                ATMS 在 Display 1 上重新
                                实例化并拉起副驾 Launcher
```

## 4. 落地到架构设计中的修改点

为了实现上述流转，你只需要在 Framework 层做两处修改：

1. **改造 `accmode` 的状态检查触发源**：

   不要只在"有锁/无锁"变化时才去检查屏幕。**挡位切换（AccOff $\rightarrow$ AccOn）必须作为一个最高优先级的 `DIRTY_VEHICLE_POWER` 信号**，强制刷新所有屏幕的 `TargetState`。

2. **重构 `startAccOn` 的执行粒度**：

   把原先高耦合的 `startAccOn()` 函数拆解，支持传入 `DisplayId`。

   - 当从宠物模式（AccOff）切回 AccOn 时，调用 `startAccOn(DISPLAY_B)`。
   - 该函数内部不再关心整车电源，它只看到副驾当前是灭的，就会精准执行：**打开副驾屏幕通路 $\rightarrow$ 调用 `ActivityTaskManagerService` 在副驾屏上拉起指定的 User / 应用（User 100）**。

通过这种**以每块屏幕的"期望与现状差"来驱动**的设计，场景四的异常情况在逻辑上被天然消灭了，因为副驾屏的 `Target(ON) != Current(OFF_MUTE)` 会强制逼迫系统去执行副驾的唤醒与应用引导流程。



# 多用户场景

在 Android 的"一拖 N"多屏座舱架构中，多用户管理（Multi-User Management）**和**多显示屏（Multi-Display）的结合，是实现"中控看导航，副驾看视频且互不干扰"的核心底层技术。

在传统的手机或单屏车机中，Android 的多用户是**互斥切换**的（即 User 0 处于前台时，User 10 SYSTEM 或其他用户必须在后台冻结/休眠）。但在单芯片多屏（一拖 N）场景下，Android 演进出了多用户同时在前台运行（Multi-User Multi-Display, 简称 MUMD）的全新架构。

以下从架构关系和工作流两个维度，为你拆解副驾屏的多用户管理机制。

## 一、 中控与副驾在 1 拖 N 场景下的用户关系

在原生 Android Automotive OS (AAOS) 的标准设计中，中控和副驾的地位与运行的用户有着本质的区别。系统将用户划分为**主用户、系统用户和乘客用户**。

```
                       +-----------------------------------+
                       |      Android System (User 0)      |
                       | (系统核心服务: HAL/SurfaceFlinger) |
                       +-----------------------------------+
                                   /           \
                                  /             \
                                 v               v
           +---------------------------+   +---------------------------+
           |   Main User (User 10)     |   |  Passenger User (User 11) |
           +---------------------------+   +---------------------------+
           | - 绑定 Display 0 (中控)    |   | - 绑定 Display 1 (副驾)    |
           | - 拥有系统完整控制权       |   | - 仅拥有受限娱乐权限       |
           | - 账号: 驾驶员A的账号      |   | - 账号: 独立或游客账号     |
           +---------------------------+   +---------------------------+
```

### 1. 系统用户 (User 0 / SYSTEM)

- **角色**：幕后大管家。
- **关系**：不论车里有多少块屏、多少个用户，**User 0 在整车中永远只有一个**。它不直接对应任何一块看得见的屏幕，而是常驻后台，运行着系统的核心服务（如 `CarPowerManagementService`、`SurfaceFlinger`、音频路由等）。它负责调度和供养所有可见的用户。

### 2. 主驾驶用户 (通常为 User 10 / Main User)

- **角色**：整车的主控核心。
- **关系**：与中控屏（Display 0）强绑定。主驾驶用户通常拥有最高的系统权限，可以控制车辆设置（空调、ADAS、车窗）、查看仪表信息、管理其他屏幕的开关。

### 3. 副驾驶/后排乘客用户 (如 User 11, User 12 / Passenger User)

- **角色**：独立的娱乐终端。
- **关系**：与**副驾屏（Display 1）\**强绑定。这是一个\**完全独立运行的前台用户**。
  - 它有自己独立的沙盒存储（副驾登录自己的微信/爱奇艺，缓存不会污染主驾）。
  - 它的生命周期由主驾或系统管理模块（如你们的 `accmode`）控制。
  - 它的功能受到严格限制（Permission Policy），无法调用涉及驾驶安全的敏感车载接口（例如无法关闭车身稳定系统 ESC）。

## 二、 副驾屏场景下的多用户管理是如何进行的？

为了让副驾屏作为独立用户顺畅运行，Android Framework 层在组件生命周期、窗口隔离和音频流上做了深度的定制：

### 1. 空间的绝对隔离：多用户沙盒与多屏绑定

在 Framework 初始化时，系统服务会通过 `DisplayManager` 和 `UserManager` 进行"屏-人绑定（Display-User Assignment）"。

- 当系统识别到副驾屏（Display 1）上电时，`CarUserService` 会启动一个专为副驾准备的乘客用户（如 User 100）。
- 核心关键在于 `ActivityTaskManagerService (ATMS)` 的物理隔离：当 User 100 启动应用时，ATMS 会强制将该应用的 `DisplayId` 设为 1。这意味着，副驾用户启动的任何 Activity，**绝对不可能肉眼可见地跳到中控屏去显示**。

### 2. 状态的并行运行：前台多用户同时激活

在普通 Android 手机上，切换用户会触发旧用户 `switchUser` 走后台挂起流程。但在车机多屏下，Android 引入了 `startUserInForegroundOnDisplay(userId, displayId)` 接口。

- **主驾（User 10）** 在 Display 0 处于 `Foreground` 状态。
- **副驾（User 100）** 在 Display 1 **同时**处于 `Foreground` 状态。
- 两个用户各自拥有独立的生命周期调度，WMS（窗口管理器）会为每块屏独立计算焦点（Focus Window），使得主驾操作中控导航时，完全不影响副驾在副驾屏上刷短视频的触摸响应。

### 3. 音频路由的精细化控制（音频多音区 Audio Zone）

多用户管理不仅是看和触控，还有声音。

- Android Automotive 引入了 **Audio Zone（音频分区）** 概念。中控屏默认属于 `PRIMARY_ZONE`（主音区，声音走全车扬声器或主驾头枕）。
- 副驾屏和副驾用户被划分到 `ZONE_1`（副驾音区）。
- 当副驾用户（User 100）的应用请求播放音频时，Android 的 `CarAudioService` 会拦截该请求，并根据启动该应用的 `uid`（包含了 UserId 信息），自动将音频硬路由到副驾专属的硬件通道（如副驾蓝牙耳机，或副驾侧的独立扬声器），实现听觉隔离。

## 三、 回到你的业务：accmode 视角下的多用户生命周期

结合你之前提到的 `accmode` 业务（管理 ONOFF、亮灭屏、杀应用），在多用户架构下，你们的工作流其实是在管理"特定屏幕绑定的特定用户"。

以你之前的场景为例：**"档位：AccOn 转 AccOff，宠物模式持锁，中控亮，副驾灭"**：

1. **旧的做法**：无差别杀掉属于副驾的应用进程。
2. **多用户架构下的标准做法**：
   - `accmode` 探测到副驾需要下电。
   - `accmode` 根本不需要去肉眼识别副驾跑了哪些应用，而是直接向 `CarUserService` 发出指令："停止副驾用户"。
   - 命令：`UserManager.stopUser(100, true)`（假设副驾是 User 100）。
   - Android 系统会自动销毁 User 100 的所有前台 Task、释放内存、清理缓存、关闭副驾屏，极其干净。
3. **当 AccOff 转 AccOn 恢复时**：
   - `accmode` 发现副驾当前没有用户在线，直接调用 `CarUserService.startUserInForegroundOnDisplay(100, 1)`。
   - 系统会自动在副驾屏（Display 1）上以 User 100 的身份，重新干净地拉起副驾的 Launcher 桌面，完美收敛。




---




这是一个非常典型的汽车座舱智能化带来的架构演进问题（从单屏到**一芯多屏 Single SoC Multi-Display**）。

在单屏时代，你们的 `accmode` 逻辑其实是将**电源状态（ON/OFF）**、屏幕物理状态（Display Power）**和**业务逻辑（杀应用/持锁）强行绑定在一起的。要实现"OFF 状态下，A 屏亮、B 屏不亮"的精细化控制，核心解耦思路是：**将"车机电源状态（Vehicle Power State）"与"各屏幕显示状态（Display Power State）"彻底剥离。**

下面是针对 Android Framework 层的重构设计方案：

## 1. 核心架构重构：引入 Multi-Display 状态管理器

不能再让 `accmode` 直接决定整机的亮灭屏，而是要引入一个屏幕策略管理器（DisplayPolicyManager 或 DisplayPowerController）来做中介。

### 概念抽象

- **System Power State (系统级状态)**：由原有的 `accmode` 或 `CarPowerManagementService (CPMS)` 管理（如：ON, OFF, SLEEP）。
- **Display Power State (屏幕级状态)**：每块屏幕（Display ID 0, 1, 2...）都有独立的物理状态（ON, OFF, DOZE）。

## 2. 关键设计实现方案

### 方案一：升级已有的锁机制（逻辑最延续，改动较小）

之前你们用的是"全局锁"，现在需要将其升级为"带 DisplayId 属性的锁"。

- **设计逻辑**：当某个特殊应用（如：哨兵模式、OTA 提示、后台充电动画）需要在 OFF 状态下亮起 A 屏时，它申请锁的时候必须指定 `DisplayId`。
- **Framework 实现**：
  1. 扩展 `accmode` 的锁接口：`acquireWakeLockForDisplay(IBinder token, int displayId, String tag)`。
  2. `accmode` 收到 OFF 信号时，**不再直接向底层下发整机下电指令**，而是检查当前持锁情况。
  3. 如果发现有应用持有了 `Display 0` 的锁，系统保持伪 OFF 状态（SoC 不休眠），但 `accmode` 会通知 `LocalDisplayAdapter` 或底层 HAL 层：**关闭 Display 1 的背光，保持 Display 0 的背光。**

### 方案二：对齐 Android Automotive OS (AAOS) 标准架构（推荐，扩展性强）

如果你们使用的是较新的 Android 版本（Android 10+，特别是 Android 13/14），建议利用谷歌原生针对多屏的布局。

```
                  +--------------------------------+
                  |  accmode / CarPowerManager     |
                  +--------------------------------+
                                  |
                                  v
                  +--------------------------------+
                  |  DisplayPowerController (DPC)  |
                  | (维护 Display 0, 1... 的状态机) |
                  +--------------------------------+
                     /                            \
                    v                              v
        +-----------------------+      +-----------------------+
        |  Display 0 (仪表/A)    |      |  Display 1 (副驾/B)    |
        |  状态: ON              |      |  状态: OFF             |
        +-----------------------+      +-----------------------+
```

1. **利用 `DisplayPowerController (DPC)` 路由**：

   Android Framework 内部的 `PowerManagerService (PMS)` 针对每块物理屏幕都会创建一个 `DisplayPowerController`。你需要修改 PMS，使其支持独立控制每块屏幕的 `TargetPowerState`。

2. **应用层解耦（不再感知下电锁）**：

   特殊应用不需要向 `accmode` 申请不准下电的锁，而是直接请求向 A 屏请求"亮屏"。

   - 应用通过 `ActivityOptions.setLaunchDisplayId(A_DISPLAY_ID)` 将自己投射到 A 屏。
   - WindowManagerService (WMS) 发现 A 屏有可见窗口（Window）且该窗口带有 `FLAG_KEEP_SCREEN_ON`。
   - WMS 将此需求通知 PMS，PMS 仅让 `DisplayPowerController[A]` 保持 ON，而 `DisplayPowerController[B]` 因为没有可见窗口且系统处于 OFF 状态，直接走向销毁或灭屏（D3/OFF）状态。

## 3. 针对"杀应用"管理模块的重构策略

既然在 OFF 状态下允许 A 屏亮起跑应用，那么原有的"OFF 触发杀应用"的清理逻辑必须建立"白名单"与"屏幕绑定"机制：

1. **按屏幕可见性决定生死**：
   - 当进入 OFF 状态，B 屏确认灭屏。`accmode` 应该遍历当前运行的应用。
   - 如果应用运行在 B 屏（可以通过 `ActivityRecord.getDisplayId()` 获取），则执行正常的杀进程/回收逻辑。
   - 如果应用运行在 A 屏，且属于本次 OFF 亮屏业务的关联应用（如哨兵模式），则予以豁免。
2. **动态移屏或冻结（可选）**：
   - 有些常驻后台应用（如音乐、导航），在进入 OFF 状态且 A 屏独立亮起时，如果不属于 A 屏业务，应该利用 `ActivityTaskManagerService (ATMS)` 将其移入后台并执行 `freeze`（冻结），不给 CPU 带来额外功耗，而不是一刀切地杀掉。

## 4. 关键避坑指南（车规级考虑）

> ⚠️ **功耗管理（暗流涌动）**
>
> 在单控制器的多屏车机中，即使 B 屏不亮，如果 SoC 仍然处于 ON 状态（为了支持 A 屏跑应用），底层的 GPU、视频解码器可能还在为 B 屏的图层做合成。
>
> **解决办法**：在 Framework 层通知灭 B 屏的同时，必须调用 `SurfaceFlinger` 的 `setPowerMode(DisplayId_B, SurfaceControl.POWER_MODE_OFF)`。这会彻底停止 B 屏的 VSync 信号和图层合成，最大程度降低静态功耗，防止电瓶亏电。

> ⚠️ **音频路由同步**
>
> 屏幕 A 亮起时，如果该应用需要发声（比如哨兵模式报警），需要确保音频也只路由到对应的声场，而原本属于 B 屏的音频通道（如副驾蓝牙耳机/副驾音区）应当被 `AudioService` 彻底静音或关闭。

## 总结建议

修改的切入点可以放在 **`PowerManagerService` 对 `DisplayPowerRequest` 的处理上**。不要让 `accmode` 直接去控制硬件，让 `accmode` 只充当"车身状态的输入者"。

由 `accmode` 告诉系统："现在车子是 OFF 状态，但由于有锁/有业务，我允许系统处于 **Pseudo-OFF（伪休眠）** 状态"；然后由 `PowerManagerService` 和 `WindowManagerService` 根据当前各个屏幕上的应用窗口状态，去精准给 A 屏供电、给 B 屏断电。





---

抛开具体的代码实现，我们将这个需求抽象为**系统架构**与业务工作流（时序与状态机）的设计。

在多屏多任务（一芯多屏）的架构下，核心的解决思想是：**"解耦核心状态，策略集中仲裁，各屏异步收敛"。**

## 一、 系统架构设计 (Architecture Design)

要解决"中控亮、副驾灭并杀应用"的需求，必须打破过去 `accmode` 直接控制整机电源的扁平结构，演进为**分层、分布式**的屏幕管理架构。

```
+-----------------------------------------------------------------------+
|  1. 输入感知层 (Input Layer)                                            |
|     - 车身电源信号 (CAN: ON / OFF)                                     |
|     - 应用级电源锁请求 (Display WakeLock: DisplayId=0/1, AppKey)       |
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
|  2. 核心仲裁层 (Arbitration Layer: accmode)                           |
|     - 全局时序控制器 (Time & Sequence Manager): 生成状态版本号(Seq)，防抖  |
|     - 屏幕策略仲裁器 (Display Policy Arbitrator): 决定每块屏的「期望状态」|
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
|  3. 业务执行层 (Execution Layer: 各子系统)                             |
|     - 窗口/组件管理器 (WMS/ATMS): 负责按 DisplayId 冻结/销毁/拉起应用     |
|     - 图层与渲染器 (SurfaceFlinger): 负责控制特定 DisplayId 的 VSync 与背光|
+-----------------------------------------------------------------------+
```

### 核心解耦概念：物理状态 vs 期望状态

- **车身电源状态（Vehicle Power State）**：整车的物理状态，只有 `ON` 和 `OFF`。
- **屏幕期望状态（Display Target State）**：每块屏幕根据"车身状态 + 自己的电源锁"计算出的**独立目标**。
  - *中控屏目标*：`ON` (因为车身是 OFF，但有哨兵模式等锁).
  - *副驾屏目标*：`OFF` (车身是 OFF，且无锁).

## 二、 核心工作流设计 (Workflow Design)

工作流的核心在于应对**正常下电逻辑**与**快速 ON/OFF 逆转**时的状态对齐。

### 1. 正常下电工作流：中控独立持锁亮屏，副驾灭屏杀应用

当车辆从 ON 切换到 OFF，且中控应用持锁时，系统内部的流转逻辑如下：

```
 车身信号(OFF)       accmode仲裁中心         中控执行管线(A)         副驾执行管线(B)
      |                    |                    |                    |
      |----(1) 物理OFF---->|                    |                    |
      |                    |-- (2) 评估各屏锁 --|                    |
      |                    |    中控有锁->保持ON |                    |
      |                    |    副驾无锁->去OFF  |                    |
      |                    |                    |                    |
      |                    |---(3) 维持状态---->|                    |
      |                    |   (背光/应用不变)   |                    |
      |                    |                    |                    |
      |                    |----------------(4) 触发伪休眠---------->|
      |                    |                    |                    | 关背光/停VSync
      |                    |                    |                    | 开启500ms清理倒计时
      |                    |                    |                    |
      |                    |----------(5) 500ms 缓冲区超时---------->|
      |                    |                    |                    | 
      |                    |                    |                    | 获取Display B的Task
      |                    |                    |                    | 过滤系统白名单
      |                    |                    |                    | 执行Kill应用
```

### 2. 瞬态反转工作流：快速 ON -> OFF -> ON 规避设计

这是测试中最容易出现"副驾应用死在半路，点火后副驾黑屏"的场景。我们通过"延迟执行 + 令牌截断"的工作流来规避。

#### 场景：系统收到 OFF，副驾开始走灭屏流程，100毫秒后系统突然又收到 ON。

```
 车身信号            accmode仲裁中心           序列号令牌(Seq)        副驾执行管线(B)
    |                      |                        |                    |
    |---(1) 收到 OFF ----->|                        |                    |
    |                      |-- (2) 事务生成 -------->| [Seq = 101]        |
    |                      |                         |                    |
    |                      |-- (3) 发送异步清理指令 --------------------->| (进入500ms等待期)
    |                      |       带有令牌 [Seq=101] |                    |
    |                      |                        |                    |
    |                      |                        |                    | (此时副驾应用还活着)
    |                      |                        |                    |
    |---(4) 突发 ON ------>|                        |                    |
    |                      |-- (5) 事务更新 -------->| [Seq = 102]        |
    |                      |                        |                    |
    |                      |-- (6) 发送恢复上电指令 --------------------->| 
    |                      |       带有令牌 [Seq=102] |                    | 
    |                      |                        |                    | 瞬间恢复背光与供电
    |                      |                        |                    |
    |                      |                        |                    |
    |~~~~~~~~~~~~~~~~~~~~~~|~~~~~~~~~~~~~~~~~~~~~~~~|~~~~~~~~~~~~~~~~~~~~|
    | (500ms时间到，原[Seq=101]的延时杀应用任务在后台触发)                        |
    |                      |                        |                    |
    |                      |                        |                    |-- (7) 拦截检查:
    |                      |                        |                    |   任务Seq(101) 
    |                      |                        |                    |   不等于
    |                      |                        |                    |   当前最新Seq(102)
    |                      |                        |                    |   [拒绝执行杀应用]
    |                      |                        |                    |
```

## 三、 状态机收敛规则（关键设计防线）

为了保证无论外部物理信号如何"抖动"，系统最终都能正确收敛，仲裁层必须遵循以下三条**无状态判定规则**：

### 规则一：动作由"当前状态差"决定，而不是"事件"决定

当状态机被唤醒检查时，只做一件事：对比 **`TargetState`（最新期望）** 与 **`CurrentState`（当前实际）**。

- 如果 `Target == Current`：说明受到了抖动信号影响，系统兜了一圈又回到了原点。**立刻取消后续的异步清理任务（如杀应用），硬件不做任何切换。**
- 如果 `Target != Current`：说明状态确实变了，启动状态转移管线。

### 规则二：清理事务不可逆临界点

在副驾屏执行清理时，将其分为两段：

1. **可逆阶段（前 500ms 伪休眠）**：应用只是不可见、背光灭。此阶段若发生 ON 逆转，直接丢弃清理任务，应用毫无影响。
2. **不可逆阶段（已经调用 Kill 接口）**：如果逆转发生时，应用已经被杀了一半。此时**绝不中断清理**，而是让副驾执行管线"顺其自然地把应用杀干净"，转为 `REAL_OFF` 状态；紧接着，状态机发现当前最新期望是 `ON`，再重新触发一次标准的 `OFF -> ON` 上电唤醒流，由系统重新拉起副驾应用。从而避免了应用进程卡在"半生半死"的中间态。

### 规则三：多屏锁的生命周期跟随屏幕，不跟随整车

当系统处于 OFF 状态，中控因为有锁保持亮屏。

- 一旦中控的应用主动释放了锁，状态机只重新评估中控屏的 `TargetState` 为 `OFF`，并单独触发中控屏的下电和应用清理。
- 此时副驾屏本来就是 `OFF` 状态，因此副驾屏不做任何动作。实现了每块屏幕的生命周期完全独立闭环。
